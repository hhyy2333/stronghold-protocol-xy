# DESIGN §43 — 【特限恢复】下普通形态的模组：始终显示、可更换、两侧同一份 3 级记录（0.19.46，2026-11-03）

## 43. 【特限恢复】下普通形态的模组（0.19.46，2026-11-03）

业主 2026-11-03 原话：「有特限恢复时，未精锐干员只有1、2技能能显示模组，而且不能更换。完善」。

这一节记的是「为什么只有那两个技能带着模组」「模组区块凭什么始终显示」「局内怎么换」「四处界面与战斗
凭什么读同一份数据」四条，以及它们钉住的边界。规范落点：[design/match.md §6](../design/match.md) 的
【特限恢复】④；服务端那一半（`battleInput` 补 `moduleId`、`simdata.getChess` 的 `moduleLevel === 3`）在
§43.5 只做交叉引用，本次没有改服务端。

### 43.1 为什么「只有 1、2 技能」能显示模组

不是模组的问题，是**干员调配存了什么**的问题。

`shared/protocol.js checkLoadout` 只留**不等于默认**的条目：

```js
if (skill === opt.defaultSkill && module === opt.defaultModule) continue;
out[id] = { skill, module };
```

模组是**跟着技能那一条**存下来的（`{ skill, module }` 一起进 `room.loadout.entries`）。于是一名还在用**默认技能**
的干员，压根没有条目 ⇒ `shared/loadoutRecord.js selectedModuleOf` 拿不到任何东西 ⇒ `ui/detailPanel.js` 的
`lo?.module` 为假、整个「模组」区块不画，也就没有可点的更换行。

「1、2 技能能显示」= 「那两个技能不是默认技能」的同义反复：它们各自的条目把模组顺带存进去了。**第 3 个技能
（默认技能）什么都没存**，于是卡片上什么都没有 —— 看起来就像「未精锐干员只有 1、2 技能能显示模组」。

### 43.2 判据只有一份：`normalFormModuleOf`

`shared/loadoutRecord.js normalFormModuleOf(rec, loadout, getChess)` 回答「这个普通形态**现在**用哪个模组」
（`selectedModuleOf` 回答的是「玩家**选过**什么」，差别只有第 3 条）：

1. 干员调配里**选过** ⇒ 那个，按**精锐记录的模组表**校验（普通记录没有 `modules` 列表 —— 模组只挂在精锐记录上，
   `data/chess.json` 135 条普通记录的 `module` 只有「当前生效的那一个」，不是表）；
2. 选的是 **「不装备」** ⇒ `{ id: 'none', none: true }` —— 默认模组的 3 级数据也**不套**；
3. **没选过** ⇒ 精锐记录的**默认模组**（`modules.find(m => m.isDefault)`，`isDefault: true`）—— 与
   `server/sim/simdata.js getChess` 缺省 `moduleId` 的那条回落完全一致；
4. 精锐记录**根本没有模组**（蒂比 / 凛御银灰 / 甄选干员）⇒ `null`（不画模组、不套 3 级）。

客户端 `ui/gameLogic/loadout.js chessLoadout` 与（本次未改的）服务端 `simdata.getChess` 共用这份判据的语义，所以
「卡片说哪个模组」与「战斗打哪个模组」不可能分叉。

### 43.3 卡片：始终画，而且能换

`ui/detailPanel.js ChessDetail`：

- **模组区块**在 `moduleLevel === 3` 时对普通形态**始终**画（`lo?.module` 现在有值了：默认模组也是值）；
- **更换行**的选项从**精锐记录**的模组表来：

  ```js
  const goldenRec = c.isGolden ? c : (c.goldenId ? getChess(c.goldenId) || null : null);
  const modeModules = moduleLevel === 3 && !c.isGolden && Array.isArray(goldenRec?.modules)
    ? [...new Set(goldenRec.modules.map((x) => x?.uniEquipId).filter((id) => id && id !== MODULE_NONE)), MODULE_NONE]
    : null;
  const moduleChoices = modeModules || opt.modules || [];
  ```

- 换的是**同一个干员调配条目**：`swapBaseId = c.isGolden ? c.baseId : c.chessId`，走 `actions.loadout({ [swapBaseId]: { module } })`
  的 `g.loadout` 增量 —— 精锐形态也读这一条，换模组不需要精锐棋子在场。
- `screens/loadout.js RosterRow` 的模组快捷行不再只给精锐渲染（原来的 `golden ? … : null`），没精锐时也能直接点。

**没有这张卡时逐字段不变**：`moduleLevel` 不是 3 ⇒ `modeModules` 是 `null` ⇒ `moduleChoices` 退回 `opt.modules`
（普通形态本来就是空），卡片与改动前完全一样（`test/ui/mode-modules-detail.test.js` 第二条钉住「没有卡就不画」）。

### 43.4 一处客户端/服务端分歧（本次修掉）

普通形态选「不装备」时，`withModuleLevel3(rec, moduleLevels, moduleId)` 在 `null` / 缺省时**回落到 `rec.module.id`**，
而普通记录的 `module.id` 正是默认模组 —— 于是客户端把默认模组的 3 级套上了，服务端却是 `u.moduleId = 'none'`
一个都不套。现在 `chessLoadout` 把 `'none'` **原样**传进去（`withModuleLevel3` 见到 `'none'` 直接返回原记录），两边
都是「一个模组都不套」。

### 43.5 其余界面接上同一份记录（判据只有一份）

新增 `ui/gameLogic/modeModules.js`：`modeModuleLevel(priv)` / `ownsModeModules(priv)` —— `m.private.effects` 里
`iconKind === 'hex'`、`iconId` 去掉 `hex:` 与 `#<copySeq>` 之后等于 `MODE_MODULES_HEX_ID` 就是拥有者，返回 `3`，
否则 `null`。这是客户端**唯一**的所有权判据（`server/match/hextech.js addHexRef` + `player/views.js` 补出 ref id）。
它单独成文件是因为 `placement.js` 已经 import `standIn.js` 的 `deployedRecord`，反过来 import 会成环。

接上的四处（都按「同一份 3 级记录」，且**没有卡时传 `null`、输出逐字段不变**）：

| 界面 | 文件 | 读的是 |
|---|---|---|
| 商店卡的模组徽标 | `ui/shopBar.js ChessCard` | `chessLoadout(..., { moduleLevel: modeModuleLevel(priv), moduleLevels })` |
| 详情卡的攻击范围（画在棋盘上） | `screens/game/range.js inspectRange` | `chessLoadout(detail.chess, …, { moduleLevel, moduleLevels })` |
| 棋盘范围 / 落位轮盘 / 召唤物 ownerRange | `ui/gameLogic/placement.js ownerRangeOf` | `deployedRecord(rec, priv, getChess, backups, { moduleLevel, moduleLevels })` |
| 局内单位记录 | `ui/gameLogic/standIn.js deployedRecord` | 同上（补位分支**不**吃这个 opts） |

`ui/gameLogic/placement.js` 原来的 `ownsModeModules` 改成从 `modeModules.js` `re-export`：导出面与调用点都不动，
目标点规则与 3 级模组从此用同一个判据。顺带修掉「卡面 3 级、棋盘 1 级」—— `attackRangeGrid` 读的是记录里的
`modules`，`withModuleLevel3` 对**普通形态**（本来没有模组列表）会把 3 级那条塞成唯一一条，所以范围跟着变。

服务端那一半本次**未改**（`server/match/player/round.js` 的 `battleInput` 与 `server/sim/simdata.js getChess`
早就是这条口径），规则正文见 [design/match.md](../design/match.md) 的【特限恢复】④，战斗侧测试见
`test/match/module-level3.test.js`。

### 43.6 实测

真数据（`data/chess.json` + `data/moduleLevels.json`），号角普通形态 `chess_char_5_08_a`（`goldenId` =
`chess_char_5_08_b`）：精锐模组表三档 —— 默认 `uniequip_002_horn`「典范之人」FOR-X、`uniequip_003_horn`「旧日新装」
FOR-Y、`uniequip_004_horn`「号角特限证章」ISW-A；3 级 attr 分别是默认 `{atk 100, def 70}`、ISW `{maxHp 230, atk 85}`。

| 情形 | `chessLoadout` 的 `module` | 记录 `module.level` | stats |
|---|---|---|---|
| 没有【特限恢复】 | `null` | 0 | atk 806 / maxHp 2200（与改动前一致） |
| 有卡、**没选过** | 「典范之人」FOR-X，`isDefault: true` | **3** | atk **906** / maxHp 2200 |
| 有卡、选 ISW 特限模组 | 「号角特限证章」ISW-A，`isDefault: false` | **3** | atk **891** / maxHp **2430** |
| 有卡、选「不装备」 | `{ id: 'none', none: true }` | 0 | atk 806（3 级一个都不套） |

第二行就是这次要的那一格：**没选过也有模组区块**，画的是默认模组的 3 级数据。

### 43.8 明确没做的

- **干员调配的存储没有改**：条目仍是「不等于默认才留」，本次只在**读**的一侧补齐（`normalFormModuleOf` 回落
  默认模组）。改存储会动 `room.loadout` 的协议形状与全部既有存档，不在这一刀里。
- **服务端没有改**：`battleInput` 与 `getChess` 早就是这条口径，本次只把客户端对齐过去。
- **补位干员仍不适用**：它打的是 `data/backups.json` 里另一名干员的身体与模组（§6【特限恢复】④ 末句，
  `[ASSUMED]` 不变）。
- **浏览器实测**：沙箱里起不了浏览器（`spawn EPERM`），商店卡徽标、详情卡范围、落位轮盘、召唤物 ownerRange
  这四处**数值**已由上表与既有测试钉住，**观感**（换模组那一行在窄屏的排版、徽标刷新时机）还要在有浏览器的机器上走一遍。
