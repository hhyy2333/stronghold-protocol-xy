## 转换方式（不是手绘，也不是逆向 moc3 内部结构）

1. 用 **Cubism Core（官方 SDK，5.1.0）在 Node 里离线加载 moc3**，读 269 个 drawable 的顶点/UV/遮罩/不透明度。
2. 自写**软件光栅器**（三角形仿射贴图 + 双线性采样 + 预乘 alpha + 遮罩缓冲）把模型逐帧渲染成 RGBA；
   - 关键点：Cubism 的 UV 的 V 轴与图片行序相反，采样时必须 `v' = 1 - v`，否则整只模型会打散。
3. 用参数驱动出 8 帧待机循环（呼吸 + 头部微摆 + 每 3.2 s 眨眼 + **尾巴摆动**，见下面「尾巴」一节），
   另渲染 3 张情绪帧（闭眼/惊讶/开心）。
4. 所有帧统一裁切到同一包围盒并缩放到 480 宽（现为 480×436），交给 **Spine 3.8.75 的 Texture Packer** 打成 3 页图集。
5. 生成 Spine 3.8 JSON：一个 slot + 11 个 region 附件 + attachment 时间轴（定格动画），
   动画 `Idle`（1 s / 8 帧循环）、`Start`、`Attack`、`Skill`、`Die`；再用 `Spine.com` 导出**二进制 .skel**。
6. 接进工坊包：`pack.json` 的 `art.chars.char_ws_ds_whale.spine.front`，棋子记录 `assets.spine` 指向同一个 id。

## 已知取舍

- 这是**定格动画**（逐帧图集），不是可再绑定的骨骼：改动作要重烘帧，不能在 Spine 里单独转动某根骨头。
- **没模拟 Live2D 的物理（CubismPhysics）**：尾巴是直接驱动它的 5 段旋转参数做出来的摆动（见下），
  头发（`ParamHairFront*`、呆毛、蝴蝶结）仍然是「跟着头一起转」的刚体，帧间靠轻微头部旋转制造动感。
  要连头发一起摆，得把 `render2.mjs` 里 physics 的设置挨条驱动（或真写一遍 Cubism 物理积分）。
- 眨眼是 8 帧里固定一帧，长期看会比 Live2D 生硬。
## 尾巴与头发为什么会动（2026-10-24）

模型的待机是**逐帧定格动画**，所以「哪一帧」就等于「什么姿势」—— 尾巴/头发不动不是引擎的问题，是**烘帧时没让它们动**：

- 这套 Live2D 里它们由 **CubismPhysics** 驱动（`c_0120.physics3.json`）：尾巴是 `PhysicsSetting13 = B_tail`（输入 `ParamBreath`），
  头发是 `呆毛1 / 呆毛2 / 后发_4段` 那几条（输入 `ParamAngle*`）。
- 而 **Cubism Core 只负责「参数 → 顶点」，它不含物理**（物理在上层框架里）。原来的 `render2.mjs` 只驱动了
  那些**输入**参数，物理的**输出**参数一直停在默认值 0 ⇒ 尾巴、头发在每一帧里都是同一个姿势。

做法：把物理的输出参数**直接驱动**成一组有相位差的波（`render2.mjs` 的 `TAIL_*` 与 `HAIR` 表）。

### 尾巴

5 段 `Param_Angle_Rotation_1..5_B_tail3`（每段 ±45°）：幅度逐段变大 3/4/5/6/7°，每段滞后 0.10 个周期 ——
像一条被甩动的链子，不是整体刚性旋转。

### 头发

先把每个候选参数**拉到 ±0.6 各渲一帧、比整帧差异**（`render2.mjs` 的 `PROBE` 模式），确认哪几缕真的能动；
结果很干脆：**大部分头发参数是死通道**（`hair_d` 8/9/10、`后发_4段` 17/18、蝴蝶结 19–23、`呆毛L` 24，±0.6 整帧零差异），
真正活着的是这 12 个：

| 参数 | 动的是 | 幅度 | 周期 | 相位滞后 |
|---|---|---|---|---|
| `ParamHairFront11` | 呆毛 | 0.34 | 1 个 / 循环 | 0 |
| `ParamHairFront13` | 呆毛R | 0.24 | 1 个 / 循环 | 0.12 |
| `ParamHairFront14/15/16` | 后发_4段（1/2/3 段） | 0.14 / 0.22 / 0.30 | 1 个 / 循环 | 0.10 / 0.22 / 0.34 |
| `ParamHairFront5/6/7` | 侧发 hair_f_m | 0.08 / 0.10 / 0.12 | 1 个 / 循环 | 0.16 / 0.26 / 0.36 |
| `ParamHairFront2/3/4/191` | 前侧发 hair_f_lr1 | 0.08 / 0.10 / 0.08 / 0.06 | 1 个 / 循环 | 0.20 / 0.30 / 0.40 / 0.50 |

两条规矩：

1. **游戏里的待机只有 8 帧 / 1 秒**，所以超过 1 Hz 的摆动只能采样到 4 帧一个周期 —— 看着像闪。呆毛一开始按
   2 次/循环（= 2 Hz）做，肉眼看就是抖；现在统一成 **1 秒摆一次**，靠段间相位差做「先动根、再甩尖」的鞭子感。
2. **侧发/前发幅度压小**（0.06–0.12）：那几缕覆盖在脸上，甩大了会盖住眼睛。

### 三个连带改动

1. **无缝循环**：一个整周期正好落在 4 s 的烘焙区间里 ⇒ 8 帧 × 0.125 s 的 1 s 循环首尾相接。
2. **画布要留余量**：变换原来按「默认姿势」的包围盒 + 6 px 边距算，而尾巴摆动会甩出默认剪影 —— 实测尾巴尖会顶到
   画布边缘被切掉。现在边距 6 → **60**，裁切（按所有帧的并集包围盒）仍然正常。
3. **帧裁切是并集**：11 帧共用同一个裁切框，所以摆动的幅度会稍微扩大裁切框（480×449 → 480×436，人物在画面里
   小约 2%），这是正常的，引擎按「底边贴地、水平居中」摆她，不会错位。

实测（8 帧，480 px 宽）：

```
尾巴尖（最右一列）：476 → 471 → 461 → 450 → 444 → 448 → 460 → 472 →（回到 476）
右半页差异：0 / 18.9 / 34.2 / 44.3 / 46.5 / 44.7 / 34.7 / 19.1        ← 一个正弦周期
与第 0 帧的差异像素数：头部 0 → 17568 → 0   右侧长发 0 → 10496 → 0   背部 0 → 10984 → 0
```

### 两处与设计稿的偏差（引擎能力所限）

1. **「数值增益效果提升至 1.5 倍」**没有通用实现点：引擎的 buff 是逐条加算/乘算，没有「二次结算」钩子。
   当前按 **区内友方攻击力、防御力 +50%** 近似（`dsw:s3:amp`）。要真的放大「已获得的所有数值增益」需要改引擎的
   属性汇总层（`server/sim/units.js _recalc` 或 buffs 收集处），加一个「增益放大」系数键——待确认后再做。
2. **「抵抗」**用引擎状态 `resist`（同名取最高、默认减半）实现，0.5s 心跳续到 0.6s，覆盖全部常规控制。

### S3 的脆弱（业主 2026-10-24「给敌人增加 40-50 的脆弱」）

走引擎 catalogue 状态 `fragile`（`server/sim/buffs.js` 的 `fragile: dmgTakenMul = 1 + value`，`valued` ⇒ **同名效果取最高**，
与其它来源的脆弱不叠乘、只取最大值），和史尔特尔 AFT-Y、稀音、魔王 用的是同一条实现：

```js
b.applyStatus(e, 'fragile', { duration: 1.2, source: unit, value: s3Fragile });
```

- **数值在数据里**：S3 的黑板加了 `fragile`，普通 `_a` = **0.4**、精锐 `_b` = **0.5**（即 +40% / +50%），kit 读
  `num(b3.fragile, 0.4)`，所以两档自动跟着记录走。
- **范围 = 深水区**（与她的减速、每秒伤害同一片区域，半径 2/2.5 格），每秒由 zone 脉冲续 1.2 秒 —— 走进来的敌人
  同样吃到，走出区外约 1.2 秒后失效。
- **挂在本次伤害之前**：与官方「脆弱是伤害附加效果，于本次伤害前生效」同一条口径，所以它**连她那口每秒伤害
  自己也一起吃**（这也是实测倍率正好等于 1.4 / 1.5 的原因）。
- 只作用于**物理 / 法术 / 真实**伤害的 `dmgTakenMul`；元素伤害那一档是另一条 `elementalTakenMul`（元素脆弱），
  本技能不涉及。

实测（`test/helpers/battleHarness.js`，30000 血的妖怪当靶，两档各跑一次「开脆弱 / 关脆弱」对照）：

```

精锐 Lv7  fragile {dmgTakenMul: 1.5}   每秒伤害 3990 → 5985   ×1.500 ✓
两档引擎错误都是 0
```

> （基准值比「120% × 最大生命」高，是因为抄来的迷迭香特质给了她 +20%/+40% 生命上限：1480×1.2 = 1776 血 →
> 1776×1.2 = 2131 伤害；精锐同理。）

### 特质：吟游者的真实机制（原来写错了）

原描述「攻击为友方单位恢复生命」是错的——**吟游者不攻击**。官方机制（`server/sim/professions.js` 的 `installBard`）：

> 不攻击，持续恢复范围内所有友军生命（每秒相当于自身攻击力 10% 的生命）

数据侧改成：
- `trait.desc` / `trait.descRaw` = 上面这句（与魔王 `chess_char_5_09_a` 一字不差）；
- `trait.bb["attack@atk_to_hp_recovery_ratio"] = 0.1`（引擎从这里读 `auraRatio`，默认就是 0.1）；
- `dmgType: heal` / `attackKind: none`（不攻击）。

**连带修正**：吟游者的"治疗"是「生命回复速度」光环（`hpRegen` buff），**不是 heal**，所以：
- 天赋 1 的「每层治疗量 +3%」如果只挂 `healingDealtMul`，对她完全没有效果；
- 现在改为挂 **`bardRegen` 钩子** 放大光环值（魔王「微尘」用的也是这个钩子）：
  `ctx.value *= 1 + 0.03 × 层数`。直疗（S2 的 180%、S3 的每秒 50% 最大生命）仍走 `healingDealtMul`。
- S1 的「攻击力 +45%」也因此**真的提升她的治疗量**（光环 = 攻击力 × 10%）。

实测（Lv7，11 层）：攻击 520 → 光环 52/s；开 S1（攻击 +45%）后攻击 754、光环 75.4，再乘 1.33 = **100.28/s**，引擎错误 0。

## 盟约「前文明」（业主 2026-10-24）与实现落点

一条**本包自写的新盟约**（不是官方 23 条里的任何一条）。数据侧是 `bonds.json`（`content: ["bonds"]`），
逻辑侧是 `battle/bonds.mjs`（`pack.json` 的 `server.battle`，DESIGN §28.17 的战斗逻辑载荷：服务端与浏览器
加载**同一份字节**，与官方 `content/bonds/*.js` 里的 `install(battle)` 逐字同形）。引擎与 `data/*.json` 一个字节都没改。

| 设计（业主要求） | 实现 |
|---|---|
| 每消耗 **5** 点部署费用加 1 层（2026-10-25 从 20 改来） | 每 tick 用引擎自己的 DP 公式 `min(dpMax, dp + dpPerSec×dt)` 还原「这一 tick 本该有多少 DP」，与实际值的差额即**真的被消耗掉**的部署费用，攒够 `layer_per_dp`（=5）给本盟约 +1 层 |
| 每叠加 10 层所有盟约加 2 层 | 层数每跨过 `cascade_every`（=10）的倍数，对本玩家**所有已激活盟约**（含前文明自己）各 `cascade_add`（=2）层 |
| 首次到达 50 层时大肥鱼攻击范围 +1 | 层数首次 ≥ `range_at`（=50）：给她挂 `persist` 的 `rangeExtend: +1` buff（阵亡不掉、再部署后仍在），并重建一次攻击范围 |
| 首次到达 150 层时获得 20 层远见 | 层数首次 ≥ `foresight_at`（=150）：给【远见】加 `foresight_add`（=20）层（`battle.addLayers('visiShip', 20)`），随战后结算落进玩家层数 |

这几个数字全部在 `bonds.json` 的 `bb` 里（`layer_per_dp` / `cascade_every` / `cascade_add` / `range_at` /
`range_extend` / `foresight_at` / `foresight_add`），改数据即生效，不用动脚本。

### 三条实现判断（业主没点名，按最贴近原文的方式定的）

1. **「消耗部署费用」= 任何净消耗**，不只是再部署付的钱。引擎里 DP 有三处会变少：手动的 `redeploy()`、
   自动再部署（`_checkRedeploys` 倒计时走完自动回来）、内容自己的 `addDp(负数)`（她自己天赋「吃白饭」每秒 −1 就是这一处）。
   看 `deploy` 事件会数错（免费再部署也算一次），所以走账本差额：[ASSUMED] 天赋的 DP 扣减也算「消耗」——
   这与她天赋文本「每秒消耗 1 点部署费用」是同一套说法。
2. **「所有盟约」含前文明自己**，且只发给**已激活**的盟约：所以每 10 层实际是「自己 +2、其它激活盟约 +2」，
   到 50 / 150 的速度比只算 DP 快约 20%。未激活的盟约不叠（层数整局保留，等它激活后再吃后续档位）。
3. **一次性阈值是从「整局保留的层数」推出来的**，不额外存状态：开局读一次当前层数（上一场结算过的），
   算出下一个 10 层档位；只有「跨过」的那一刻触发。于是同一局的第 2、3 场战斗不会重复发 50 / 150 的奖励，
   而 149 层结束的那一场之后，下一场照样会补上 150 层那一档。

另外：`weight: 0`（**本局禁用的随机抽签永远抽不到它**）——一条自写盟约被随机禁用等于这套内容消失；
`thresholds: [1]`（大肥鱼自己一人在场即激活），成员只写她两条记录。

### 实测（`test/helpers/battleHarness.js` + 真引擎装载器 `loadBattleInstallers`）

## S3 的范围特效（2026-10-24）

战斗里**引擎本来不画干员的攻击范围**（`public/js/render/` 下没有任何 `rangeKeys` 的读者），而 S3 把范围整片换成
25 格的「钙质化」菱形 —— 玩家看不出边界在哪。这一版给它加了一层地面高亮。

**kit 侧**（`kits/chess_ws_ds_whale_*.js`）：S3 的 `onStart` 发一条

```js
battle.fx('field', { x: unit.x, y: unit.y, id: unit.id, dur: d3, tiles });
```

`tiles` 是 `absoluteRangeKeys(CALC_GRID, unit.tileR, unit.tileC, unit.dir, 0)` 算出的 25 个格子键，按
`@sim/constants.js` 的 `COLS` 拆成 `[r, c]`；`dur` = 技能时长，所以高亮跟着技能一起结束。用 `absoluteRangeKeys`
自己算、不读 `unit.rangeKeys`，是因为后者在 `onStart` 时刻是否已刷新取决于 hook 顺序。

**客户端侧**：这是引擎新增的一个 fx 类型（`public/js/render/fx/`，4 个文件各一处，跟官方内容无关，
没装这个包的局一点变化都没有）：

| 文件 | 改动 |
|---|---|
| `kinds.js` | `field: { a: 'field', c: 0x9fe6ff }`（薄荷青）+ 注释 |
| `simfx.js` | `case 'field': this.tileField(tilesAround(at.x, at.y, r, ex.tiles), col, dur)` —— `tilesAround` 对 `[[r,c]]` 是直接透传（≤80 格） |
| `zones.js` | 新增 `tileField(tiles, tint, dur)`：与一次性的 `tileFlash` **共用 `tileGfx`**（同一趟 `clear()`，先画持续高亮再画闪光，否则两层互相擦掉），逐格填充 + 边框，慢脉动，最后 10% 淡出 |
| `system.js` | `tileFields` 列表（构造 + `clear()`）+ 在 `FX_METHOD_ORDER` 登记 `tileField`（那张表要求每个方法恰好被一个 part 定义一次，漏登记加载时就抛错） |

**为什么用格子而不是圆**：`zone` 是圆，盖不住菱形范围（对角线那几格会露在圈外）。`field` 才是「判定格就是画面」。

实测（真战斗里读事件流）：S3 起手发出 **1 条 `field`，`tiles` 25 格**，行 8–14 / 列 2–8（她站 11,5 的半径 3 菱形），
`dur` 25；深水区的 `zone` 照旧发；引擎错误 0。两个技能档位（普通 / 精锐）各跑一遍结果一致。

> 提醒：那 4 个客户端文件是**引擎代码**（`git status` 里是 `M`，不是包内文件）。要回滚就
> `git checkout -- public/js/render/fx`；包本身在没这层特效时依然完整可用（kit 只是发一条没人认识的 fx 事件时
> 会走客户端的兜底 sparkle，不会报错）。

## S1 / S2 改成「自动回复 + 自动触发」（2026-10-24）

业主的新规格：

```
S1 数据流溢出     自动回复·自动触发    初始 10 · 消耗 20 · 持续 20s
```

**数据侧**（`chess.json` 两条记录各三处）：

| 字段 | 改成 | 为什么 |
|---|---|---|
| `skillType` | `AUTO` | 卡面「自动触发」；引擎里 `manual=false` ⇒ 不需要操作冷却 |
| `trigger.rule` | `SP_FULL` | 引擎的「技力满了就放」规则（`skills.js` 的 `TICK_RULES`）；只写 `AUTO` 而不改 rule 的话，AUTO 仍然走 DEFAULT 的「范围内有敌人」条件，站桩的吟游者会一直不放 |
| `spCost` / `initSp` / `duration` | S1 20 / 10 / 20 · S2 6 / 5 / — | 就是规格里的数；`spType` 一直是 `INCREASE_WITH_TIME`（自动回复） |

`bb` 一个键都没新增：数值照旧分两档（普通 Lv4 / 精锐 Lv7），S1 的「+5 层」写在 kit 里（`num(b1.stacks, 5)` 的默认值）。

> 为什么 5 层不写进数据：共享校验器只对**默认技能**（`skill` 那条）跑「通用黑板白名单」，`bb.stacks` 会被报一条
> `BB_UNKNOWN_KEY`（它说的是「没有手写 kit 时这条键什么都不做」——本包有手写 kit，属于误报）。为了让包里保持
> 0 warning，5 放在 kit 的默认值里；哪天数据里真写了 `stacks`，那段代码照样读得到。

**kit 侧**（`kits/chess_ws_ds_whale_*.js`）：

- S1 的 `onStart` 先 `addStacks(unit, 5)` + `syncSamples`，再给范围内友方挂 20 秒的 `aspd+35`；
  `duration` 从记录的 20 秒读（原来写死 15 的默认值也一起改了）。
- S2 的 `onStart` 改成：`addStacks(unit, 1)`（先「获得 1 层」）→ 读总数 `n` → 清零 → `atkPct += n × 每层`；
  治疗与 `giveSp(1)` **各只做一次**（旧实现是「每层各治疗一次 + 各回 1 技力」，与新文案不符）。

实测（真战斗）：

```

    持续 20.0s，友方 aspd buff = 25/35（两档）持续 20s，攻击力 504→680（×1.35）/ 728→1056（×1.45）✓
S2  自动触发 0.87s / 0.83s 一次（初始 5、消耗 6），每 6 秒左右再触发一次 ✓
    攒 7 层 → 触发后消耗 8 层：atkPct = 1.60（Lv4 = 8 × 20%）/ 2.40（Lv7 = 8 × 30%）✓，样本归零 ✓
    治疗 1 次 1966 = 1310 × 150%（Lv4）/ 4455 = 2475 × 180%（Lv7）✓；回技力 1 次 `[1, 'skill']` ✓
两档引擎错误 0
```

> 两个连带现象，都是既有设计的自然结果，不是 bug：
> 1. **S1 实际会 +6 层**：S1 自己给 5 层，而她的 T1「范围内友方释放技能时 +1 层」把**她自己这次施法**也算进去
>    （`a !== unit` 那个判断只用在范围检查上），所以触发瞬间是 6 层。
> 2. **S2 每次施法给自己再 +1 层**（T1 同一条），下一次施法就会把它一起消耗掉 —— 于是 6 点技力 ≈ 每 6 秒一次、
>    每次至少 +40%（Lv4）/ +60%（Lv7）攻击力。这是规格里「获得一层再立刻清空」× T1 的直接叠加，数值上偏强；
>    要让 T1 不含她自己，改 kit 里那一条判断即可。

业主：「放 3 技能时播放 `LetMeGo.m4a`」，随后补充「**技能停止音乐停止**」。

### 为什么不是「语音」

第一版把这首曲子挂在她装备 S3 的**台词槽**上（`pack.json.voices[...].skill3`，引擎原生的干员语音通道）。
能响，但**停不下来**：语音通道（`public/js/audio.js`）没有对外的停止入口，只有「更高优先级的台词抢占」才会切掉正在播的
一句 —— 而这首 2 分 05 秒的曲子远长于 S3 的 25 秒，技能结束后会一直放下去。所以这一版改成**技能自己的一段音频**。

### 现在的做法：kit 发事件，客户端 fx 放

| 侧 | 做法 |
|---|---|
| kit（`kits/chess_ws_ds_whale_*.js`） | S3 的 `onStart`：`battle.fx('music', { url: S3_MUSIC, dur: d3 })`；`onEnd`：`battle.fx('musicStop', {})` |
| `S3_MUSIC` | `/workshop-assets/ds-whale/voice/LetMeGo.m4a`（包内素材 URL 规则 = `/workshop-assets/<包 id>/<路径>`，改包 id 时要同步改） |
| 客户端 `render/fx/` | 新增两个 **fx 类型**：`kinds.js` 的 `music` / `musicStop`；`simfx.js` 的两个 case 分别调 `this.music(url, dur)` / `this.stopMusic()`；`zones.js` 里用单独的 `HTMLAudioElement` 播（音量 0.6），`_updateMusic(dt)` 在**每帧**里倒计时、末段 0.35 秒淡出；`system.js` 里初始化 + `clear()` 时停（换战场不留上一场的歌）+ 把四个方法名登记进 `FX_METHOD_ORDER` |

用 fx 系统承载而不是新建一条音频通道：它本来就有每帧 `update` 和 `clear`，**「技能停了声音也停」「换场不残留」
这两个要求在那里是天然成立的**；而且 kit 只发一条事件，服务端不必知道音频怎么放。

### 什么时候会停

- **技能自然结束**（25 秒到）→ `end('time')` → `onEnd` → `musicStop`；
- **技能被打断 / 单位阵亡 / 撤退** → 引擎都会走 `skill.end(...)` → 同样发 `musicStop`；
- **换战场 / 战斗重置** → 客户端 `fx.clear()` → `stopMusic()`；
- 兜底：`dur` 到时也会淡出（万一事件丢了）。

实测（真战斗里读 `battle.fx` 事件流）：

```
S3 起手  → field, music /workshop-assets/ds-whale/voice/LetMeGo.m4a, zone
技能结束 → musicStop            （手动 end 与自然结束都发；引擎错误 0）
包校验 0 error / 0 warning（`voices` 已从 pack.json 移除，音频文件仍在 assets/voice/）
```

### 两个取舍

1. **音量不走游戏的「语音」滑块**：这段音频是包自己的 `Audio`，音量固定 0.6，受系统/标签页音量控制；「语音」滑块只
   影响官方台词。想让玩家能单独调，要么改引擎给 fx 加一个音量参数（可以加），要么接受现在这个固定值。
2. **自动播放策略**：浏览器要求先有用户交互才允许 `play()`；战斗中玩家已经点过地图/技能，所以正常；被拒绝时静默失败，
   不会报错。

### 顺带留下的一处引擎修正

第一版用语音通道时，校验器把这条台词报成 `VOICE_UNKNOWN_OPERATOR`（「这些台词永远播不了」）—— 因为台词键按
`u.spine`（= 记录的 `assets.spine`）查，而本包的 spine id 是自造的 `char_ws_ds_whale`，既不是官方 id 也不是 chess id。
已给 `shared/workshopValidate.mjs` 的豁免加上「**本包 `art.chars` 声明的 id**」这一条（`docs/WORKSHOP.md` 的语音规则表
也补了一行「台词的键 = `u.spine`」），这条修正对以后所有自带外观的包都成立。

## T2 吃白饭的庇护改成 20% + 2x%（2026-10-25）

业主的规格：

```
大肥鱼在场时，每秒消耗 1 点部署费用。为攻击范围内的友方单位提供 20 + 2x% 的庇护（x = 「数据样本」层数）和抵抗。
```

改动很小，因为公式本来就是「基线 + 每层」的形状：

| 位置 | 改前 | 改后 |
|---|---|---|
| `talents[1].bb` | `protect_base: 0.08/0.1`、`protect_per_stack: 0.01`、`protect_cap: 0.25/0.3` | `protect_base: 0.2`、`protect_per_stack: 0.02`（**删掉 cap**） |
| kit | `Math.min(PROTECT_CAP, base + per × 层数)`，cap 默认 0.3 | cap 默认改成 **1 = 不封顶**；数据里不写 `protect_cap` 就不截断 |
| 两档 | 普通 8%/层+1%/上限25%，精锐 10%/层+1%/上限30% | **两档统一** 20% + 2%/层（业主这次只给了一套数） |
| 卡面文案 | 「8%+数据样本层数…上限25%」 | 「获得20%庇护，数据样本每层再+2%（每层独立生效，庇护与抵抗同时提供）」 |

- 抵抗沿用引擎的 `resist` 状态（`applyStatus(..., 'resist', { value: 0.5 })`，同名取最高、减半），这次没改数值。
- 庇护走 `applyStrongest` 的 `protect` 效果（`physTakenMul / artsTakenMul = 1 − v`）——「同名取最高」，所以**和其它庇护
  来源不叠乘，只取最大那一份**；层数上限 20 ⇒ 最高 60%。
- DP 扣减没动：仍然 `battle.every(1, … addDp(-1))`（`addDp` 钳在 0）。

实测（真战斗）：

```
层数  0 → 受伤 ×0.80（20%）     层数  5 → 受伤 ×0.70（30%）     层数 20 → 受伤 ×0.40（60%）   抵抗：都有
把 DP 自然回复关掉后 3 秒 DP 10.00 → 7.00（每秒 −1）                                    引擎错误 0
```

> 层数上限 20（T1 的 `stack_max`）⇒ 这套庇护的实际上限是 **60%**；如果哪天把样本上限调高，庇护会跟着继续涨。

## S1 / S2 / S3 的第二轮改动（2026-10-25）

业主给了三条新规格（其中 S3 那句「把鼓舞效果搞到 3 技能上」是按魔王的 S3 文案来的：`攻击范围内所有其它友方单位
获得相当于魔王 65% 最大生命值的鼓舞效果`）：

### S3：去掉「+攻击力/防御力」，改成本体的鼓舞

| | 改前 | 改后 |
|---|---|---|
| 区内友方 | `atkPct/defPct +40%（Lv7 +50%）`（当年「1.5 倍」的近似） | **删掉**（`KEY_AMP` / `dsw:s3:amp` 整个移除） |
| 鼓舞 | 无 | 每 tick 给**攻击范围内的其它友方**挂 `inspire:hp`：`hpFlat = 她最大生命 × 65%`，0.6 s 续一次 |

鼓舞的实现（复刻魔王的 `inspire()`，但只开放了 `@kit/tier1.js` 能拿到的东西）：
- 用**同一个 buff key** `inspire:hp` —— 与魔王的鼓舞「同类取最高」，两个吟游者同时在场时只吃最大的那一份，不叠乘；
- 引擎的 `maxHp = (base + hpFlat) × (1 + hpPct) × hpMul`，即 `hpFlat` **会被生命% 放大**。官方的鼓舞是「附加在
  百分比乘算之后」，所以要除以目标的生命倍率 `f = s.maxHp / base.maxHp`；
- **换算时必须先摘掉自己上一轮的鼓舞再量** `f` —— 否则量到的是「含鼓舞的 maxHp」，每刷一次系数大一点、数值越滚越小
  （第一版实测：她 1776 血 → 应给 1154，实际只给了 773，就是这个自反馈 bug）；
- 吟游者自身 `mem.noInspire`（官方「自身不受鼓舞影响」），她不吃别人的鼓舞，自己也不吃自己的（只发给 `a !== unit`）。

### S1：特性提高到 35%

`profile.auraRatio` 是吟游者光环的比例（每秒回血 = 攻击力 × 比例）。S1 期间提到 `0.35`，`onEnd` 恢复。
与 S2 的永久加成的关系是「取较高者」：`最大生命倍率 = S1 期间 0.35，否则 base + S2 累计`。

### S2：每层特性 +2%、治疗/护盾 = 她最大生命 80%

- 层数不再加攻击力（`KEY_S2_ATK` 已删），改成 `mem.dswAuraBonus += 2% × 层数`，然后重算 `auraRatio`（本场战斗永久）；
- 治疗：`battle.heal(unit, target, unit.s.maxHp × 0.8)`（是**她**的最大生命，不是目标的）；
- 护盾：`battle.addBuff(target, { shield: unit.s.maxHp × 0.8, duration: 12 })`（新建一个 12 秒的护盾 buff，可叠加刷新）；
- 回技力仍是 `giveSp(target, 1)` **一次**。

### 实测（真战斗）

```
S1   auraRatio 0.10 → 技能中 0.35 → 结束 0.10
S2   9 层 + 自身 1 层 = 10 层 ⇒ auraRatio 0.10 → 0.30；治疗 1421 = maxHp 1776 × 80%；护盾 1421；回技力 1 次
S3   友方 鼓舞 val = 她 maxHp×65% = 1154；实测友方 maxHp 1569 → 2723（+1154）；旧的 dsw:s3:amp 已消失
     她自己的 auraRatio 不受影响；三档引擎错误 0；包校验 0 error / 0 warning
```

> 两处口径说明：
> 1. S2 的「80% 最大生命值」按**大肥鱼自己的最大生命**算（与魔王的「相当于魔王 65% 最大生命值」同一条读法）；护盾取了
>    同样的 80%（业主只说了「治疗和护盾」，没给护盾数值）。
> 2. 鼓舞只发给「其它友方」（`a !== unit`），不含她自己 —— 与魔王的文案逐字一致。
