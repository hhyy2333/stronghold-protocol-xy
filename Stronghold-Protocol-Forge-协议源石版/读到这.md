## 监控后台（/admin/）

**双击 `启动游戏-管理后台.bat`** 即可。口令存在包里的 `admin-secret.local.txt`（首次双击自动生成，
以后重启都用它，浏览器不用重新输）；面板地址会同时打印出来，并在游戏页开出来之后自动打开「已登录」的那一页。

> **为什么另开一个 bat**：面板由 `ADMIN_SECRET` 环境变量把关，而**源码里刻意没有默认口令**
> —— 忘了配置的部署不该有一个所有人共用的密码。不设它时 `/api/admin/*` **一律 404**（不是 401），
> 所以一个干净安装**连面板的存在都探不到**。用普通 `启动游戏.bat` 就是这种状态。

### 面板能做什么

| 区块 | 说明 |
|---|---|
| **总览** | 进程 RSS / 堆、CPU%、负载、在线 socket / 会话 / 房间 / 对局 / 真人与 AI 数、各阶段耗时 |
| **房间** | 每个房间一行：房号、房主、模式、难度、人次、**当前对局阶段**、每房间性能消耗；每名真人（与观战者）旁边一颗**「移出」**，任何时刻都能用（对局中等于中途退出，不是封禁） |
| **日志** | 服务器自己的输出（启动、对局、告警）——**实时环形缓冲，上限 300 条** |
| **玩家反馈** | 游戏内「问题反馈」提交的内容，可逐条删除 |
| **全体公告** | 发一条横幅到**每一个在线会话**（大厅与对局中都显示），可撤回 |
| **更新公告** | 编辑玩家进游戏时弹的那份更新说明；服务端没有时用包内置的那份 |
| **封禁 IP** | 封 / 解一个地址或 CIDR，**立刻断开该地址已开的连接** |
| **人数上限** | 服务器并发 socket 上限，**改完即时生效、不用重启**（调低不会踢人） |
| **另一个槽** | 蓝绿部署时探测对端进程是否还在、上面还有多少人 |

### 几条安全设计（不是我加的，是上游刻意如此）

- 口令**只从 `Authorization: Bearer` 头**读 —— 不走查询串（会进访问日志与 `Referer`），不走 Cookie。
- 比较是**定时安全**的（`timingSafeEqual`），猜口令的耗时不会泄漏"猜对了几位"。
- 同一地址**连续 10 次**口令错误就锁 60 秒，且**锁定时回同一个 401**（不告诉攻击者已被限流）。
- **封禁优先于口令**：被封的地址**连管理接口也 404/403** —— 口令不能成为绕过封禁的后门。
- 写操作只有**六个**（公告 / 更新公告 / 封禁 / 人数上限 / 删反馈 / 踢出房间，`POST /api/admin/rooms/kick`），
  每一个都够窄：**踢出房间**是唯一碰到房间的那一个，而它做的仍然只是「一次正常离开」（与本人在房间里点离开
  逐字节相同：座位释放、`room.closed {reason:'kicked'}`、房主走了顺延房主），**不封禁**，人可以用房间号加回来。

### 命令行自检

## ⚠️ 要知道的四件事

**1. 这不是工坊包，是引擎级改动。**
Forge 的工坊包只能填引擎**已经挖好的格子**（15 张内容表、已具名的钩子）；
协议源石需要**新的阶段、新的协议消息、新的注册表命名空间** —— 那三样包做不到，必须改引擎。

**2. Forge 一旦升级，需要重新对一遍。**
重点是**七个缺口**，其中 `app/server/viewsDelta.js` 的 `SCALAR_KEYS` 是
**唯一一个不补就报错**的（每一帧降级成全量帧）；其余六个不补是「功能静默不生效」。

**3. 测试场没有搬。**
「测试场」（面板里点一下直接发卡）是**另一项功能**，不是协议源石的一部分，按决定不搬。

**4. 客户端界面修过一轮，但仍未做浏览器实机验证。**
第一次交付时界面报 `normalizeHex is not defined`，我漏了四处，现已全部补上并通过静态检查（见文末「修订记录」）。
**但包里没有 Chrome / 驱动，浏览器实机验证仍然没做** —— 静态检查能保证不再有同类错误，保不了视觉效果。

### 2026-10-17 · 悬赏第 7 张卡选不了 + boss 休整期地图弹回道中（**均未上线**）

#### 1. 「超过 6 个人时，前 6 个以外的悬赏选不了，说无效的请求」

根因是**两层各写了一份卡数**：服务端 2026-10-16 已改成按人数铺牌（`generateDraft`: `max(6, 存活人数)`），
7 人房的第 7 张卡 `idx = 6`；但协议层 `shared/protocol.js` 的 `g.choice` 还写着 `isInt(idx, 0, 5)`。
于是第 7 张卡在**协议校验**就被判 `ERR.BAD_MSG`（界面「无效的请求」），根本到不了 `pickCard` 的业务校验。

> 之前那条「按人数铺牌」的测试没抓到，是因为它直接调 `Match.handle`，**绕过了协议校验**。

改法：`DRAFT_CARDS_MAX` 收到 `shared/constants.js`（原来只长在 `server/match/choices.js`），协议层、服务端、
客户端三处读同一个数。回归：新增 `test/match/draft-many-players.test.js`（协议上界 0…19 全合法、20/负数仍拒；
7 人房实战每人一张且真的取到 `idx ≥ 6`）；单变量对照「改回 0..5 → 2 条全红，恢复 → 2/2 绿」。

#### 2. 「boss 战前休整期点干员，有概率把地图从 boss 地图变成道中，直到战斗开始才恢复」（>4 人）

**先说清楚一件事**：boss 战前休整期和道中是**同一张地图、同一个 `stageId`**，差别只在取景 ——
`bossPrep` 把战场行 2–5 当棋盘行 9–12 画（`render/prepfield.js bossPrepField`），普通 prep 是恒等映射。
所以「地图变了」= 棋盘取景变换（`prepXf`）退回了恒等，棋子也就站回道中的位置。

渲染器里这两半必须**同源**：`setCamera(kind)` 决定 `prepXf`（`render/app.js` setCamera → setPrepField），
`kind` 为 `prep` ⇒ 恒等、`bossPrep` ⇒ 战场半场，其它 kind **不改**。而客户端只在「相机键（kind:side）」变化时
才重新请求镜头（`screens/game.js` 的 `prepCamSeen`），并且一旦 `viewModeRef` 记成 `'prep'` 就再也不请求 ——
于是任何一条把渲染器留在另一套取景的路径都会**卡到开战**。

**这一轮修的是「不会卡死」，不是「找到触发点」**（坦白）：

* 新增纯函数 `ui/gameLogic/camera.js prepFieldMismatch(prepField, cam)`：拿渲染器的**实际状态**
  （`view.prepField()` → `{kind:'board'|'bossPrep', side}`）与该帧应有的 prep 相机比对；
* 休整期分支里不一致就 `setCam` 重新请求一次；拖拽中 / 方向轮开着时延后（落点与轮子画在当前相机的格子上，
  与 `foldCamera` 的 busy 纪律同一条），并把 `drag`/`facing` 加进 effect 依赖，松手后必然重跑；
* 所以：真出现不一致时会在**下一帧自愈**，不再「一直到战斗开始」。

已排除的（都有证据，不是猜）：boss 与道中共用同一个 `stageId`；点击本身不触发任何相机调用
（`pieceClick` 只做 `setSel`/`setDetail` + `g.unitStats` 预览，服务端预览战斗不广播 `m.field`）；
4 人与 6 人的 boss 回合服务端下发完全一致（`bossPairs` 覆盖每个人，`prepCamera` 对 6 人逐个返回 `bossPrep`）。

回归：新增 `test/ui/prep-camera-reassert.test.js` 6 条（两个方向的不一致、半场 L/R、一致时不动镜头、
渲染器不报告时不乱动、接线正则）；`playtest2` 24/0、`playtest5-deploy` 13/0、`feedback5-boss-prep-scout` 2/0、
`finalAssault` 12/0。既有的红（`issue5-fold-camera` 4 条、`gameLogic` 3 条）在改动前后**同数**，与本轮无关。

### 2026-10-17 · 素材 CDN 审计 —— 线上跑的是 Forge 这套（nginx 302），并修掉三处真缺陷

业主问「看看这个版本的 CDN」。查完确认：**这一版与 0.3.0 的 CDN 是完全两套机制**，而且**线上正在用的就是这一套**。

#### 两套机制的根本差别

|  | 0.3.0（`Stronghold-Protocol-repo`） | **Forge 协议源石版（本包）** |
|---|---|---|
| 在哪改 | `server/http/cdn.js`，**响应层改写美术清单** | **nginx 302**，应用**一行没改** |
| 读 CDN 键表 | 读 `/cdn/v1/index.json` + `hosted-index.json` | **根本不读**（所以 CDN 同步抖动伤不到它） |
| 开关 | `SP_ASSET_CDN` 环境变量 | **与变量无关**，装了 nginx 规则就一直在 |
| 兜底 | 键表里有才改写，缺哪条哪条走本机（自动） | `$sp_keep_local` 路径白名单（**手写**，要维护） |

**线上实测**（2026-10-17 00:5x）：`/opt/Stronghold-Protocol-{a,b}/server/http/cdn.js` **两个槽都不存在**，
两个槽 `/healthz` 都报 `app: 0.18.6` —— 所以线上跑的**就是本包**，读键表那条路**已经退役**，
**10-15 那次「键表被写坏 → 素材全回落源站」的事故在这个版本上不会再发生**。

`/etc/stronghold.env` 里那个 `SP_ASSET_CDN=https://speedcdn.jiangjiangze.icu` **两个槽的代码里 0 处引用**
（`grep -rl` 实测），是 0.3.0 时代留下的、**不生效**的一行。

#### 关键设计：302 前必须**抹掉** `~<hash>`

Forge 的清单是内容寻址的 `/assets/~398f32e2ff78d9e6/char/avatar/x.png`，而 CDN 上是普通路径
`/assets/char/avatar/x.png`。所以 302 不能原样转发，必须是：

```nginx
location ~ "^/assets/~[0-9a-f]{16}/(?<sp_rest>.+)$" {
    if ($sp_keep_local = 0) { return 302 $sp_cdn_base/assets/$sp_rest; }   # ← 用 $sp_rest，不是 $request_uri
    ...
}
```

线上跑的正是这一条。配置注释里记着 10-16 那次「全站素材变白」就是没抹导致的。

#### 实测：这条路今天是通的

```
抽样 120 条（从 17723 条真实路径里）  → CDN 120/120 = 206，0 条失败
分目录 avatar/portrait/spine/skill/item/voice → 各 3/3 全中
spine 跨域（客户端要 XHR）            → 200 + access-control-allow-origin: * + vary: Origin
302 跳转耗时                          → 0.4–1.3 ms（纯 nginx return，不碰后端）
今日 /assets 请求 96,346 条           → 95,797 条 302 到 CDN（99.4%），本机只发 549 条
```

#### 修掉的三处真缺陷

**① `/fonts/` 的 302 漏抹 `~hash` → 带 hash 的字体路径 404（线上已修）**

`/assets/` 那条抹 hash，`/fonts/` 那条却用了 `$request_uri`：

```
/fonts/~af82f8e4bffb870d/fonts.css → 302 → CDN/…/fonts.css → 404
                                          抹掉 hash 再取    → 200（1046 字节）
```

**7 个字体全部如此。** 而 nginx 的 `location ^~ /fonts/` 里那个 `^~` 会**压过**正则 location，
所以补丁必须同时**去掉 `^~`** 并加一条抹 hash 的正则。改法（已上线）：

```nginx
location ~ "^/fonts/~[0-9a-f]{16}/(?<sp_rest_f>.+)$" { return 302 $sp_cdn_base/fonts/$sp_rest_f; }
location /fonts/ { return 302 $sp_cdn_base$request_uri; }   # 不能带 ^~，否则上面那条不生效
```

改前/改后实测（7 条）：`404 → 200`；不带 hash 的入口 `/fonts/fonts.css` 仍是 `200`；
`/assets/` 与三类本地豁免**一条没动**。全量日志核对：**带 hash 的 `/fonts/` 请求 25 条全部来自我自己的 curl**，
**真实玩家 0 条**（`index.html` 静态写死 `<link href="/fonts/fonts.css">`）——
所以这是**哑弹**，不是正在流血的伤口；但任何客户端哪天去用清单里那份路径就会中招。

**② `服务器/部署说明.md` §7.3 的示例是错的（照它装会复现事故）**

文档**开头注释专门警告**「不抹 hash 会全站变白」，但 §7.3 给的示例代码恰恰**就是没抹的版本**
（`location ^~ /assets/ { … $request_uri }`）。已整段换成与线上一致的正确写法，
并把 `/fonts/` 那条、`^~` 的坑、四条自测方法一起补上。

**③ `sp-forge-check.sh` 第 6、7 节都是坏的（现已全绿）**

- 第 6 节：设了 `SP_ASSET_CDN` 报 `[!!]` —— 但 Forge **不读**这个变量，留着**无害**，
  于是自检**永远不通过**。改成 `[--]` 提醒。

  改成递归找第一个 `/assets/…` 字符串，并且 `curl -L` **跟着 302 取回**（顺带验证 CDN 那一跳）。

### 2026-10-16（晚）· 莱茵护甲把怪的生命值改了 —— 用错了机制（次数盾 ≠ 血量等于次数）

#### 根因：`hitShield` 用了 `setHits`，而它会**覆盖 maxHp**

旧实现（两棵树一字不差，是上游原始写法）：

```js
hitShield(battle, p) {

  battle.on('enemySpawn', ({ enemy }) => {
    if (isHitCount(enemy)) return;
    hitCount(battle, enemy, true, artsOnly);
    setHits(enemy, hits);          // ← 这里

```

`setHits`（`enemies/helpers.js`）的实现是 `e.base.maxHp = h; e.hp = h;` —— 它的注释本来就写着
**`maxHp := hits`**。于是 `hits: 3` 把**所有敌人**（十万血的首领也一样）压成 **3 点血**、血条直接消失。

`hitCount` + `setHits` 是给**器物 / 频次怪**用的**另一种**机制 —— 那 14 个 `tile_*` 单位**本来就是**
"打 N 次才倒"，没有血量可言（`archetypes.js` 的 `times()`：`setHits(e, e.base.maxHp / supplyHpMul)`）。
而卡面写的是「敌人**获得一层**次数盾（可抵挡 3 次攻击）」= **额外**一层，血量不该动。

#### 引擎里本来就有真正的"一层盾"

`ab.hitShield`（`enemies.js onHitIn`）：整段物理/法术伤害被 `cancel`、扣 1 层、破盾放 `shieldBreak`
特效。官方两个使用者：**莱茵生命防卫科高级成员**（`enemy_1249_lysdb_2`，`Shield.max_block_damage_cnt`）
与 **假想敌：再生** 的光环（`times.js kitRegen`，`Aura.max_damage_block_cnt`）—— 卡名「莱茵护甲」
正是前者。Forge 移植时这套机制**完整保留**（`enemies.js:197`），一直可用，只是这张卡没用它。

#### 改法（两棵树同改）

```js
hitShield(battle, p) {
  const hits = Math.max(1, Math.round(pnum(p.hits, 3)));
  battle.on('enemySpawn', ({ enemy }) => {
    if (!enemy || !enemy.alive) return;
    const ab = abOf(battle, enemy);
    ab.hitShield = Math.max(ab.hitShield, hits);   // 额外一层；已有的那层取较大者，不重置
  });
}
```

- `import` 去掉 `hitCount` / `setHits`，加 `abOf`（这两个符号已无人用，只出现在注释里）。
- `p.artsOnly` 分支一并删掉：**roster 里没有任何卡用过它**（grep 0 命中），且 `hitShield` 本来就
  只对 `phys` / `arts` 生效，不需要那个开关。
- `setHits` 的注释补了一条警告：**它会覆盖 maxHp，只该给器物/频次怪用**（防止下一个人再踩）。

#### 3. 根因：`local/scene/` **不在 nginx 的源站直发白名单里**，而 CDN 会抖动

nginx 的 CDN 302 规则（`/etc/nginx/sites-enabled/stronghold`）用 `$sp_keep_local` 决定「本机发」还是
「302 给 CDN」。白名单原来只有三类：

```
"~*[\[\]]"                                            方括号文件名
"~^/assets/~[0-9a-f]{16}/local/hextech/"               协议源石自制素材（CDN 上是 404，必须本机发）
"~^/assets/~[0-9a-f]{16}/local/char/char_9002_yana/"   娅娜（同上）
```

**`local/scene/`（0.2.5 合并时新增的 62 MB 官方场景）不在里面**，于是走 302 → CDN。

**CDN 覆盖实测是完整的**（22 个 scene 主文件逐个测，21 个稳定 200；唯一一次 `000` 重试 3 次全 200
—— 是**瞬时抖动**，不是缺文件）。所以问题不是「CDN 没有」，而是「**CDN 抖那一下没有兜底**」：
场景素材是**一次取不到就整块退化**的那一类，而 CDN 偶发抖动 / 某些网络到 Cloudflare 不稳时，
正好赶上的人就看到图2 —— 这就是业主说的「**部分人**」。

> 中途我两次判断错、各纠正一次：① 先以为 CDN 缺 scene（本机 curl 全 `000`）—— 从**服务器侧**复测才发现
> CDN 上都有，是本机网络到 Cloudflare 不通；② 顺手把 `local/spine/` 也加进白名单，实测 CDN 上
> `local/spine/` **全是 200**，那是多余豁免（白占源站带宽），已撤掉。

#### 改法（线上 nginx，一条规则）

```nginx
map $request_uri $sp_keep_local {
    default 0;
    "~*[\[\]]" 1;
    "~^/assets/~[0-9a-f]{16}/local/hextech/" 1;
    "~^/assets/~[0-9a-f]{16}/local/char/char_9002_yana/" 1;
    "~^/assets/~[0-9a-f]{16}/local/scene/" 1;     # ← 新增：官方 3D 场景源站直发
}
```

备份 `/etc/nginx/backups/stronghold.bak-prescene-20261016-202040`（**注意：备份不能留在
`sites-enabled/`**，那里每个文件都会被加载 —— 我第一版放在同目录，`nginx -t` 直接报
`duplicate upstream`）。

**代价**：`local/scene/` 62 MB/槽 改从源站出。首载按需取（一个 stage 约 2–6.5 MB + 贴图），不是一次性全下。

#### 实测（reload 后，从源站侧）

```

官方 spine/op/…                302 → CDN（不变，CDN 有）
娅娜 local/char/…              200 源站（不变）
```

`nginx -t` 通过、`systemctl reload nginx` 成功。**这只是「抖动兜底」，不是替代 CDN** ——
CDN 能通的人照旧走 CDN，其余素材一条都没动。

### 2026-10-16 · 情报部抑制（`ehex_mosaic`）收窄成「只糊机变」

业主：「改成只有敌人形象和机变看不清」。原来它是**全屏**的一层 `backdrop-filter` 马赛克。

#### 为什么做不到「只糊敌人形象」

**敌人画在 canvas 里**（three.js / Pixi），而 `backdrop-filter` 是 DOM 的东西，只能作用于某一个元素**下方**的整块区域 ——
没有任何办法把它裁剪到「canvas 里的敌人模型」。要糊到敌人，就只能糊整块战场 canvas，那会连自己的干员和地形一起糊，
结果还是「看不清战场」，正是业主要摆脱的效果。所以能精确命中的只有 DOM 侧的浮层。

给了三个方案让业主选（只糊机变 / 糊整个战场 canvas / 全屏但很轻），业主选了 **A：只糊机变**。

#### 改法

| 层 | 改动 |
|---|---|
| `public/js/ui/mosaic.js` | `MosaicOverlay` **不再渲染任何元素**，改成用 `useDocClass` 给 `<html>` 挂 `sp-mosaic` 类（`useDocClass` 是设备层既有的做法）；导出 `MOSAIC_CLASS` |
| `public/css/theme.css` | 删掉全屏 `.mosaic-layer`（含 z-index 55 与那三层棋盘格渐变），换成一条 `.sp-mosaic .spov:not(.hxov) { filter: blur(2px) saturate(.72) contrast(1.06) }` |
| `public/js/main.js` | 挂载点不变（组件现在返回 null） |

**关键细节：`.spov` 是共用外壳** —— `choiceOverlay.js`（机变 / 教鞭，根类就是 `spov`）与 `hexOverlay.js`
（协议源石抽取，根类 `spov hxov`）都用它。业主要的是「机变」，所以选择器带 `:not(.hxov)`，**协议源石抽取界面保持清晰**
（它同样是「看清卡片再选」的界面）。这一点是 grep 出来的，第一版差点连协议源石一起糊了。

**强度**：只用 `blur(2px)` + 轻微去饱和（沿用调过三轮的中点值），**不再要棋盘格纹理** —— 网格是「全屏层」的做法，
对一个必须读的浮层只会更难辨认。机变上有选项名、描述和倒计时，所以「看不清」是氛围，不是真读不出来。

**顺带的收益**：全屏 `backdrop-filter` 是**每帧**的合成开销，而且那个层永不消失、一直参与合成。现在只在机变真的开着时
付费，关掉就是零成本。

### 2026-10-16 · 查清 `verification-slices` 那条红（11/0）—— 又是 `prepFallbackGuard` 让测试前提失效

上一条记录里我提到的「另一条独立的红」。查清了：**复核（verification）本身没问题**，是测试的时序前提被移植改进推翻了。

#### 现象

`m.lastResults.get('p_0').leaked` 抛 `TypeError: Cannot read properties of undefined`。

#### 两棵树并排跑同一个探针（决定性）

```
Forge:  报告后 keys=["p_0"]  →  SETTLE R1 keys=["p_0"]  →  checked=1 时 phase=COMBAT R2 keys=[]   ✗
repo :  报告后 keys=["p_0"]  →  SETTLE R1 keys=["p_0"]  →  checked=1 时 phase=PREP  R2 keys=["p_0"]  ✓
```

**Forge 从 SETTLE R1 一路推到了 COMBAT R2**（`startCombat()` 里 `this.lastResults = new Map()` 把那份结果清掉），
而 repo 停在 `PREP R2`。

#### 根因：`prepFallbackGuard`

本测试是 `humans: 1, bots: 0` —— 正是「**1 真人 + N AI**」那一档（`loneHuman=true`、`soloUntimed=true`）。
本树多了 `prepFallbackGuard`（`docs/PS100-MIGRATION.md` hunk #4 的「纯收益修复」：那一档休整期退到官方

于是 SETTLE R1 没有停留就进了 R2 开战。repo 没有这个 guard（那一档 `untimed`），所以它停在 PREP —— 测试当年正是照那个行为写的。

复核那条路本身是对的：`sample` 档在报告那一刻就 `accept(result)`（`reports.js _verifyResult` 末尾），
复核在后台只记 mismatch、**不替换**已接受的那份。测试要断言的语义完全正确，只是它**顺手从 `lastResults` 里取那份结果**，
而那个 map 的寿命挂在「回合没有推进」这个前提上。

断言的意图（「复核不替换已接受的结果」）与回合推进无关，所以改成直接读那份被接受的结果：`f.result` 就是 `accept()`
写进去的（复核若要替换，`verified = server` 走的也是 `accept`）。顺带把「复核跑完也没换掉」写成一条独立断言
（`resultDigest(f.result).hash === resultDigest(forged).hash`，放在 `checked === 1` 之后）。

### 2026-10-16 · 「手机切 qq 后切回来会退出全屏」—— 记住「想要全屏」的意图，回前台补一次

#### 为什么必然会退出

这是 Fullscreen API 的**既定行为**：页面被切到后台（隐藏）时浏览器**自动退出全屏**，而且**不会**自动恢复；
更麻烦的是，在页面隐藏的状态下请求全屏会被直接拒绝 —— 所以只能在**回到前台之后**再请求一次。

原来的实现只有一个手动按钮（`ui/device.js` 的 `FullscreenButton`），没有任何「切回来补上」的逻辑，所以用户看到的
就是「切个 QQ 回来全屏没了」。

#### 修法：记一个「意图」，回前台补一次

`public/js/ui/device.js` 里新增模块级的 `wanted`（用户是否想要全屏）与 `restoreFullscreen()`：

| 时机 | 动作 |
|---|---|
| `enter()` 成功 | `wanted = true`（用户主动进的） |
| `exit()`（按钮 / 手动） | `wanted = false`（用户主动退的 —— **绝不**把他拉回去） |
| `visibilitychange` → visible | 若 `wanted` 且当前不在全屏 → 补一次 `enter()` |

**关键的一处判断**：浏览器自己的退出手势（Esc / 系统返回）**不走** `exit()`，但它会派发 `fullscreenchange`。
所以那个事件里要区分这次退出是谁干的：

```js
const onFsChange = () => {
  if (fullscreen.active(win)) return;                 // 还在全屏：什么都不做
  if (doc.visibilityState === 'hidden') return;       // 切后台被系统收走 —— 保留意图，回前台再补
  wanted = false;                                      // 页面可见时的退出 = 用户自己退的
};
```

**为什么不立刻恢复**：切回来的瞬间浏览器通常还没放开全屏请求，直接请求多半被拒。所以先等一帧（`requestAnimationFrame`）
再试，失败就静默放弃 —— 下次切回来还会再试。

#### 验证

`test/ui/devices.test.js` 新增一条用例，覆盖四种情形：

1. 进全屏 → 切后台（hidden + 系统收走）→ 切回来 → **自动补回全屏** ✓
2. 用户主动退出 → 切回来 → **仍是非全屏**（不被拉回）✓
3. 浏览器自己的退出手势（可见时只派发 fullscreenchange）→ 当成用户意图，清掉 wanted ✓
4. 不支持全屏的设备（iPhone Safari）→ 恢复是空操作，不抛 ✓

**踩到的坑**：`installDeviceSupport` 与 `wanted` 都是**模块级单例**（真实页面只装一次），测试里第二个 `fakeWindow` 会拿到
第一个的注册 —— 每个小场景用完必须 `dispose()`。

#### 修复 1 · 石像鬼变飞行后隐匿仍在

`stealth` 脚本只在 `enemySpawn` 那一刻判断一次 `enemy.isFlying`，但 `Unit.isFlying` 是**动态 getter**：
守墓石像的 `statue()` kit 在重生结束时执行 `e.motion = 'FLY'`，那一刻它变成飞行，

作者的意图很明确（`hextech.js:1578` 原文）：

> **A flyer has no block to end its stealth and no ground path to hide along**

修法：给这张卡自己加的 stealth buff 挂一个 0.25 秒的 `onTick`，一旦 `isFlying` 就移除。

```js
battle.addBuff(enemy, {
  key: 'ab:stealth', flags: { stealth: true }, persist: true, data: { stealthRestore: restore },
  interval: 0.25,
  onTick: ({ battle: b, unit: u }) => { if (u.isFlying) b.removeBuff(u, 'ab:stealth'); },
});
```

**为什么不动 `enemyStealthed`**：官方自带的 `kitStealth`（潜伏者 / 隐形弩手…）用的是**同一个**
`ab:stealth` buff key，作者明确写了「The gate is scoped to THIS card: the official kits' own 隐匿 keeps hiding」。
所以我只改**这张卡自己加的 buff** —— 官方 kit 的规则一个字没动。

#### 修复 2 · 镜像协议获得的债务不给干员

```js
+  if (spec.debt) {
```

**为什么安全**：作者在 `hextech.js:161` 写明了 depth guard 的唯一目的 ——

而这件事**已由函数顶部的 `depth >= 2` 做到**（同时限制镜像→镜像、二次抽取→二次抽取）。
`=== 0` 只挡住了合法获得。观察者自身的去重仍在（id = `effect:hexdebt:<picker>:<hex>`）。

### 2026-10-15 · 点开测试场报错（作用域 bug）

```js
// ProtocolSelect() 里（第 682 行）—— 这是【另一个函数】！
```
