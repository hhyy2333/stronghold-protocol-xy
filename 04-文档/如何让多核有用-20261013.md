# 如何让多核有用 · 2026-10-13

> 背景：线上是 **2 vCPU**，但实测 **主线程 p99=97.8%、峰值 101.2%**（30 真人 / 19 bot / 20 局），
> 也就是说**第二颗核基本没被游戏逻辑用上**。本文回答「怎么让多核真的有用」。
> 结论来自实测，不是推测。相关：[服务器承载能力评估](服务器承载能力评估-20261013.md)。

---

## 一、先看 CPU 到底花在哪（线上实测）

并发者做的性能面板给出的 buckets（95.8 s 窗口，总 193 s CPU）：

| bucket | CPU | 占比 | 是什么 |
|---|---|---|---|
| **bots** | 112.7 s | **58.3%** | bot 休整期的**摆阵排练**（每方案跑一整场战斗） |
| **serverRun** | 39.5 s | **20.5%** | 服务器替**无真人的战场**跑战斗 |
| core | 23.3 s | 12.0% | 阶段机、经济、抽卡 |
| views | 13.4 s | 6.9% | 构造 m.public / m.private |
| intents | 4.4 s | 2.3% | 处理玩家消息 |

**78.8% 的 CPU 是「战斗模拟」**——而战斗模拟恰恰是**最容易并行**的那一类工作：
输入是一段 JSON，输出是几个数字，中间不碰任何共享状态。

**这决定了答案：不要去并行化整个服务器，要并行化「跑战斗」这件事。**

---

## 二、可行性已验证（三个硬事实）

### 事实 1：战斗是纯函数式的（spec 进 → 小结果出）

实测一场真实战斗：

```
BattleSpec 大小   : 289 字节
可结构化克隆      : ✓ (structuredClone 成功，JSON 逐字节相同)
含函数/Map/类实例 : 无
结果大小          : 86 字节（几个数字）
```

`server/sim/` 本来就**不含任何 Node API**（`tools/check-imports.mjs` + ESLint 强制），
因为它要同时跑在浏览器里。**这意味着它天然可以放进 worker。**

### 事实 2：跨线程结果逐位一致（决定性实验）

我把**同一场真实战斗**跑两遍——一遍主线程，一遍 worker——对比结果：

```
main   : 14.1 ms
worker : 382.3 ms（含线程启动）
result identical: YES ✓ (determinism preserved)
```

**确定性保住了。** 这是最关键的前提：黄金结果（golden）不会被破坏，因为 spec 相同、种子相同、结果就相同。

### 事实 3：排练的输入输出都可克隆

| 项 | 大小 | 可克隆 |
|---|---|---|
| `ps.battleInput()`（棋盘快照） | 3,120 B | ✓ |
| 波次 spawns | 1,587 B | ✓ |
| 回来的「选中方案」 | 21 B | ✓ |
| 回来的 `{leaks, killed}` | 几十 B | ✓ |

## 三、被并行的「单位」有多大？（决定值不值得）

实测（`tools/botbench.mjs`，1 真人 + 3 bot，HARD，真战斗）：

```
一次排练          : 144 ms（p95 267 ms）
一次 bot 休整期    : 190 ms（p95 368 ms）
一场对局的 prep    : 12.16 秒 CPU
```

对比 worker 的启动成本（实测）：

```
worker online     : 17–25 ms
worker 完整生命周期: 30–41 ms
```

**一次排练 144 ms ≫ worker 启动 25 ms。** 而且用**常驻 worker 池**时启动只付一次。
所以**offload 是划算的**——这正是「让多核有用」的可行路径。

## 四、方案：按性价比排序

### 方案 A（推荐）：把「跑战斗」搬进常驻 worker 池

**范围**：`bots` 排练（58.3%）+ `serverRun`（20.5%）= **78.8% 的 CPU**。

**怎么切**：

```
主线程（便宜）                      worker（昂贵）
─────────────────────────────      ──────────────────────
按候选方案摆棋盘                    接收 BattleSpec
ps.battleInput() 取快照     ──►     跑完整场战斗
拼出 BattleSpec（~300 B）           返回 { leaks, killed }
还原棋盘                             （几十字节）  ◄──
比较分数，选最优方案
```

关键洞察：**主线程只需要「摆一下棋盘取快照」，不需要真的模拟战斗。**
`ps.board` 的临时改动只是为了让 `battleInput()` 读到布局，模拟本身完全不依赖主线程状态。

**这一点我逐行核对过**（`server/match/bot.js` 的 `run(budgetMs)` 循环体，第 1144–1178 行）——
模拟循环里碰到的外部东西只有：

| 碰到的 | 是什么 | 能否跨线程 |
|---|---|---|
| `battle.step()` / `battle.finished` / `battle.result()` | 自包含的战斗对象 | ✓ 全在 worker 里 |
| `countedLeaks(battle, ps.playerId)` | 纯函数，参数是一个**字符串** | ✓ |
| `ps.playerId` | 字符串 | ✓ |
| `performance.now()` | **只为分片计时** | worker 里可整段删掉 |
| `m.log.warn` / `m.perf.end` | 仅出错/记账时 | 回主线程报一行即可 |

也就是说**模拟循环里没有任何主线程可变状态**。这是「能搬」的最终证据。

**为什么这个方案好**：
- 确定性已验证（事实 2），黄金结果不变
- 已有先例：`tools/golden.mjs` 和 `tools/botbench.mjs` **已经在用 worker 池**跑同一套模拟
- 改动集中在 `server/match/bot.js` 的 `createRehearsalSteps` 和 `clientCombat._runOnServer`
- **不需要**外置状态、不需要改协议、不需要粘性路由

**代价**：
- 要把「切片」语义从「主线程分片」改成「worker 异步」。现在 `botSliceMs=8ms` 是为了**不阻塞主线程**；
  搬进 worker 后**主线程根本不会被阻塞**，反而可以取消分片、让 worker 一口气跑完。
- 每个 worker 要自己加载游戏数据（`server/data.js` 是 frozen 单例，worker 里各加载一份，约几 MB）。
- 需要一个「预算/背压」机制：机器 2 核，worker 池开 2–4 个就够，别开太多。

**预期收益**：主线程负载从 101% 降到约 **30–40%**（只剩 core/views/intents），
即**同样的机器大约能多承载 2–3 倍的人**。

### 方案 B（同样重要，几乎免费）：先砍掉不需要的工作

**实测：`botRehearsal` 从 3 降到 0 省 23% 的 bot 成本**（8062 → 6207 ms/局）。
而现在它**硬编码为 3，没有任何运维开关**（不在 `LOBBY_OPTION_KEYS`、无 `SP_*`、`lobby.js:1309` 不传）。

**加一个 `SP_BOT_REHEARSAL` 环境变量**，成本极低，收益立竿见影：
机器吃紧时设 `0`（bot 只按启发式摆阵），就**立刻少 23% 的 CPU**。

> 这比任何架构改动都快，而且**今天就能上**。

### 方案 C（不推荐，除非 A+B 都做完还不够）：多进程分片

**理论上**能用到多核，但代价极高：

- `SessionRegistry.byPlayerId` / `byTokenMap` 和 `Lobby.rooms` **都是进程内 Map**
- 玩家重连必须回到**同一个进程**（否则座位丢失）→ 需要**按房间哈希的粘性路由**或**外置会话/房间状态**
- 蓝绿部署的语义也要跟着改

**结论**：方案 A 能把「跑战斗」这块（78.8%）挪出主线程，**已经足以让 2 核都有用**。
方案 C 只有在「主线程只剩 core/views/intents 仍然吃满」时才需要——按当前比例，那要等到**约 400–500 真人**。

### 方案 D（锦上添花）：把 `views` 也并行化

`views` 占 6.9%（构造 m.public/m.private，每 100 ms 一次）。可以搬进 worker 做序列化，
但收益小、复杂度不低（要传整个对局状态）。**等 A 做完再考虑。**

## 五、为什么不建议「用满 2 核」当目标

一个容易走偏的方向：给 Node 加 `--max-old-space-size` 或调 `UV_THREADPOOL_SIZE` 来「用满 CPU」。
**这没用**，因为：

- `UV_THREADPOOL_SIZE` 只影响 **libuv 线程池**（文件 IO、DNS、**以及 P0 的 zlib**）。
  P0 已经用上它了——实测线程池只占 8%，说明**它不是瓶颈**。
- **JS 代码本身永远只在一个线程上跑**。要真正并行 JS，只能用 `worker_threads`，即方案 A。

---

## 六、一句话回答

> **多核没用的原因**：Node 的 JS 只在 1 个线程上跑，而 78.8% 的 CPU 是「战斗模拟」这件事。
>
> **让它有用的办法**：把「跑战斗」搬进 `worker_threads` 池。实测已证明三件事——
> spec 只有 289 B 且完全可克隆、跨线程结果**逐位一致**、一次排练 144 ms 远大于 worker 启动的 25 ms。
> 项目里 `tools/golden.mjs` / `tools/botbench.mjs` **已经在用 worker 池跑同一套模拟**，是现成的先例。
>
> **顺手还能省 23%**：给 `botRehearsal` 加一个 `SP_*` 开关（现在硬编码 3，运维动不了）。
>
> **预期**：主线程从 101% 降到 30–40%，同样机器多承载 2–3 倍人。
