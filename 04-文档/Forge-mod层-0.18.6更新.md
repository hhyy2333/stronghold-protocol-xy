# Forge mod 层：0.15.0 → 0.18.6 更新报告

> 对象：`参考对象\Stronghold-Protocol-Forge-0.18.6-0.2.6-win-x64`（APP 0.18.6 / 上游 **0.2.6**）
> 基线：[Forge-mod层剖析.md](Forge-mod层剖析.md)（那时是 0.15.0 / 上游 0.2.4）
> 本文只做对比与剖析，**不含任何代码改动**。

---

## 0. 一句话

**从 0.15.0 到 0.18.6，Forge 的 mod 层从「21 格表面」长到「38 格表面」，设计稿从 2,109 行长到 3,860 行，
新增 §28.23–§28.51 共 20 余节。** 但最值得注意的是**它没有变的那件事**：

```
MOD_API_VERSION  仍是 1     （从 0.15.0 到现在，一格表面都没删、没改名、没改语义）
MAX_SEATS        仍是 4     （官方档）
```

这恰好**验证了**基线报告 §5 那条「加一格不抬世代」的政策不是口号——**几十格新表面加进来，一个已发布的包都没被拒**。

**但有一处口径反转了**（§1.3），它直接影响你之前问过的容量问题。

---

## 1. 三处「口径变了」

### 1.1 ⚠️ 座位默认上限：4 → **20**

这是最重要的一条变化，直接推翻我上一轮给你的一个结论。

| | 0.15.0 | **0.18.6** |
|---|---|---|
| `MAX_SEATS` | 4 | **4**（不变，仍是「官方房间 1–4 人」的声明） |
| 默认天花板 | `maxSeatsFrom(env)` 缺省返回 **`MAX_SEATS` = 4** | 新增 **`DEFAULT_MAX_SEATS = 20`**，`maxSeatsFrom` 缺省返回 **20** |
| `SP_MAX_SEATS` 未设时 | **4 座** | **20 座** |

[shared/constants.js:82-112](C:/Users/hhyyl/Downloads/Stronghold-Protocol-v0.2.1/参考对象/Stronghold-Protocol-Forge-0.18.6-0.2.6-win-x64/Stronghold-Protocol-Forge-0.18.6-0.2.6-win-x64/app/shared/constants.js) 的注释原文：

> unparsable ⇒ `DEFAULT_MAX_SEATS`, i.e. a deployment that says nothing gets a **20-seat ceiling**.

以及：

> `SP_MAX_SEATS=4` 是**回到官方那一档**的口径：那时 `room.state` 与协议帧与「缺省 4 座」的旧部署**逐字节相同**。

**含义**：Forge 从「默认官方、要 20 人得显式开」变成了**「默认 20 人、要官方档得显式关」**。
「≤4 座逐字节不变」那条纪律**没有被放弃**——只是**触发条件从「缺省」变成了「显式 `SP_MAX_SEATS=4`」**。

> **对业主的直接影响**：基线报告里我写的「Forge 的做法是默认不变」**在 0.18.6 上已不成立**。
> 抄 Forge 的架构仍然正确，但**不要抄它的默认值**——你要的是「默认 4、显式开」，那正是 Forge 0.15.0 的形态。

### 1.2 ⚠️ `PROTOCOL_VERSION` 1 → **2**

0.15.0 是 `1`，现在是 `2`。这发生在 0.16–0.18 之间的某一刀（**不是因为 mod 层**——`MOD_API_VERSION` 一直是 1）。

**含义**：Forge 现在与 0.15.0 的客户端**协议不兼容**。任何按 0.15.0 写的对接代码都要重新对一遍。

### 1.3 ⚠️ 九格「刻意没有通道」里，两格被**部分打开**

`docs/WORKSHOP.md` §1.1 曾对 `official` / `config` / `meta` / `shared` / `theme` / `serverModules` 六格写下「刻意没有通道」。
0.18.6 里这条线被**两条新的收窄通道**绕开了（是收窄，不是打开）：

- **§28.39 `variants`**：口径层。包说的是**「哪一套」，不是「改成几」**——值由引擎给。
  轴表 `VARIANT_AXES` 是**闭枚举**（`training`、`deploy`），**只在被一份真实投稿要求时才加轴，不许为将来预留空轴**。
- **§28.43 `behaviour`**：行为开关。同样闭枚举，**动作由引擎构造**（`actions(option)`），
  包**给不出数字，也给不出键路径**。今天 4 格：`shopBias` / `prepLoadout` / `morphPairing` / `unequip`。

设计稿把判据写得极清楚（§28.43 原文）：

> 一个能指定任意文件覆盖、或让包直接写数值的包格式**就是安装器**。

**加一格的门槛**（比 `VARIANT_AXES` 更严）：那一格**必须已经在引擎里有实现点**，
「每一格都有一处具名读取点、一个测试文件与一节文档」。而且 `BEHAVIOUR_SWITCHES` **在第 4 刀落地时是一张空表**，
那是刻意的——**空表不是「不认识的开关一律忽略」，而是「一个都不认识」**。实测它真的挡过投稿。

> 这两格是这一层**最值得学的设计**：它把「作者想要一个引擎没有的规则」这件事，
> 从「改引擎文件」变成了「维护者实现一格 → 任何包声明它」。**这是对安装器形态的结构性回答。**

## 2. 表面表：21 → 38 格

新增的 17 格（按 `shared/modSurface.js` 的 `id`）：

| 新格 | 层 | 是什么 |
|---|---|---|
| `traits.grantsBonds` | A | **纯数据**：`trait.grantsBonds: [bondId]` ⇒ 该棋子视为盟约成员 ⇒ 层数自然上去 |
| `variants` | A | 口径层（§28.39） |
| `behaviour` | A/B | 行为开关（§28.43） |
| `target` | — | `forge`（缺省）/ `stardust`（声明型，本引擎只认识不装载） |
| `dependencies` / `conflicts` | — | 装载期跨包裁决（§28.48） |
| `enabled` | — | 装好 ≠ 生效（§28.50） |
| `server.transport` | B | 启动期传输配置（§28.33） |
| `server.modules.metrics` | B | 只读指标快照（§28.34） |
| `server.modules.route` | B | 动态只读端点（§28.35） |
| `media.voices.cdn` | A | 作者自备 CDN 的语音（§28.36） |
| `client.sources` | C | 素材加载源（§28.40） |

**内容表**：14 → **15** 张（新增 `variants`）。
**顶层键 `PACK_FIELDS`**：延长到 **35**（`target`、`dependencies`、`conflicts`、`enabled`、`variants`、`behaviour`）。
**客户端宿主**：**仍是 9 个**（`CLIENT_PANEL_SLOTS` 一字未变）。

### 2.1 最漂亮的一格：`traits.grantsBonds`（§28.49）

业主原话是「我们的 forge 能不能做出游戏内的『特质』效果，即一般是用来**叠加盟约层数**的固有天赋」。

落法是一条**纯数据**通道：`chess.json` 的记录在 `trait` 上写一格 `"grantsBonds": ["<bondId>"]` ⇒
**带这条特质的棋子视为那些盟约的成员** ⇒ `rawCount` +1 ⇒ 层数自然上去。

> **不需要模块、不需要 `server.meta`、不需要一行脚本——一个不懂代码的作者也能落这条天赋。**

这正是「能力分级」判据的最佳示范：一个能改对局结果的东西，用**数据**表达出来，就不必开代码通道。

### 2.2 `enabled`（§28.50）里的一条纪律值得单独记

> **只有布尔**：`"false"` / `0` / `null` / `"true"` 一律 `ENABLED_BAD_SHAPE` **整包拒**。
> 理由：一个被 JS 真值表放行的**假布尔**是**静默失效**——作者写下的是 `"false"`，引擎读到的是「启用了」，
> 而**这之间没有任何人会收到一条错误**。

以及「跳过必须响亮」：`false` 的包**不进入 `packs`**，而是进 `errors`（`ENABLED_FALSE`）并逐条 warn 点名——
**一个静默消失的包比一个报错的包难查得多**。

## 3. 一条贯穿全篇的「缺省不变」纪律

新增的每一格都遵守同一条（设计稿反复引用 `§28.2` 那笔老账）：

> 不声明 `X` 的包，归一化清单里**不长出这个键**——无条件写进去会让**所有已发布包**的内容哈希改变，
> 房间的摘要闸门随即误判。

`skins` / `voiceCdn` / `variants` / `behaviour` / `enabled` / `target` / `dependencies` / `conflicts`
**八格逐字同一条**。而**声明了就必须进身份哈希**：只差一个开关的两份包摘要必须不同。

**这条纪律是「加一格不抬世代」能成立的机械原因**——它让新增字段对已发布包**在字节上不存在**。

## 4. 跨包裁决（§28.48）：从「同 id 抢占」升级到「图裁决」

基线报告里那一节只有两条规则（官方不可无声明替换 / 包 id 小者赢）。0.18.6 加了**装载期的图裁决**
（`adjudicatePackGraph`，纯函数、确定性、全部具名）：

| 情形 | 裁决 |
|---|---|
| 缺失依赖 | 依赖方被拒 |
| 版本不合 | 依赖方被拒。**依赖包没写 `version` 时视为满足**（`0.0.0` = 未声明） |
| 互斥 | **包 id 大的**那个被拒 |
| 级联 | 被拒的依赖让它的依赖方也无法工作，**迭代到不动点**（`top → mid → low → 缺失` 要三轮） |
| 循环 | 幸存集合里的依赖边成环 ⇒ **环上全体被拒** |

⚠️ 设计稿**主动记录了一处与社区 PR 自带测试相反**的地方（PR 测「未声明 ⇒ 0.0.0 ⇒ 不合 ⇒ 拒」，
规则与业主裁决是「未声明 ⇒ 视为满足」），并按**规则**实现——**这种「把冲突写进文档而不是悄悄选一边」的做法值得学**。

## 5. 管理器（§28.47）：登记册 + 两条硬闸

新增 `mod-registry.json`（**唯一事实**，在状态根，**永远不在 `workshop/` 包根里**——那里是加载器扫描的地方，
一个状态文件放进去会被当成一个包）。方向是**「不在册 = 启用」**：

> 装一个包就该立刻能用。反过来的话，这个文件一旦丢了（或换了机器），所有包都会**静默消失**——又是一个静默方向。

两条硬闸：
1. **ownership**：只卸载本管理器登记过的包（仓库自带 / 手工放置的，管理器**不认识它，就没有资格处置它**）；
2. **留底**：卸载与回滚都是 `renameSync` 挪进 `.mod-backups/`，**不是 `unlink`**。

**越界删除必须被拦，而且要有测试证明**——分两层（入口层 `PACK_ID_RE` + 第二层 `normalizePackEntry` 校验
「包内相对留底目录」），并用**逐字节比对目录树**证明：`data/`、`test/golden/`、`server/` 哨兵四棵树逐个哈希不变。

> 这是整份设计稿里**测试写得最硬**的一节：不是「断言函数返回了什么」，而是「断言磁盘上什么都没变」。

## 6. 新增的两条「能力通道」（对业主最有参考价值）

### 6.1 `uses: ["metrics"]`（§28.34）

设计理由写得很直白：

> 一条只有禁令没有替代品的规则会逼作者绕路（`globalThis['pro'+'cess']`）。

所以 `host.metrics()` 返回一个**深冻结的普通对象**，字段**闭集**
（`uptimeSec` / `rss` / `heapUsed` / `elu` / `loopP50` / `loopP95` / `loopP99` / `loopMax` / `sampleAgeMs` / `state`）。
**是值不是句柄**：没有 `process`、没有直方图对象、没有定时器、没有函数。**惰性启用**（没装包 ⇒ 开销为零）。

还有一条纪律：**过期不给旧值**——采样器跑不动时 `loopP*` 全是 `null`、`state` 是 `stale`，并**点名 warn 一次**。
「不许静默空白」与「不许静默旧值」是**同一条纪律的两面**。

### 6.2 `uses: ["route"]`（§28.35）：动态只读端点

六条纪律，其中三条特别值得抄：
- **命名空间**：路径必须在 `/mod/<包id>/…` 里——包**没有位置**去点名 `/data/support.json`；
- **核心保留路径表**（`RESERVED_ROUTE_PREFIXES`）：**纵深防御**——将来谁放宽了第 1 条，第 2 条还在；
- **回调必须同步返回**（`Promise` 点名拒绝）：单进程单事件循环，一个 `await` 的处理器就是一条能拖住整台服务器的路。

## 7. 新文档层：从「规则」到「入门」

0.15.0 的 `docs/WORKSHOP.md` 是 2,232 行**规则**，0.18.6 是 2,803 行。但真正新增的是**入门层**：

| 新文件 | 作用 |
|---|---|
| `docs/START-HERE.md` | 四步做一个包（复制模板 → 改三处 → 导出 → 上传），每步写清「输入 / 敲什么 / 成功看到什么 / 最常见失败原因」 |
| `docs/errors.md` | 错误码**白话表** |
| `docs/task-01-换个立绘.md` / `task-02-加个干员.md` | 两个具体任务 |
| `docs/my-first-pack/` | 一个**真跑过**的模板包（`pack.json` + `assets/portrait.png`，共 **438 字节**） |
| `docs/STANDARD-PACK.md` | 标准包格式 |

以及一处**架构性改动**：判据本体从 `tools/workshop-validate.mjs`（**维护者工具**，不随玩家包发出）
搬进 **`shared/workshopValidate.mjs`**（随包发出、编辑器与游戏共用），CLI 变成**薄包装**。

> 理由：B1 要的是「界面里按一下给我结论」，而那条结论必须与 CLI **一致**；编辑器服务端 import 维护者工具会当场崩。
> **「判据只有一份，CLI 与界面都调它」**——这条对业主的 `tools/packs.mjs check` 同样适用。

### 8.1 我上一轮的建议**不变，而且被加强了**

基线报告 §8.1 说「只有表面表值得立刻抄」。0.18.6 **强化**了这个判断：

- Forge 在 **几十格新增** 的情况下 `MOD_API_VERSION` **一动不动**——证明这套机制**真的能长期维持**；
- 而它维持的方式**不是**「大家小心点」，是**那张表 + 双向闭合守卫**；
- 业主这棵树现在**依然没有任何东西**阻止一次上游移植悄悄删掉 `PACK_TYPES` 的一格。

### 8.2 新增的一条警告

⚠️ **不要抄 Forge 0.18.6 的默认值。** 它的 `DEFAULT_MAX_SEATS = 20` 意味着**缺省就是 20 人房**。
业主如果做容量，要的是**「默认 4、显式开」**（= Forge **0.15.0** 的形态）。
把两件事分开看：**架构抄 0.18.6，默认值抄 0.15.0。**

## 10. 结论

1. **这一层在健康地长。** 几十格新表面、+2,932 行、20 余节设计稿，**一个已发布的包都没被拒**——
   「加一格不抬世代」不是口号。
2. **它的核心仍是那张表。** 0.18.6 新增的每一格都带着「符号 + 实现文件 + 测试 + 设计稿一节」，
   `MOD_SURFACE` 从 21 格长到 38 格，**双向闭合的守卫一字未改**。
3. **⚠️ 两处口径反转要记住**：`DEFAULT_MAX_SEATS` 4 → **20**、`PROTOCOL_VERSION` 1 → **2**。
   前者意味着「抄 Forge 架构」时要**抄 0.15.0 的默认值**。
4. **最值得学的两处新设计**：
   - **§28.43 `behaviour`**：把「作者想要引擎没有的规则」从「改引擎文件」变成「维护者实现一格 → 任何包声明它」。
     这是对**安装器形态的结构性回答**，而且它**允许表是空的**（空表 = 一个都不认识，不是静默忽略）。
   - **§28.49 `traits.grantsBonds`**：一个能改对局结果的东西，用**纯数据**表达出来，就不必开代码通道。
5. **对业主的行动建议不变**：**只抄表面表 + 双向闭合守卫**（零运行时改动、与现有政策完全兼容），
   锚点你已经有（`PACK_TYPES` / `DATA_ROLES`）。
6. **另加一条**：`shared/workshopValidate.mjs` 那条「**判据只有一份，CLI 与界面都调它**」的做法，
   对你 `tools/packs.mjs check` 与将来的编辑器同样适用——**判据不要住在维护者工具里**。
