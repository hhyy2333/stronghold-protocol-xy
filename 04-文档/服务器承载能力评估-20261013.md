# 服务器承载能力评估 · 2026-10-13

> 问：这台服务器最多能承担多少人？
> 方法：**在线上真实负载下实测**（不是估算）。采样期间线上有 20–30 名真人、13–20 局在跑。
> 硬件：阿里云轻量 **2 vCPU / 1613 MB / 无 swap**，Ubuntu 24.04，Node v22.20.0。

---

## 一、结论

| 场景 | 舒适上限 | 硬上限（开始卡） |
|---|---|---|
| **有 AI 队友**（当前用法，bot:真人 ≈ 1:1.5） | **约 60–80 真人** | **约 110–130 真人** |
| **纯真人、无 bot** | **约 1500–2000 真人** | 2500+ |
| 现在（2026-10-13 15:38） | **29 真人 / 19 bot / 20 局 —— 已经在硬上限附近** | |

**一句话**：这台机器今天已经跑在它的极限上了——瓶颈不是内存（只用了 249 MB），
而是 **Node 只用一个 CPU 核跑 JS**，而 **bot 的整场战斗排练把那个核吃满了**。

---

## 二、决定性证据：主线程已经触顶

线上实测（300 个 500 ms 采样窗口，当时 **30 真人 / 19 bot / 20 局**）：

```
MAIN JS 线程 : p50=  6.0%   p90= 45.8%   p99= 97.8%   max= 101.2%   （占单核）
libuv 线程池 : p50=  0.0%   p90=  2.0%   p99=  6.0%   max=   8.0%
进程合计     : p50=  6.0%   p90= 63.9%   p99=131.2%   max= 143.7%
```

- **主线程 p99 = 97.8%，最差 101.2%** —— 也就是说，**这个核已经被占满了**。
- `libuv` 线程池（P0 的 zlib 压缩就跑在这里）只用 8%，**它和主线程并行**，所以进程合计能到 143%——
  但**游戏逻辑本身只能用那一个核**。
- **第二颗 vCPU 帮不了游戏循环**，只能帮压缩和磁盘 IO。这就是为什么这台 2 核机器实际是「1 核」的容量。

**实测主线程从未超过 ~101%**，符合 Node 单线程的预期。所以**容量的天花板 = 1 个核**，不是 2 个。

---

## 三、成本结构：bot 贵 23 倍

线上分层统计（14 个有足够数据的房间）：

```
有 bot 的房间   : 平均 1.37% 单核/房间（1.8 真人 + 2.2 bot）
无 bot 的房间   : 平均 0.04% 单核/房间（1.3 真人）
                 → 有 bot 的房间贵 37.8 倍
```

逐席拆分：

| 席位 | 平均成本 | 峰值成本 |
|---|---|---|
| **真人** | **0.027% 单核** | ~0.1% |
| **bot** | **0.62% 单核** | **~8% 单核** |

**为什么 bot 这么贵**：真人的战斗在**他自己浏览器里**跑；bot 的战斗在**服务器上跑**。
而且每个 bot 在每次休整期要**排练最多 3 场完整战斗**（`botRehearsal` 默认 3）来决定怎么摆阵。

实测（本机，1 真人 + 3 bot，真战斗，虚拟时间跑完整局）：

```
botRehearsal=3（默认）: 8062 ms CPU/局
botRehearsal=1        : 6957 ms CPU/局
botRehearsal=0（只启发式）: 6207 ms CPU/局
→ 排练占一场 bot 对局的 23%
```

**bot 模拟占全部房间 CPU 的 57.5%。**

---

## 四、为什么"平均成本"会严重低估

用平均成本 0.62%/bot 预测「26 真人 + 16 bot」只得 10.6% 单核，
但**线上实测同一时刻的峰值是 129%**——低估了 12 倍。

**原因：bot 的成本是脉冲式的**，不是均匀的。实测 500 ms 窗口：

```
CPU 百分位（占单核）: p50=6.0  p90=45.6  p99=142.0  max=155.7
超过 60% 的采样占比 : 8.6%
```

**8.6% 的时间里 CPU 冲过 60% 单核**，而这些尖峰与 bot 数量相关——多个 bot 的排练在同一瞬间到期时，
主线程会被连续占用。`botSliceMs=8ms` 的设计让单个切片不阻塞太久，但**切片排队起来仍然占满一个核**。

**所以容量必须按峰值算，不能按平均算。**

---

## 五、为什么不是内存问题

内存实测**极其宽松**：

```
线上 RSS        : 231–255 MB / 1613 MB
系统可用        : 758–797 MB
线性拟合        : RSS ≈ 232 MB + 176 KB/局 + 61 KB/连接
```

按 176 KB/局算，1 GB 可用内存够 **6000 局**。**内存完全不是瓶颈。**
（⚠ 但**没有 swap**，所以真到内存墙会 OOM 杀进程，而不是变慢——目前离得很远。）

## 七、要提升上限，按性价比排序

| # | 措施 | 预期效果 | 代价 |
|---|---|---|---|
| **1** | **减少 bot 数量**（空位让真人补，或空位就用空位） | **最大杠杆**：bot 贵 23 倍。把 19 个 bot 换成真人，CPU 反而降 | 玩法上少一点便利 |
| **2** | **降低 `botRehearsal`**（3 → 1 或 0） | **省 23% 的 bot 成本**；bot 变笨一点（少试摆阵方案） | 现在**不可运维调**（不在 `LOBBY_OPTION_KEYS`、无 `SP_*`）——需要加一个开关，见下 |
| **3** | 提高单核性能 / 换更强的单核 CPU | 直接线性提升 | 花钱；**加核没用**（除非改多进程） |
| **4** | **多进程分片**（按房间哈希到不同进程 + 共享会话/房间状态） | 能用上多核，理论上 ×N | **大工程**：会话与房间都是进程内 Map，需要外置状态或粘性路由 |
| **5** | `botSliceMs` 调小 | 让尖峰更平滑、更少排队 | 每个切片更短，但总工作量不变；治标 |
| 6 | 内存相关 | **不需要** | 离内存墙还远 |

### 建议立刻做的两件小事

1. **给 `botRehearsal` 加一个环境变量**（照 `SP_MAX_*` 的做法，`server/http/config.js`）。
   现在它**只有 `startServer({...})` 调用方能改**，而进程入口不传任何选项——
   线上机器吃紧时运维**没有杠杆**。这是本次评估发现的**最实际的缺口**。

   **已核实（三处证据）**：
   - `server/match/Match.js:214` 硬编码 `const BOT_REHEARSAL_DEFAULT = 3;`
   - `server/http/config.js` 的 `LOBBY_OPTION_KEYS` **不含** `botRehearsal`（只有 `lobbyGraceMs / maxRooms / maxRoomsPerAddr / maxMatchesPerAddr / resyncMinGapMs / soloReconnectWindowMs / mods / statsPushMinGapMs / roomListMax`）
   - `server/lobby.js:1309` 的 `new this.MatchClass({...})` **没有传** `botRehearsal`
   - 全部 `SP_*` 变量只有 `SP_ANNOUNCE_DIR / SP_BOT_EMOTES / SP_FEEDBACK_DIR / SP_MODS / SP_NOTES_DIR` —— **没有任何 bot 相关开关**

   即：**改 bot 的排练次数，今天只能改源码**。而它占一场 bot 对局 23% 的 CPU、bot 又占全部房间 CPU 的 57.5%。

2. **把 `maxRooms`/`maxConnections` 从默认值收紧**到与实测相符（`SP_MAX_*` 已支持，但线上**未设置**）。
   不过要说明：**这两个上限不是当前的瓶颈**——内存离墙很远，真正的墙是主线程。

## 八、复现方式

本次评估用的探针已删除（不留在仓库/服务器）。重现方法：

```bash
# 主线程 vs 线程池（关键指标）
#   /proc/<pid>/task/<tid>/stat 的 utime+stime，按 tid 分类：
#   tid == pid 或 comm == 'node' → 主 JS 线程；comm == 'libuv-worker' → 线程池
# 每 500 ms 采样，除以 (CLK_TCK × 间隔) 得「占单核百分比」

# 每房间成本（并发者做的面板）
curl -H "Authorization: Bearer $ADMIN_SECRET" http://127.0.0.1/api/admin/rooms
#   perf.totalMs / (perf.matchUptimeSec × 1000) × 100 = 该房间占单核百分比
#   perf.buckets.bots = bot 排练与模拟的累计毫秒

# bot 的排练成本（本机）
node tools/botbench.mjs --configs coop4:HARD --seeds 3 --jobs 1
#   输出 "per match: prep CPU s"
```

## 九、一句话回答

> **当前用法（带 AI 队友）下，这台 2 vCPU / 1.6 GB 的机器大约能承载 60–80 名真人；
> 硬上限约 110–130 人，而且今天下午 29 人在线时主线程已经摸到 100% 了。**
>
> **瓶颈是「Node 单线程 + bot 在服务器上跑整场战斗排练」，不是内存、不是带宽（P0 已经把带宽问题解决了）。**
> **最快的提升办法是少用 bot；其次是给 `botRehearsal` 一个运维开关。**
