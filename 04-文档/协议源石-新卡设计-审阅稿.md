## 1. 先说最重要的一件事：敌方为什么「太普通」

你说的「敌人的太普通了」不是设计偷懒，是**架构上限**。我把链路走了一遍：

| 环节 | 现状 | 后果 |
|---|---|---|
| `tools/build-hextech.mjs` 的 `MOD_KEYS` | 只允许 7 个键：`hpMul` `atkMul` `defMul` `resMul` `speedMul` `supplyHpMul` `countAdd` | **非数值的敌方效果根本无法写进名单**，构建直接报 `unknown mod` |
| 同上，每个键的取值域 | 强制 `0.5 < v ≤ 1.35` | 连「+50% 伤害」这种数值都会被校验挡下 |
| `shared/hextech.js sumEnemyMods` | `out[k] = (out[k] ?? 1) * v`，且只收 `Number.isFinite(v)` | 布尔 / 字符串（想做「开/关」类效果）会被**静默丢弃**（实测：`{boom:true}` → `{}`） |
| `server/match/hextech.js` `NORMAL_MODS` | 闭集，只把上面 6 个键折进刷怪 | 自定义键进不去 |
| `server/match/match/combat.js:66`（普通战斗） | `flags: { layerGainsEnabled: true, ...dp }` —— **没有 `enemyMods`** | 敌方效果只会变成「每个小怪的身材数字」，战斗里没有任何脚本能读到「敌方拥有什么」 |
| `server/match/match/bossRounds.js:107`（首领战） | `flags: { …, enemyMods: hexMods }` | **只有首领战**带了敌方效果 |

**结论**：现在敌方协议的 14 张，上限就是「给敌人加几点血/攻/防/抗/速/器物敲击数」。要做「亡语」「回响」「腐蚀领域」这类有性格的动词，需要先补一条**敌方战斗通道**。

**好消息是这条通道不用新架构**，三个现成的部件已经在了，只是没接上：

1. `server/sim/content/index.js` 的 `MODULES` 里**已经包含 `hextech`** → `install(battle)` 在**每一场**战斗（含普通战斗、含客户端自己的模拟）都会跑；
2. `battle.on('enemySpawn', …)` 是**已验证的扩展点**——`choices.js:492`（机变卡给敌人上 debuff）、`bosses.js:278`、`enemies.js:138` 都在用；
3. `server/sim/content/enemies/helpers.js` 里 `areaAllies` / `areaAlliesInTiles` / `hurt` / `elem` / `zone` / `auraBuff` / `spawnChildren` 全部是现成导出的工具。

所以补通道 ≈ **三处小改**（都还没动，等你点头）：

* `combat.js` 的 `flags` 加上 `enemyMods`（甚至直接带 `enemyHexes` 的 id 列表），与 `bossRounds.js` 对齐；
* `build-hextech.mjs`：允许敌卡带一个「动词」字段（例如 `enemyScript: {...}`），不再强制 `mods` 非空；
* `server/sim/content/hextech.js`：`install()` 读这批 id，按 id 挂 `enemySpawn` / `death` / `tick` 等脚本。

**另外必须提醒**：`server/match/unite.js`（联防）**也没有** `enemyMods`（实测 `unite.js` 里搜不到这个词）。联防是把上回合漏掉的敌人按「泄漏时携带的 mods」重新放出来，所以**倍率能跟着走、动词走不了**。要让敌方动词在联防里也生效，这条通道得一起补。

## 2. 本次实测发现的其他几个坑

### 2.1 「团队卡 + 获得时的 LP 效果」目前只对发起人生效

`server/match/hextech.js` `applyHex()`：

```js
for (const p of targets) {
  …
  if (p === ps) applyHexLp(m, p, hex);   // ← 只有发起人走这里
  addHexRef(m, p, hex);
}
```

`effect.team: true`（现行只有 共鸣协议）会把 `onRoundStart` 发给每名队友，但 `onPick.lp` 被 `if (p === ps)` 挡住，
且没有任何注释说明这是有意的。§27.1 文档写的是「团队卡照机变团队卡处理，每名目标各跑自己的 ctx」——这里是例外。

**影响**：你把战争机器改成 **LP +5**，现在会**只给发起人 +5，队友一点没有**。
必须把那一行改成 `applyHexLp(m, p, hex)`（1 行 + 1 条测试），否则这张卡是残的。

### 2.2 第二张 `countAdd` 敌卡不会叠加（`sumEnemyMods` 是乘法）

实测：

```text
1 张：{ countAdd: 1, hpMul: 0.92 }
2 张：{ countAdd: 1, hpMul: 0.8464, atkMul: 0.95 }   ← countAdd 仍是 1
```

4 人敌组只加 1 而不是 2。**这条现在只影响「如果以后第二张身材卡」**——重做后的敌方 10 张里我没有再放 `countAdd`，
所以**可以先不动**；但如果你想要「数量」这条轴回来，得先把这个改成交加。

### 2.3 `onEquip` / `onArt` 永远到不了协议源石

`EffectDispatcher.dispatch()` 第 5 步跳过 `onEquip`/`onArt`/`onDestroy`（它们只走 `dispatchItem` → `item:<key>`），
而协议源石是 `hex:<id>` 持久效果，只能从第 6 步拿钩子。实测枚举全部调用点后的结论：

```text
协议源石能收到：onIncome onPrepStart onPrepEnd onGain onSold onRefresh onBuy onSpend
                onMerge onLevelUp onBattleStart onBattleResult onChoicePick onDestroy onLayers onPrice
收不到（物品专属）：onArt onEquip
```

`onDestroy` 能收到（`items.js:158` 有玩家级派发），所以 装备转化 没问题。
**建议**：把 `onEquip`/`onArt` 从 `HEX_HOOKS` 摘掉，或在头注释里注明「物品专属钩子对 hex 不可达」——
否则后来者一定会写出和 §27.8 一样的废卡。

### 2.4 「获得时扣 LP」会撞不变量（这次没用上，但要知道）

`applyHexLp` 是 `ps.lp = Math.max(0, …)`（下限 0），而 `invariants.js:59` 要求
「存活玩家在 SETTLE 之外 `lp > 0`」。对比 `ctx.spendLp` 用的是 `Math.max(1, …)`（§27.7 明写过理由）。
你没让我做扣血的卡，所以**本批安全**；将来要做「以血换强」，这 1 行得先补。

### 2.5 军械库：**我上一版说错了** —— 随机完全能做到，**零代码改动**

你问「为什么不能随机」。**能，而且现成**——你贴的**凯瑟琳【定向投放】就是活证**（「每次升级调度中心时，刷新随机 3 件装备」）。
我上一版只看了 `spec.item` 那一条路，就下了「实现不了」的结论，是错的。真实情况是**两条路**：

```js
// 路 A：hextech 现在用的（server/sim/content/hextech.js:92-95）—— 只能整数阶
const tier = Number.isInteger(spec.item.tier) ? spec.item.tier : 1;   // 'level' 被吞成 1
const id = ctx.rollItem({ tier, maxTier: Math.max(tier, shopLevel) });
//                          ↑ 只要 tier 是整数，rollItemId 就走 tierList(tier, tier)，maxTier 被忽略
```

```js
// 路 B：凯瑟琳 / 娜仁图亚用的（server/sim/content/bands/meta.js:263 → ctx.rollPool）
const r = ctx.rollPool('pool_equip_normal');   // 注意：不用传 shopLevel
```

**为什么路 B 一行就够**：`effectsMeta.js` 的 `rollPool` **自己就把 `shopLevel: ps.shop.level` 注入了**：

```js
rollPool: (poolId, opts = {}) => m.rollPool(poolId, { shopLevel: ps.shop.level, …opts }),
```

而 `choices.json` 里 `pool_equip_normal` 的定义正是 `{ kind:'equip', rule:'shopEligible', maxTier:'shopLevel' }`
——「不高于调度中心等级」**本来就是它的语义**。

**实测**（真 `makeMatch` + 真 `makeCtx`，每档 400 次）：

```text
调度中心 1 级 → 阶分布 {"1":400}                    最高阶 1  ✓ 不高于等级
调度中心 2 级 → 阶分布 {"1":193,"2":207}            最高阶 2  ✓
调度中心 4 级 → 阶分布 {"1":59,"2":78,"3":138,"4":125}  最高阶 4  ✓
调度中心 6 级 → 阶分布 {"1":42,"2":40,"3":78,"4":83,"5":61,"6":96}  最高阶 6  ✓
```

对照 `rollPool('pool_equip_kathe')`（凯瑟琳池，**故意不设上限**）：1 级时就能刷出 6 阶——所以「要不要封顶」是**池子定义**的事，不是引擎的事。

**结论（修正）**：军械库**不需要改引擎**，写成
`onRoundStart: { item: { pool: 'pool_equip_normal', count: 1 } }`，
`applySpec` 里给 `spec.item` 加一个「有 `pool` 就走 `ctx.rollPool`」的分支即可——**约 3 行**，比 `'level'` token 那条路更短、还复用现成语义。

* 上一版说的「`maxTier` 是死参数」在**路 A 内**依然成立（值得记一笔，将来有人写 `item.tier: 'level'` 会静默只出 1 阶）；
  但**对这张卡不构成障碍**——绕开就行了。
* 顺带：`build-hextech.mjs` 确实只校验 `chess.tier`、不校验 `item.tier`，这一条仍然成立，建议顺手补上。
