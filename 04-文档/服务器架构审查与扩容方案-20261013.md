# 服务器架构审查与扩容方案 · 2026-10-13

> 审查对象：`Stronghold-Protocol-repo/server/`（389 文件 / 5.2 MB；http 9、match 60、sim 310）
> 方法：读代码 + **实测**（真 ws 服务器、真客户端、真 m.public 帧、真战斗引擎）。所有数字都是本机跑出来的。
> 并发状态：期间有人在改 `server/match/perf.js`、`server/admin.js`、`public/admin/*`（房间性能查看）。
> **本文只提方案，没有改动任何服务器代码**——那是那位的工作面。

---

## 一、结论先行

**这个架构本身没有「撑不住」的结构性问题。** 它做对了几件通常会被做错的事：

| 设计 | 为什么是对的 |
|---|---|
| 战斗在**玩家浏览器**里跑（`SP_COMBAT=client` 默认） | 最贵的那部分 CPU 根本不在服务器上 |
| `m.public` 广播**每房间只序列化一次**，再把同一个字符串发给 N 个 socket（`lobby.broadcastRoom`） | 没有「N 个客户端 = N 次 stringify」的经典错误 |
| bot 排练按 `botSliceMs=8ms` **切片**，一次调度回调只跑 8 ms | 整场模拟不会阻塞事件循环——这是单进程架构最容易死的地方 |
| 背压：`b.snap` 在 1 MB 排队时丢弃，16 MB 直接断开重连 | 慢客户端不会拖垮整个进程 |
| 广播节流 `PUBLIC_THROTTLE=100ms` + 去重（`_lastPubJson`） | 上限锁死在 10 帧/秒 |

**真正的瓶颈是下行带宽，不是 CPU。** 而且这个瓶颈已经被定位并有现成方案（见第三节）。

## 三、首要方案：打开 `permessage-deflate`

### 现状

```js
// server/http/websocket.js:41
new WebSocketServer({ noServer: true, maxPayload: WS_MAX_PAYLOAD, perMessageDeflate: false, clientTracking: false });
//                                                                                  ^^^^^ 关着的
```

我全工作区扫过：**开发版、v0.2.5、Forge 三方都是 `false`**，一个都没开。

### 为什么收益这么大

`m.public` **每 100 ms 发一次、内容 99% 相同**（棋盘、资金、回合、队伍栏）。deflate 的**上下文保持**（context takeover）让第 2 帧起只传「与上一帧的差异」——实测 2669 B → 42 B/帧。

### 已经有一份做好功课的补丁 —— ⚠ 但它是**坏的，不能 `git apply`**

工作区里 **[`_verify/PATCH-ws-compression.patch.txt`](../_verify/PATCH-ws-compression.patch.txt)** 的思路是对的，而且它避开了一个真实的坑：

> **不要**声明 `serverNoContextTakeover` 或 `serverMaxWindowBits`。声明任何一个就变成「要求」，`ws` 对不可接受的协商直接回 **HTTP 400**——客户端**连不上**，不是降级。作者实测过一个只提供 `server_no_context_takeover` 的客户端会吃到 400。

**但 2026-10-13 复测：这个补丁文件本身是坏的，`git apply --check` 直接报 `corrupt patch`。**

```
error: corrupt patch at ../_verify/PATCH-ws-compression.patch.txt:15
```

原因（逐 hunk 数了一遍）：

| hunk 起始行 | 声明 | 实际 |
|---|---|---|
| 行 3 | `@@ -1,10 +1,11 @@` | 只有 7 行 old / 8 行 new |
| 行 15 | `@@ -38,7 +39,16 @@` | 只有 8 行 old / **24** 行 new |
| 行 42 | `@@ -0,0 +1,52 @@` | 只有 **42** 行 new |

也就是说：这是一份**手写/手工注释过、但从未验证过能否应用**的补丁——三个 hunk 的行数声明全都对不上。**别照着它 `git apply`。**

**正确做法**：照它**手工改** `server/http/websocket.js` 那一处（改动很小，就是一个选项），测试文件另写。

### ⚠ 另一个它没测到的细节，必须补上

`ws` 的 `threshold` 默认是 **1024**：

```js
// node_modules/ws/lib/permessage-deflate.js:56
this._threshold = this._options.threshold !== undefined ? this._options.threshold : 1024;
```

而补丁建议 `threshold: 64`。这不是可选项：

- **上下文保持开启时，threshold 被完全忽略**（`sender.js`：`rsv1 = byteLength >= _threshold` 只在上下文保持被关掉的那一侧生效）；
- 可一旦某个客户端协商成 `client_no_context_takeover`（部分代理/中间件会这么要求），threshold 就生效了，**1024 会把小帧放过去不压**。

补丁设 64 是对的，**保留它**，理由要写清（补丁注释里已经写了）。

### 建议做法

1. 采纳补丁改 `server/http/websocket.js`（`perMessageDeflate: { threshold: 64 }`）；
2. **补一档 level 设置**：实测 `level 3` 是性价比拐点（20.9 µs、50.2×），`level 6` 只多 6 µs 却换来 127×——如果带宽更紧张就上 6；
3. 加一条**真实字节数**的回归（像上面的 `_wire.mjs`），否则「哪天有人把它改回 false」没人会发现——补丁自带的测试只读握手串，**抓不到带宽回退**。

### 预期效果

| 场景 | 现在 | 打开后 |
|---|---|---|
| 100 客户端在线 | 2606 KB/s ≈ 20.8 Mbps | ~52 KB/s ≈ 0.4 Mbps |
| 单客户端 60 秒 | 152.7 MB（raw）| ~2.9 MB |
| 首次加载素材 | 不变（那是 HTTP 静态资源，本来就 gzip） | — |

**这是本仓库最大的一笔免费带宽**，且不改任何游戏逻辑。

## 四、第二梯队（按性价比排序）

### 1. `maxConnections: 2000` 是硬天花板 —— 要改也要配套改别的

```js
// server/net.js
maxConnections: 2000,        // 并发 socket，硬上限
maxConnectionsPerAddr: 64,   // 单个网络最多 64 个并发连接
maxSessions: 20_000,         // 会话登记表上限
maxRooms: 1000, maxRoomsPerAddr: 16, maxMatchesPerAddr: 8
```

⚠ **`maxConnectionsPerAddr: 64` 在移动网络下会误伤**：一个学校/公司/运营商的 NAT 出口会让很多真人共享同一个 IPv6 /64 或公网 IPv4，第 65 个连接被 **429 拒绝**。局域网内因为 key 为空反而不限。建议：

- 对**已经进过房间**的地址放宽到 128；
- 或者把「拒绝」改成「只对新房间拒绝，已在房间里的重连放行」。

### 2. 会话/房间是**纯进程内存** —— 决定了不能横向扩

```js
// server/net.js: SessionRegistry → this.byPlayerId = new Map(); this.byTokenMap = new Map();
// server/lobby.js: this.rooms = new Map();
```

没有共享存储、没有粘性会话层。所以：

- **不能**简单起多个 Node 进程做负载均衡——玩家会被随机分到没有他房间的进程；
- 真正的横向扩需要一个 **房间路由层**（按 room code 哈希到固定进程）+ 会话/房间外置，那是**大工程**；
- **短期正确做法**：垂直扩容（单进程吃满一个核 + 压缩把带宽打下来），而不是上集群。

这跟现在的**蓝绿部署**是同一个约束的两面：`sp-release.sh` 同时跑 A/B 两个槽，靠「等旧槽排空」而不是共享状态——所以扩容也不能绕开它。

### 3. `m.public` 每 100 ms 全量 —— 可做**增量下发**

单帧 2669 B 里绝大部分每帧不变。压缩已经把传输解决了，但**序列化 + 每个客户端一个有状态 deflate 流**仍是每客户端的固定成本（实测 1.6% 单核/100 客户端）。

如果将来要往 1000+ 客户端走，下一步是把 `m.public` 改成**脏字段增量**（服务端只发变化的键，客户端打补丁）。这一改动**碰协议**，要同步 `shared/protocol.js`、`docs/design/network.md` 和黄金结果，属于中期项。

### 4. `b.snap` 只在 `SP_COMBAT=server` 下产生 —— 别开这个模式

`SP_COMBAT=server` 让服务器跑所有战斗并推快照。实测一次真实作战 13.9 ms，若 100 个战场同时跑就是**单核 1.39 秒/回合**，必然卡死。**保持 `client` 默认**，压缩方案也是为它服务的。

## 五、我给并发者的建议（房间性能查看）

有人在做的「逐房间 CPU 占比」正好是扩容的**观测面**，方向对。两点提示：

1. `server/match/perf.js` 已经声明「只读时钟、不改变任何计算结果」，`measureOn` 在 owner 没有 `perf` 时直接透传——这个设计很好，**别为了统计去改调用点的语义**。
2. 面板的百分比是「**本线程墙钟占比**」，不是 OS 级 CPU；文档（DEPLOY.md §8.2）已经这么写了。**扩容决策要看的其实是带宽和房间数，不是这个百分比**——建议面板顺带显示每个房间的**下行 KB/s**（有了压缩之后它才是有意义的容量指标）。

## 六之二、P0 能不能在「有人在改服务器」时做？——**能，而且是当前最安全的一件**

2026-10-13 11:10 实测的并发态势：

| 核查项 | 结果 |
|---|---|
| 文件相交 | **不相交**。P0 只动 `server/http/websocket.js`（+ 新增一个测试文件）。并发者在 `server/match/**`、`server/admin.js`、`public/admin/**`、`test/{admin,match/perf}*` |
| 该文件是否被并发者写过 | **没有**。它的 mtime 是 **06:18:09**（0.2.5 合并留下的：给 `createSessionStack` 加 `contentPacks`），不是并发者的 10:18–10:24 窗口 |
| 语义耦合 | **没有**。`perMessageDeflate` 只作用于 `/ws` 帧；并发者的**整条链路是 HTTP**——`public/admin/admin.js` 用 `fetch` + `setInterval` 轮询，`test/admin.test.js`、`test/admin-rooms-perf.test.js`、`test/match/perf.test.js` 里 **WebSocket 引用数 = 0** |
| 测试端口冲突 | **不会**。全仓测试都用 `server.listen(0)`（随机端口），无固定端口 |
| git 冲突 | 无 `index.lock`；两边改的是不同文件，不会互相覆盖 |

**唯一的真实干扰是「同一时刻跑测试」**：并发者改的是对局引擎，跑 `node --test` 会同时吃 CPU；而且本沙箱里 `node --test` 多进程会 `spawn EPERM`（184 个测试文件用子进程），只能**逐文件**跑。建议：

- P0 改完后**只跑** `node test/net-compression.test.js`（新写的）和 `node test/client-static.test.js`、`node test/version.test.js` 这几个**不碰对局引擎**的；
- **不要**在对方正在跑对局测试时去跑 `test/match/**` 或 golden；
- 提交时**只 `git add` 那两个文件**——千万别 `git add -A`（工作树里有对方未完成的 260+ 个改动）。

### 还有一条：改完必须**通知**对方

`server/http/websocket.js` 是**共享**文件，虽然当前没人在写，但：一旦压缩打开，**所有** WS 流量的字节数都变了。如果对方之后要加「按房间统计下行字节」，他看到的数字会与今天不同。所以：

1. 改完在提交信息里写清「WS 传输层压缩已开启，m.public 从 ~2669 B 降到 ~42 B/帧」；
2. 把**本报告 §六之二**的内容转告他，特别是「面板该显示每房间下行 KB/s」那条——**那正好是他正在做的面板的下一步**。

## 六之三、P0 更新时，**服务器上的子民会怎样**（2026-10-13 实测）

> 结论：**P0 不重启进程、不切流、不打断任何对局。** 它比现在每天 4 点的自动更新**安全得多**。
> 但有两个**没人量过的代价**（内存 ×7、每连接一个 zlib 上下文），以及一个**部署门禁看不见的失败模式**。

### 1. 先看现在的更新会让玩家经历什么

`sp-release.sh` 的蓝绿流程（已从脚本逐行核实）：

```
1. 公告「服务器即将更新到新版本，进行中的对局会正常打完」   ← 让玩家有心理准备
2. 解包到空闲槽 → 起新槽 → curl /healthz 校验 build
3. 切 nginx upstream（改一行文件 + nginx reload）
4. 把开机自启交给新槽
5. 等旧槽排空（DRAIN_TIMEOUT=1800s；每 10s 轮询 rooms/matches/humans）
6. 排空才 stop 旧槽；超时就**不强杀**（宁可留着）
```

**关键：nginx reload 不切断已建立的 WebSocket。** 所以正在对局的人**在旧进程里打完**，期间不会有任何感知——这跟脚本注释 `# 旧槽上已建立的 WebSocket 不被切断` 一致。

**但有一个真实的断点**：旧槽最后被 `systemctl stop` 时，上面**还挂着的**连接会断。此时：

- 客户端有指数退避重连（`base 500ms, factor 2, max 10s, ±20% jitter`）；
- **重连会打到新槽**（`defaultWsUrl` 在**连接时**从 `location` 生成地址）；
- **座位保不住**：`SessionRegistry.byTokenMap` 和 `Lobby.rooms` 都是**进程内 Map**，新槽不认识旧 token → 玩家回到大厅，那一局作废。

所以现在的更新，**对局中的人可以打完；打完之前没结束、又恰好被 stop 到的人会丢局**。这就是「等排空」要等的原因——它把这种情况压到最小，但**排空条件是 rooms=0 && matches=0 && humans=0**，而一个刚打完的玩家会让 humans 变 0 却可能立刻又开一局，所以脚本给了 1800s 上限，超时就留着旧槽。

### 2. P0 会怎么改变这一切：**什么都不变**

P0 改的是 `server/http/websocket.js` 里的一个**启动选项**：

| 问题 | 答案 |
|---|---|
| 需要重启进程吗？ | **需要**（和任何服务端改动一样），但走的是**现有蓝绿流程**——不是原地重启 |
| 会切流吗？ | 会，但**和今天的自动更新走同一条路**：新槽起好 → 校验 → 切 upstream → 等旧槽排空 |
| 正在对局的人会怎样？ | **完全一样**：连接留在旧槽，打完为止，不受影响 |
| 比今天更危险吗？ | **不。风险完全等同**，因为用的就是同一条发布流水线 |
| 有额外风险吗？ | 有，**两个**，见下 |

**真正的新风险不在「更新时」，而在「更新后每个新连接」**——因为压缩是**每连接**的状态。

### 3. ⚠ 代价一：每个连接的 RSS 从 ~44 KB 涨到 ~237–313 KB（实测）

`permessage-deflate` 需要**每条连接**一个 deflate 上下文 + 一个 inflate 上下文。zlib 默认窗口 15 bits，光窗口和哈希表就是几百 KB 量级。

**实测（300 条并发 socket，`--expose-gc`，量 RSS 增量）：**

| 配置 | RSS/连接 | 相对关闭 |
|---|---|---|
| `perMessageDeflate: false`（现状） | **44 KB** | — |
| `{ threshold: 64 }` | **313 KB** | **+269 KB** |
| `{ threshold: 64, zlibDeflateOptions: { memLevel: 5 } }` | 284 KB | +240 KB |
| `{ threshold: 64, zlibDeflateOptions: { memLevel: 3 } }` | 258 KB | +214 KB |
| `{ threshold: 64, zlibDeflateOptions: { level: 3 } }`（**推荐**） | **237 KB** | **+193 KB** |

**换算到线上**（来自 `线上后台实况-20261013.md`：服务器总 **1613 MB**、当前每槽约 **157 MB**）：

| 同时在线 | 关闭压缩 | 开启（level 3） | 增量 |
|---|---|---|---|
| 200 连接 | ~9 MB | ~46 MB | **+37 MB** |
| 1000 连接 | ~43 MB | ~231 MB | **+188 MB** |
| 2000 连接（`maxConnections` 上限） | ~86 MB | ~463 MB | **+377 MB** |

⚠ **注意 `maxConnections: 2000` 与 1613 MB 内存是矛盾的**：真跑到 2000 连接，光压缩上下文就要 ~460 MB，加上房间/对局（每场约 2.2 MB）会逼近上限。**建议把 `maxConnections` 从 2000 降到与内存匹配的值（比如 600–800），并配 `--max-old-space-size`。**

**缓解**：`zlibDeflateOptions: { level: 3, memLevel: 3 }` 是性价比拐点——实测 50.2× 压缩、1.6% 单核/100 客户端，内存从 313 KB 降到 ~258 KB。**别用默认的 level 9。**

### 4. ⚠ 代价二：zlib 并发上限默认只有 10

`ws` 内部有个 `Limiter`（`node_modules/ws/lib/permessage-deflate.js`）：

```js
// We limit zlib concurrency, which prevents severe memory fragmentation
* @param {Number} [options.concurrencyLimit=10]
```

**默认同时只压 10 个连接**。超过的连接**排队**。对 100+ 在线、每 100ms 一帧的 m.public 广播，这意味着**排在后面的连接延迟会涨**。

- 实测广播频率是 **10 帧/秒/房间**，100 个连接就是 1000 次压缩/秒；
- 只有 10 个并发槽 → 队列会积压；
- 建议显式设 `concurrencyLimit`（例如 32–64），并观察 `perf` 面板的延迟。

**这一条恰恰是并发者的面板该显示的指标**（每房间下行 KB/s + 压缩队列深度）。

### 5. ⚠ 部署门禁看不见的失败模式（我实测复现了）

我上一轮转述补丁时说过「声明 `serverNoContextTakeover` 会 400」。**这轮我把每种组合都跑了一遍，把边界钉准了：**

| 服务端配置 | 客户端 | 结果 |
|---|---|---|
| `{ threshold: 64 }`（**推荐**） | 普通客户端 | OPEN ✓ |
| `{ threshold: 64 }` | 完全不要压缩的客户端 | OPEN ✓ |
| 服务端不声明 | 客户端 | OPEN ✓ |
| **`{ serverNoContextTakeover: false }`** | **客户端要求 `serverNoContextTakeover: true`** | **HTTP 400** ✗ |
| `{ serverMaxWindowBits: false }` | 客户端要求 `serverMaxWindowBits: 15` | **HTTP 400** ✗ |
| `{ serverNoContextTakeover: true }` | 客户端拒绝它 | OPEN ✓ |

**也就是说：只有「把某个值显式钉成 `false`」才会变成硬要求而 400。** 补丁说的是对的，但**触发条件比我上轮转述的更窄也更阴险**——它取决于**客户端 offer 了什么**，而不是服务端单方面。

**为什么这跟「子民会怎样」直接相关：**

```
发布脚本的校验全部是 curl /healthz      ← HTTP
发布脚本里没有任何一处开 WebSocket        ← 已核实：12 个脚本，零 ws 验证
```

**HTTP 200 不等于玩家连得上。** 一旦这里出问题：

- 部署门禁会**通过**（`/healthz` 正常返回）→ 流量被切到坏槽；
- 玩家看到的是「**连接中断，正在重连**」（`title.js:188`）**无限循环**——客户端会一直退避重试，但每次握手都被 400；
- **旧槽此时已经被 stop 或正在排空**，回滚窗口只有 `--rollback` 那一次机会。

**这就是 P0 唯一真正的「子民受害」场景，而且恰好是现有流程抓不到的。**

### 6. 所以 P0 落地时，必须加这三道保险

1. **手改，不要 `git apply`**（原补丁文件已损坏，见 §三）。
2. **配置写最保守的一版**：`perMessageDeflate: { threshold: 64, zlibDeflateOptions: { level: 3, memLevel: 3 }, concurrencyLimit: 32 }` —— **绝不声明** `serverNoContextTakeover` / `serverMaxWindowBits`（连 `false` 都别写）。
3. **给发布脚本加一次真实 WebSocket 校验**（这是本次审查发现的**真缺口**，与 P0 是否落地无关）：

```bash
# 切流后、判定成功之前，必须真开一次 WS：
node -e "
const {WebSocket}=require('/opt/Stronghold-Protocol-b/node_modules/ws');
const w=new WebSocket('ws://127.0.0.1:3001/ws');
w.on('open',()=>{console.log('WS OK');process.exit(0)});
w.on('error',e=>{console.error('WS FAIL',e.message);process.exit(1)});
setTimeout(()=>{console.error('WS TIMEOUT');process.exit(1)},8000);
" || die "新槽 WebSocket 握手失败 —— 不上线"
```

**没有第 3 条，就不要上 P0。** 现在的流程能承受「HTTP 好、WS 坏」的代价吗？不能——那正是全员连不上的场景。

### 7. 一句话回答

> **P0 更新时，子民和今天一样：在旧槽把对局打完，只有恰好被 stop 到的会丢局。**
> **P0 的危险不在更新那一刻，而在更新之后——内存 ×5–7、每连接一个 zlib 上下文、并发上限 10，以及一个只有 WebSocket 才能发现的 400 拒绝模式，而现在的发布脚本从不测 WebSocket。**

## 六之四、加了门禁之后，P0 现在如何（2026-10-13 12:1x 实测）

> 一句话：**门禁已经装好，并且我在这一轮把它补强了两处**——原来那版**抓不到 P0 自己的两个陷阱配置**。
> P0 本身仍然**没有落地**（按你的指示先修更基础的），但**现在落地的风险已经从「部署门禁看不见」降到「可测、可拦」**。

### 1. 门禁现状（`05-部署/sp-release.sh`）

位置在**切流之前**（3b 步）：握手不过就不切，线上保持原样，并顺手把新槽停掉。

### 2. ⚠ 本轮发现并修掉的两个缺口

#### 缺口 A：原来那版门禁**抓不到 P0 的两个陷阱**

上一轮我加的门禁用 `new WebSocket(url)`（不带任何选项）当客户端。这一轮实测发现：

| 服务端配置 | 旧门禁判定 | 应该 |
|---|---|---|
| P0 推荐 `{threshold:64, level:3}` | PASS | PASS ✓ |
| **陷阱 `{serverNoContextTakeover:false}`** | **PASS（漏！）** | 拦住 |
| **陷阱 `{serverMaxWindowBits:false}`** | **PASS（漏！）** | 拦住 |

**原因**：那个客户端**不提出任何扩展要求**，服务端声明的 `false` 就**没有冲突可言**，所以不会 400。
真正触发 400 的是一个**明确要求** `server_no_context_takeover` / `server_max_window_bits=15` 的客户端
（中间代理或旧浏览器可能这么提）。

**修法**：门禁改成跑**两个**客户端——普通客户端 + **挑剔客户端**（后者才是陷阱探测器）。逐字抽取运行验证：

```
P0 recommended {threshold:64,level:3}    exit=0  ✓  "WS OK (plain + picky, deflate negotiated)"
off (baseline)                           exit=0  ✓  "WS OK (plain + picky) — note: deflate NOT negotiated"
TRAP serverNoContextTakeover:false       exit=1  ✓  "picky: HTTP 400"
TRAP serverMaxWindowBits:false           exit=1  ✓  "picky: HTTP 400"
dead port                                exit=1  ✓  "plain: FAIL connect ECONNREFUSED"
```

#### 缺口 B：P0 的核心价值（压缩本身）**没人看得见**

即使 P0 上线了，**哪天有人把 `perMessageDeflate` 改回 `false`**，部署会**静默通过**——98% 的带宽白丢。

**修法**：门禁现在**总是报告**是否协商到 `permessage-deflate`，并提供一个开关：

```bash
SP_REQUIRE_DEFLATE=1   # P0 上线之后设上：压缩没协商到就拒绝发布
```

**默认不强制**，因为**今天 P0 还没上线**——强制会让**当前每一个 build 都发布失败**。这个默认值是刻意的。

两条分支都实测过：

```
deflate OFF + SP_REQUIRE_DEFLATE=1 → exit=1 "deflate NOT negotiated ... refusing"
deflate ON  + SP_REQUIRE_DEFLATE=1 → exit=0 "WS OK (plain + picky, deflate negotiated)"
```

### 3. 所以 P0 现在的状态

| 项 | 状态 |
|---|---|
| P0 是否已落地 | **没有**（按你的指示先修更基础的） |
| 落地后的「全员连不上」风险 | **已被门禁覆盖**（两个陷阱配置都会在切流前被拦下） |
| 落地后「被悄悄改回去」的风险 | **可被覆盖**（设 `SP_REQUIRE_DEFLATE=1` 即可） |
| 还差什么才能上 P0 | ① 改 `websocket.js`（`{threshold:64, zlibDeflateOptions:{level:3, memLevel:3}, concurrencyLimit:32}`）② 加真实字节数回归测试 ③ 上线后设 `SP_REQUIRE_DEFLATE=1` |
| 仍然没人量的 | 每连接内存（实测 +193 KB/连接，见 §六之三）与 `concurrencyLimit` 默认 10 的排队延迟 |

> **结论**：门禁从「只能证明 HTTP 活着」升级到「能证明 WS 真的能连、且能盯住压缩开关」。
> P0 不再是「部署门禁看不见的风险」，而是一个**改一处选项 + 设一个环境变量**就能安全上线的改动。
