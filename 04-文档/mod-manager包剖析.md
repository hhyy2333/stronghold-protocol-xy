# mod-manager 包剖析：一个真正的 Forge 客户端包

> 对象：`参考对象\mod-manager\mod-manager`（3 个文件：`pack.json` + `ui/manager.js` 229 行 + `ui/manager.css` 66 行）
> 对照：`Stronghold-Protocol-repo`（业主 0.3.0 分支）
> 本文只做剖析，**不含任何代码改动**。

---

## 0. 一句话

**这是一个「给模组做开关」的模组**——它自己不贡献任何内容（`pack.json` 里没有 `content`、没有 `server`、
没有素材），只做一件事：**把引擎已经存在的那份「本房间声明了哪些包」状态，画成一个能点的浮层**。

它是**验证我前面所有分析的活样本**：一个真实的第三方包，只用了 Forge 已声明的表面，
**没有新增任何引擎端口**，而且**刻意不碰 store、不改对局**。

---

## 1. 它长什么样

### 1.1 `pack.json`（全文 30 行）

```json
{
  "id": "mod-manager",
  "name": "模组管理",
  "version": "1.0.0",
  "author": "the mod-manager mod",
  "description": "…",
  "client": {
    "panels": [{
      "id": "manager",
      "slot": "root.overlays",
      "module": "ui/manager.js",
      "styles": ["ui/manager.css"],
      "wraps": [
        { "component": "lobby.modManager", "mode": "wrap" },
        { "component": "lobby.modPicker", "mode": "wrap" },
        { "component": "room.modManager", "mode": "wrap" }
      ]
    }]
  }
}
```

**注意它没有的东西**：没有 `content`、没有 `server`、没有 `assets`、没有 `routes`、没有 `combat`、
没有 `api`、**没有 `layer`**。它连 `gameVersion` 都只是元信息。

**它有的只有 `client.panels`** —— 即我基线报告里那一格 C 层表面。

### 1.2 三个组件改写（`wraps`）

一个模块，三条链，靠 `ctx.component` 区分这一帧自己在哪条链上：

| 改写的引擎组件 | 位置 | 做了什么 |
|---|---|---|
| `lobby.modManager` | 大厅顶栏「干员调配」左边 | 画「模组管理」按钮 + 浮层（一行一个模组、右边一个开关）。**这里能改** |
| `lobby.modPicker` | 大厅创建框里**旧的**「本房间使用的模组」列表 | **把它收走**：返回的树里**不放 `orig`** ⇒ 那张列表不再出现（内容已搬进上面的浮层） |
| `room.modManager` | 房间顶栏「玩法说明」右边 | **只读**：集合在 `room.create` 那一刻就定死，所以只列「这一局跑哪几个包」，**不给开关** |

**第二条最值得看**：它演示了 `mode: "wrap"` 的**减法**用法——不渲染 `orig` 就是「把这个界面收走」。
这不是替换一个组件，是**把引擎的一块 UI 拆掉**。

---

## 2. 它证明的三件事

### 2.1 状态不在包里（这是设计的核心）

文件头原文：

> **状态不在包里**：`available`（服务器声明了哪些包）/ `selected`（本房间点名了哪些）/ `onSet`（那一份点名的
> **唯一写入口**）全都是引擎这一帧交给链的 props。**包只画，不改对局、不碰 store**。

**三条口径**（都来自引擎，不是包自己发明的）：

1. **空 `selected` = 全选**：「本房间没声明集合」与「声明了全部」在服务端**是同一件事**，
   所以开关**默认全开**；要点名一个子集就**先展开**（`expanded()`），于是**每一次点击都是它字面上的意思**。
2. **不列出自己**：关掉本包 = 把这套界面一起关掉（`ctx.pack` 就是自己），所以它**只参与状态判定、不进清单**。
3. **「全部停用」= `onSet([selfId])`**：只点名自己一个包 ⇒ 这一局只物化管理器那份（它不贡献数据），
   其余模组一律不生效。它与「把下面每一个都关掉」**是同一个状态**，默认关闭。

> **这三条是「包只有视图、没有状态」的最佳示范。** 包拿到的是**只读快照 + 一个写入口**，
> 而**语义（空=全选、不含自己）由引擎定**，包只是把它画出来。

### 2.2 它不新增任何引擎端口

README 里那张表是**自证的**：

| 用到的能力 | 说明 |
|---|---|
| 面板挂载槽 `root.overlays` | 引擎已声明的九个宿主之一 |
| 组件改写 `lobby.modManager` / `lobby.modPicker` / `room.modManager` | 引擎**已具名**的组件 |
| 改写链的 `props` | `available` / `selected` / `onSet` 都是引擎给的 |
| `roomMods.js → room.create.modIds` | 状态由引擎保管，包只读它的投影 |

**「一个组件只能被同一个面板改写一次」**——这是引擎侧的约束，包自己遵守。

### 2.3 它碰了两个真实的工程细节

**① htm 的 vnode 缓存陷阱**（第 32-40 行）：

> htm 会把**全静态**子树缓存进模板对象里，而 Preact 挂载时会把 DOM 节点与父链写进那个共享 vnode ——
> 屏幕卸载之后模块级缓存还指着旧 DOM。`this[0] = 3` 是 htm 的 opt-out。

于是它自己定义了一个 `hFresh` 绑定。**这不是包的问题，是引擎的 `components.js` 早就踩过同一个坑**
（注释里点名 `hFresh`）。⇒ **一个第三方包会重新踩引擎踩过的每一个坑，除非引擎把解法写进文档。**

**② 改写拿不到引擎的 `t()`**（第 43-45 行）：

> 数据层/逻辑层/客户端（引擎 `screens/lobby.js LAYER_TEXT` 的同一张表：**改写拿不到引擎的 `t()`，这里照抄一份**）。

于是它自己抄了一张 `LAYER_TEXT = { A: '数据', B: '逻辑', C: '客户端' }`。

> ⚠️ **这是这一层的一个真实缺口**：面板有 `ctx.me`、有 `ctx.net`，但**没有 i18n 入口**，
> 所以一个中文界面包只能**硬编码中文**（这个包就是这样：`'模组管理'`、`'全部停用'` 全是字面量）。

## 3. 与业主这棵树的关系：**完全不能用**

我逐项核对过，这个包需要的**每一格**，业主这棵树都没有：

| 它需要的 | 业主这棵树 | 证据 |
|---|---|---|
| `client.panels` 声明 | **无** | 全仓 `client.panels` = **0 命中** |
| 九个面板宿主 | **无** | `MOD_PANEL_SLOTS` / `data-mod-slot` = **0 命中** |
| `wraps` 组件改写 | **无** | 全仓 `wraps` 只有无关的英文注释 |
| 组件 `lobby.modManager` / `lobby.modPicker` / `room.modManager` | **不存在** | `modManager` / `modPicker` = **0 命中** |
| `/workshop-panels/` 路由 | **无** | `workshop-panels` = **0 命中** |
| `/mods/catalog.json` | **无** | `mods/catalog` = **0 命中** |
| `server/roomAssets.js`（按房间物化） | **无** | 文件不存在 |
| `room.create.modIds`（房间点名集合） | **无** | `modIds` = **0 命中** |

**结论：这个包在业主这棵树上连「装上去报个错」都做不到——它需要的每一格表面都不存在。**

## 4. ⚠️ 一个必须澄清的**同名不同物**

这个包叫「模组管理」，而业主这棵树**也有一份「额外内容」的开关界面**（`public/js/ui/mods.js`，134 行）。
**两者名字像，概念完全不同**：

| | Forge 的 `mod-manager` 包 | 业主的「额外内容」（`ui/mods.js`） |
|---|---|---|
| 管理的是什么 | **工坊包**（`workshop/<id>/`，第三方投稿） | **内容 mod**（`shared/mods.js MODS`，**随 build 提交**） |
| 数量 | 任意（服务器声明的全部包） | **2 个**（`custom-ops`、`custom-fixed`） |
| 状态在哪 | 引擎的 `roomMods.js`（每帧 props） | 引擎的 `store`（`ui/mods.js` 自己读写） |
| 实现方式 | **第三方包**，靠 `client.panels` 挂载 | **引擎自己的界面**（`ModsHost` 由 `main.js` 挂一次） |
| 作用域 | 每房间声明一个**子集**（`room.create.modIds`） | 每房间开关（`room.setMods`） |

**关键差异**：Forge 的 mod 是**装上去的第三方产物**；业主的 mod 是**编译进 build 的可选内容**。
所以：

> **业主已经有「按房间开关内容」这条链（`room.setMods` + `filterData` + `额外内容` 窗口），
> 它缺的不是「管理界面」，而是「被管理的东西」——即「可安装的第三方包」。**

而 mod-manager 这个包**恰恰只解决「界面」那一半**：它管的是**已经装好的包**。
**它不能帮你装包，也不能让业主这棵树支持装包。**

## 5. 它对我的建议有什么影响

我在[Forge包能否直接用-实测.md](Forge包能否直接用-实测.md) 里建议「写一个清单翻译器，把 Forge 的内容包导进来」。
这个包**不改变那个结论**，但它**印证了两件事**：

### 5.1 印证了「内容面」与「界面面」是分开的两条路

mod-manager **一个字节的内容都没有**——它纯粹是界面。这说明 Forge 的生态里：

- **内容包**（`content` + 数据文件）→ 我实测过，**改清单能导进业主这棵树**；
- **界面包**（`client.panels` + `wraps`）→ **完全导不进来**，因为业主这棵树**没有面板宿主这一层**。

⇒ 我那句话要说得更准：**「能用同一个内容生态」是真的，但只限内容包；界面包是另一条线，需要先建 C 层表面。**

### 5.2 印证了「包只有视图」这条边界是**可用的**

这个包**不碰 store、不改对局、只读 props**——而它做到了一个**功能完整**的管理界面。
这说明 Forge 那条「`ctx` 里没有 store」的边界**不是残缺，是够用的**。

> **对业主的意义**：如果将来要给这棵树加包管理界面，**不必**开一个 store 句柄给第三方包。
> 照 mod-manager 的形状：**引擎把状态投影成只读 props + 一个写入口，包只画。**

## 6. 结论

1. **它是一个真实、完整、克制的 Forge 客户端包**——3 个文件，只声明 `client.panels` 一格表面，
   靠三条组件改写把「本房间声明了哪些包」画成一个可点的浮层。
2. **它演示了三条口径**（空=全选、不列自己、全部停用 = 只点名自己），
   而这三条**都由引擎定**，包只负责画。**这是「包只有视图」的教科书样本。**
3. **它在业主这棵树上完全不能用**：需要的八格表面**一格都不存在**。
4. **⚠️ 别被名字骗了**：业主自己的「额外内容」窗口管的是**随 build 提交的内容 mod**（2 个），
   这个包管的是**第三方工坊包**。**两者同名不同物。**
5. **它印证了我的建议的边界**：内容包**可以**导进来（实测过），界面包**不行**——
   那是业主这棵树**根本没有 C 层表面**，不是翻译清单能解决的。
6. **一条可借鉴的设计**：如果将来要做包管理界面，**照它的形状**——
   引擎投影只读 props + 一个写入口，**不要给第三方包 store 句柄**。

## 附：它暴露的两个真实缺口（值得记下）

| 缺口 | 现象 | 影响 |
|---|---|---|
| **改写链拿不到 `t()`** | 包只能硬编码中文（`'模组管理'` / `'全部停用'`） | 一个多语言引擎里的中文界面包**无法本地化** |
| **htm 的 vnode 缓存** | 引擎 `components.js` 已用 `hFresh` 解决，但**文档没把这个坑写给包作者** | 每个新包都会重新踩一遍 |

> 这两条是**包生态的真实摩擦**——不是设计缺陷，是**文档缺口**。
> 一个健康的 mod 层会把「引擎踩过的坑」写进作者文档，而不是让每个第三方包自己发现。
