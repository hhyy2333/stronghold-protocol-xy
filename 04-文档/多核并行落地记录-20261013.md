# 多核并行落地记录 · 2026-10-13

> 目标：让服务器用上第二颗 CPU 核，从而承载更多玩家。
> 状态：**已实现并验证可用**，但**默认关闭**（`SP_SIM_WORKERS` 未设置时行为与今天逐字节相同），**尚未上线**。

## 一、问题回顾（实测）

线上 2 vCPU / 1.6 GB，**主线程 p99 = 97.8%、峰值 101.2%**（30 真人 / 19 bot），第二颗核基本闲置。
CPU 去向（线上 `perf.buckets`）：

| bucket | 占比 | 性质 |
|---|---|---|
| **bots** | **58.3%** | bot 休整期摆阵排练（每方案跑一整场战斗） |
| serverRun | 20.5% | 服务器替无真人战场跑战斗 |
| core / views / intents | 21.2% | 阶段机、视图、消息 |

**78.8% 是战斗模拟**——这决定了做法：不并行整个服务器，只把「跑战斗」搬出去。

## 三、实现

| 文件 | 作用 |
|---|---|
| `server/match/simPool.js` | 常驻 worker 池：任务队列、背压、失败降级、优雅关闭 |
| `server/match/simPoolWorker.js` | worker 半边：加载一次数据，把 spec 跑成结果 |
| `server/match/bot.js` | 排练构建 specs + `job.runAsync()`（**不改 `run()`**） |
| `server/match/match/prep.js` | 有池走 async 分支，否则原样走切片路径 |
| `server/match/Match.js` | `this.simPool`（缺省 null） |
| `server/lobby.js`、`server/index.js`、`server/http/config.js` | 池的创建、传递、关闭 |
| `test/match/{simPool,spec-parity}.test.js` | 回归测试 |

### 关键设计

- **默认关闭**：`this.simPool = null` → `runAsync()` 返回 null → 完全走原路径。所以 `npm start`、所有测试、所有 golden 场景行为不变。
- **全有或全无**：`runAsync()` 只在**全部**候选都被池接受时才用池；否则整体退回内联。**两者绝不混用**，所以选出的方案不可能依赖池的时序。
- **失败只损失 CPU，不损失正确性**：worker 死了 → `task.fail()` → 调用方拿到 null → 退回内联重跑。
- **不阻塞进程退出**：idle worker `unref()`，有任务时 `ref()`。

### 途中修掉的三个真 bug（都是我自己的）

1. **`unref()` 让任务 Promise 永不 settle** —— 一个进行中的任务不再保持事件循环存活。修法：idle 时 unref、busy 时 ref。
2. **`_onMessage` 只透传 `result`**，丢掉 `ticks`/`ms`/`leaks`。修法：整包透传。
3. **`close()` 不 settle 进行中的任务** —— 只处理了队列里的，正在跑的会永久挂起。修法：in-flight 也 `fail()`。这条是**新写的测试抓出来的**。

## 四、实测效果

同一场真实对局（1 真人 + 3 bot，HARD，真战斗，`botRehearsal: 3`）：

```
无池  : 主线程内耗时 9730 ms
2 workers: 主线程内耗时 6049 ms   → 主线程阻塞减少 38%
offloaded: 66 次排练，5852 ms 的 CPU 被搬到 worker
结果一致: YES ✓
```

小规模对比（4 场战斗）：

```
主线程内联 : 170 ms（主线程全程阻塞）
2 workers  : 118 ms（主线程空闲）
```

**注意**：`process.cpuUsage()` 会把所有线程算在一起——offload 后**进程总 CPU 反而略升**（同样的活 + 传输），
**降下来的是主线程**，那才是卡玩家的那个量。这是唯一有意义的指标。
