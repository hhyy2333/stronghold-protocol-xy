# 网络优化：Forge 0.18.6 vs 本仓（0.2.6 在制）

> 问题：**Forge 有网络优化吗？**
> 答案：**有，而且很扎实。但更重要的是——本仓已经做了同一批工作的绝大部分，只差一块。**
> 对象：`参考对象\Stronghold-Protocol-Forge-0.18.6-0.2.6-win-x64` vs `Stronghold-Protocol-repo`
> 本文只做对照，**不含任何代码改动**。

---

## 0. 一句话

**Forge 的网络优化 = 三层。本仓已经有了第 0、1 层（正在制的 0.2.6），缺的是第 2 层「增量帧」。**
而**缺的这一块，恰好是收益最直接、也最独立的一块**——它只动服务端与一个客户端合并模块，不碰游戏规则。

## 1. 逐项对照

| 优化项 | Forge 0.18.6 | 本仓（0.2.6 在制） |
|---|---|---|
| **permessage-deflate** | ✅ 开（threshold 1024） | ✅ **开**（threshold **64**） |
| **内容哈希 URL + 长缓存** | ✅ | ✅ `server/http/assetIndex.js` + `assetViews.js` |
| **brotli** | ✅ | ✅ `server/http/files.js`（quality 5） |

**结论：八项里本仓有六项。** 差的正是「增量帧」那一块。

## 2. Forge 的增量帧：它到底做了什么

### 2.1 机制（DESIGN §8.2.1 / 0.15.0 changelog）

`m.public` 从「每次变化发整张表」改成 **「第一帧全量 + 之后按字段增量」**：

- 服务端保留一份**全房间共享的基线**（`_pubPrev`）；
- 只发**变了的顶层键**（`gone: [...]` 列出消失的键）、**变了的玩家行字段**、**变了的战场条目**；
- 客户端 `public/js/matchDelta.js`（177 行）把增量合并进自己的物化状态 ⇒
  **下游（store、各界面）读到的仍是一份完整的 `m.public`，看不到增量**。

**为什么**（changelog 原文）：

> 40 座房间里每帧重发 40 行是 **O(座位数 × 字段数)** 的载荷，而单客户端收包的绝大部分就是它。
> 字段级增量让帧的大小只随**真正变化的字段数**增长。

### 2.2 验收点：**语义不变**

> 客户端把增量合进自己那份物化状态后，与全量帧**逐字段相同**。
> 真对局的帧流走浏览器自己的合并再与全量帧对比，**4 座与 40 座各一遍**。

### 2.3 重置点（下一帧必为全量）

首帧 · 任何成员变化（加入/离开/断线/重连/观战者）· 某次广播没送到所有 socket ·
每 32 个连续增量帧的**保活**。

⇒ 所以**新加入者 / 重连 / 观战者先收到全量再收增量**。

### 2.4 自愈：两条独立的路

| 路 | 机制 |
|---|---|
| **服务端保活** | 每 32 个连续增量帧后强制一帧全量（无需客户端配合） |
| **客户端自救** | 合并不了时**不半途应用**，发 `g.publicFull` 要一份全量 |

最坏窗口（设计稿给的算式，不是拍脑袋）：

```
t_throttle  = 100 ms
W_keepalive = 32 × 100 = 3200 ms
W_ask       = 2000 + RTT + ε
W_worst     = max(3200, W_ask) + RTT ≈ 3.2 s + RTT
```

### 2.5 ⚠️ 它顶了 `PROTOCOL_VERSION` 1 → 2

判据只有一条：**「推送帧的形状变了，而且一个不会合并的旧页面会把它读错」才顶。**

> 没有合并逻辑的页面会把增量帧的 `players` 当成整份名册读 —— **不是「值旧了」，是人数与名册显示错**。

代价是**所有陈旧标签页在握手时被拒**（刷新一次）。设计稿的立场：

> **不确定时，顶号的代价更小。**

### 2.6 它自己记下的坑（很诚实）

- **`SCALAR_KEYS` 是隐式契约**：新增一个**顶层**字段却忘了登记，它的变化**不会**进增量帧，
  客户端一直读旧值，**而且没有任何测试会因此变红**。行内字段没白名单，改了就自动进 diff
  ⇒ **「行内加字段」安全，「顶层加字段」不安全。**
- **`gone` 与 `null` 不能弄反**：顶层 `null` 是**真值**，「键消失」必须走 `gone`；行内 `null` 才是「键没了」。
  弄反会出现「客户端状态与服务端基线永久不一致」，表现为**每 2 秒要一次全量、房间被反复打成全量帧**。
- **`g.publicFull` 必须限流**：一次请求买到的不是回包，是**一份单播全量帧 + 整个房间下一帧也变全量**。
  放进重负载桶后：40 座房间一份全量帧 **17,282 B**，从「第一秒最多 40 × 17 kB ≈ 680 kB」
  降到「稳定 2 × 17 kB ≈ 34 kB/s」。

## 3. 本仓已经有的（0.2.6 在制，且**参数不同**）

### 3.1 本仓的 deflate 调优**与 Forge 不同**，而且有实测依据

| | Forge | **本仓** |
|---|---|---|
| `threshold` | 1024 | **64** |
| `serverNoContextTakeover` | `true` | **未设**（即允许 context takeover） |
| `serverMaxWindowBits` | 11 | **未设** |
| `zlibDeflateOptions` | `memLevel: 7` | `level: 3, memLevel: 3` |

本仓代码注释里的理由（`server/http/websocket.js`）：

> Upstream 0.2.6 took the opposite route (threshold 1024 + `serverNoContextTakeover` + `serverMaxWindowBits: 11` …).
> **This tree keeps the measured tuning above: context takeover is what carries the ~99 %-identical `m.public` stream**,
> and declaring a window would turn every such client into a **refused handshake** instead of a degraded one.

**这一条值得注意**：本仓选择**保留 context takeover**——因为 `m.public` 帧流**逐帧 99% 相同**，
而 context takeover 正是吃这 99% 的那件事。Forge 关掉它（`serverNoContextTakeover: true`）是为了省内存
（每条连接约 72 KB zlib state），但**牺牲了跨帧压缩率**。

⇒ **本仓的 deflate 设置对自己的流量特征可能更优**，而且有测试钉住（`test/net-compression.test.js`）。

### 3.2 本仓的实测数据（0.2.6 history §31.3）

| session | WebSocket (server → client) |
|---|---|
| before, music on | 163–179 KB（无压缩） |
| **after, music on** | **60 KB on the wire（173 KB payload）** |
| before, muted | 165 KB |
| **after, muted** | **57 KB** |

**单人对局：173 KB → 60 KB（约 −65%）。** 这是**压缩**的收益，不是增量的。

## 4. 所以差的这一块值多少

增量帧省的是**另一笔账**：

- **压缩**省的是「每帧的字节数」（本仓已有）；
- **增量**省的是「**帧里有用的字节比例**」——40 座房间里每帧重发 40 行，其中**变化的可能只有 1-2 行**。

Forge 的立场（changelog）：**40 座房间里，单客户端收包的绝大部分就是这 40 行**。

**对本仓的含义**：

| 场景 | 增量帧的收益 |
|---|---|
| **单人对局**（本仓主场景） | **小**——只有 1 行，本来就不大 |
| **4 人同盟** | **中** |
| **20 座大房**（本仓已支持） | **大**——这正是 Forge 做它的理由 |

⇒ **如果本仓主要是单人或 4 人，增量帧的收益有限；如果要推大房，它才变成必需。**

## 5. 如果要做，成本与风险

### 5.1 成本

Forge 的实现规模（可直接参考）：

| 文件 | 行数 | 作用 |
|---|---:|---|
| `server/viewsDelta.js` | 327 | 服务端 diff |
| `public/js/matchDelta.js` | 177 | 客户端合并 |
| `server/match/match/messaging.js` | 改动 | 接进发送路径 |
| `server/match/match/common.js` | 加 `PUBLIC_FULL_EVERY` | 保活计数 |

**约 500 行新代码 + 若干接线**。而且要配套：

- `g.publicFull` 新 C2S 意图 + 放进 `HEAVY_TYPES`；
- `SCALAR_KEYS` 白名单（**本仓的 `m.public` 字段与 Forge 不同，要重新列**）；
- 客户端`store.patch` 改成走合并器；
- **顶 `PROTOCOL_VERSION`**（本仓现在是 1，要顶到 2）。

### 5.2 风险（Forge 自己记下的，逐条适用）

1. **`SCALAR_KEYS` 漏登记 = 静默失效**，而且**没有测试会红**——这是最阴的一条；
2. **`gone` / `null` 弄反 = 房间级全量帧风暴**；
3. **`g.publicFull` 不限流 = N 个客户端 × 17 kB 全量帧**；
4. **顶号 = 所有旧标签页被拒**（刷新一次）。

### 5.3 ⚠️ 与本仓现状的冲突

**本仓现在有 410 项未提交改动、48 条测试红、6 个真实缺陷。**
增量帧要动 `server/match/match/messaging.js` 与 `public/js/main.js`——**都是移植必撞的文件**。
**在这个基线上做它，你会分不清坏的是增量帧还是旧账。**

## 6. 回答

> **「Forge 有网络优化吗？」**

**有，三层都做了**：压缩（deflate）· 传输（内容哈希 + 长缓存 + brotli）· **协议（增量帧）**。

> **「本仓缺什么？」**

**只缺第三层「增量帧」**。前两层本仓**已经在制的 0.2.6 里做了**，而且 deflate 参数是**自己实测调过的**
（保留了 context takeover，理由是 `m.public` 逐帧 99% 相同）。

**并且本仓已经有一份 Forge 没有的东西**：`docs/history/0.2.6.md` §31 的**逐项实测表**
（含「一个真人从 round 3 到结果」的 host 总字节分解）。

## 7. 建议

| 选项 | 内容 | 我的看法 |
|---|---|---|
| **A** | **不做增量帧**，先把 0.2.6 收干净（清 48 条红 + 提交） | **推荐先做这个** |
| **B** | 清干净之后**只做增量帧**（抄 Forge 的 `viewsDelta` 结构，`SCALAR_KEYS` 按本仓 `m.public` 重列） | 若目标是**大房**，值得做 |
| **C** | 连 `g.publicFull` 自愈一起做 | 与 B 同批，别拆 |
| **D** | 抄 Forge 的 deflate 参数 | **不要**——本仓的参数有实测依据，Forge 的是为省内存 |

**我的判断：增量帧是「大房」的配套，不是「通用优化」。**
本仓如果主要是单人和 4 人，**它的收益不如把 0.2.6 收干净**；
如果要推 20 座，**它就是必需项**——而且 Forge 已经把那 327+177 行、以及四条踩坑记录都写好了，
**照抄结构、按本仓字段重列白名单**即可。

## 附：Forge 那份文档值得学的两点

1. **`docs/NET-TUNING.md` 是一份「可调参数说明书」**——每条都带 `文件:行`、上游原值、改大改小的后果，
   而且**没实测过的数字都标了「未证实」**。**这种诚实度值得抄。**
2. **最坏窗口是算出来的，不是拍的**：`W_worst = max(W_keepalive, W_ask) + RTT`，
   并且明说「静默期不产生增量帧，保活计数不推进——**这是有意的**，因为静默期客户端手里的状态本来就没落后」。
