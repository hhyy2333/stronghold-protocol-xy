# 协议源石转 Forge：两种 mod，我上一轮漏了第二种

> 你问：**Forge mod 不能改那四个硬阻塞吗？**
> 答：**能——但那是另一种 mod。** 我上一轮只验了「工坊包」，漏了「就地补丁式 mod」。
> 本文补齐，并给出两条路各自的真实代价。

---

## 0. 先认错

我上一轮说「路线 A 死了」，**那个结论只对工坊包成立**。
Forge 自己在 `docs/MOD-SURFACE.md` 里把 mod 分成**两类**，我读到了那段却**没有把它纳入分析**：

> **就地改动引擎文件**：`shared/protocol.js`、`shared/constants.js`、`server/lobby.js` 这类补丁式分发产物
> **不是表面**，是**发行工件**（社区 mod 的 `*.patch`）。

**「不是表面」≠「不能改」。** 它的意思是：**这类改动不走工坊包的校验器，直接改引擎文件。**

---

## 1. 两种 mod 的真实分工

| | **工坊包**（workshop pack） | **就地补丁式 mod**（patch mod） |
|---|---|---|
| 形态 | `workshop/<id>/` + `pack.json` | 一个 `install.mjs` + 文件清单 |
| 改什么 | 只能填引擎**挖好的格子** | **整份覆盖引擎文件** |
| 校验 | 过 Forge 的校验器（闭集、点名拒绝） | **不过**；靠 sha256 基线白名单 |
| 四个硬阻塞 | ❌ **碰不到** | ✅ **随便改** |
| Forge 的态度 | 官方支持 | **明确「不采纳」为投稿形态** |

**所以：四个硬阻塞对「工坊包」是死的；对「补丁式 mod」根本不构成障碍。**

## 2. Forge 对补丁式 mod 的真实态度（实测 CHANGELOG）

Forge 收到过一个真实投稿 `ac8c9821f5ba`（「跨版本一键安装包」），它就是补丁式 mod：

> `install.mjs`（43,658 B）按 `files.json` 的 `copy` 清单**整份覆盖** `data/{chess,config,items,official,skins}.json`、
> `server/**` 48 个文件（含 `server/sim/**` 22 个）、`public/**` 五十余个…… 它自己的 `files.json` 把语义写得很直：
> **「Nothing is trimmed: a target that gets the whole file gets the whole feature」**。

**Forge 的裁决**：

> **改动 / 未采纳**：**不采纳安装器**（`install.mjs` + `一键跨版本安装.bat`）、**不采纳整包 `payload/` 上架**、
> **不采纳**对 `data/*.json` / `server/sim/**` / 整屏 UI / `tools/**` 的**整份覆盖**语义……
> 但**整份覆盖**这条语义本身正是本刀要拦的形态。
> **收成引擎里两格实现好的开关**（DESIGN §28.43.1）。

**读法**：Forge **不禁止**你这么做（技术上完全可行），但它**不会把这种形态收进自己的发行体系**，
而是把「效果」重新实现成引擎的**开关**。

## 3. 四个硬阻塞，两种 mod 的对照

| 硬阻塞 | 工坊包 | 补丁式 mod |
|---|---|---|
| `KEY_RE` 没有 `hex` | ❌ 抛错 | ✅ **直接改 `server/match/effectsMeta.js` 一行** |
| `onHexPick` 无人派发 | ❌ | ✅ **改 `effectsMeta.js` + 加派发点** |
| 没有 `HEX_DRAFT` 阶段 | ❌ | ✅ **改 `shared/constants.js` + `match/match/phases.js`** |
| `g.hex` 不是协议类型 | ❌ | ✅ **改 `shared/protocol.js`** |
| import 白名单缺口 | ❌ | ✅ **无关**（不走白名单） |

**换句话说：四个硬阻塞里有三个，本质上就是「往文件里加几行」。**

## 4. 但代价是真实的，而且不在工作量上

### 4.1 你会失去 Forge 全部的保护

- **没有内容哈希对齐**：工坊包有「同一摘要 ⇒ 同一份字节」的保证，补丁式 mod 没有；
- **没有房间级 mod 集合**：工坊包可以按房间选集合，补丁式 mod 一改就是**全局**；
- **没有「装好 ≠ 生效」**：`enabled` / mod 登记册那一套全用不上；
- **没有 `MOD_API_VERSION` 世代协商**：Forge 靠它让老包**响亮地被拒**，补丁式 mod 只会**静默跑错**。

### 4.2 你会永远追 Forge 的版本

Forge 现在是 **0.18.6 / 上游 0.2.6**。你一旦改成补丁式，**每一次 Forge 更新你都要重新对一遍**
`effectsMeta.js` / `phases.js` / `protocol.js` —— 而这三个文件正是 Forge 自己说「上游移植会整段换掉」的地方。

**Forge 设计那套表面表，就是为了让这件事不发生。** 用补丁式 mod，等于**主动放弃**它。

### 4.3 与 Forge 的生态关系会变

补丁式 mod **进不了 Forge 的投稿体系**（它明确「不采纳安装器」）。所以你能**跑**，但拿不到那个生态的
分发/登记/更新机制——而那恰恰是你当初想「转到 Forge」的理由。

## 5. 所以正确的说法是

| 路线 | 我上一轮说 | **修正后** |
|---|---|---|
| **A · 工坊包** | 死了 | **确实死了**（四个阻塞对包是结构性的） |
| **A' · 补丁式 mod** | **漏了** | ✅ **可行**：四个阻塞都是「改几行」，但失去全部保护、永远追版本、进不了生态 |
| **B · Fork Forge** | 可行但贵 | 可行；与 A' 的区别是**你维护自己的树**而不是每次打补丁 |
| **C · 提能力请求** | 部分可行 | 不变 |

**A' 与 B 其实是同一件事的两种做法**：A' 是「在 Forge 上打补丁」，B 是「把 Forge 变成你的分支」。
**B 更诚实**——至少分叉是明说的，而不是每次发版时悄悄重新对一遍。

## 6. 我的修正后建议

**如果你要的是「协议源石跑在 Forge 上」**：

1. **先做 A' 的可行性验证**（成本极低）：在 Forge 上直接改那三处，看协议源石能否起来。
   这能告诉你**引擎层面的真实工作量**——我预估核心是 `effectsMeta` + `phases` + `protocol` 三处；
2. **如果验证通过，再决定 A' 还是 B**：
   - **A'**：你的东西是「Forge 的一个补丁」，每次跟着 Forge 更新重新对；
   - **B**：你的东西是「你的 Forge 分支」，分叉明说，但你要维护那棵树；
3. **无论哪条，都不要指望进 Forge 的投稿生态**——那需要路线 C，而 C 卡在「产品功能不是表面」这条设计上。

## 7. 一句话

**我上一轮错了：四个硬阻塞挡得住「工坊包」，挡不住「补丁式 mod」。**
Forge 把这两类分开，正是为了让「改引擎」这件事**必须被明说**——
它不禁止你改，它禁止你**假装没改**。
