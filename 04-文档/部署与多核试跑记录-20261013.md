## 二、⚠ 试跑抓到一个会立刻崩服的 bug（最重要的收获）

**在真实服务器上以 `SP_SIM_WORKERS=1` 起临时实例（端口 3099），派机器人进房开一局，第 9 秒就崩了：**

```
ReferenceError: Cannot access 'slice' before initialization
    at server/match/match/prep.js:108
```

**根因**：`prep.js` 里 `const slice = () => {...}` 声明在 `if (offloaded)` 分支**之后**，而该分支的
`.then(() => { ... slice(); })` 引用了它 —— **暂时性死区（TDZ）**。

**为什么之前的测试没抓到**：所有测试都走**虚拟时间**（`botSliceMs = Infinity`），
而池的异步分支在虚拟时间下从未被真正走到（见下一节的发现）。**只有真实事件循环才会踩到这一行。**

**已修**：把 `slice` 提到 `offloaded` 之前。修复后重跑：1 worker = 6 次 offload、2 workers = 9 次 offload，**不再崩溃**。

> 这就是业主要求"先起临时实例试跑"的价值——**这个 bug 上线即崩，且不试跑发现不了。**

## 三、第二个发现：虚拟时间下开池会让对局**卡死**

试跑过程中发现：用 `VirtualScheduler`（所有测试与 golden 都用它）配合池时，对局**停在第 1 回合不动**：

```
workers=1 seed=4242 → ended=false round=1 phase=PREP
pool: {"tasks":5,"offloaded":0,"queued":4}
```

**根因**：`runAsync()` 通过 **Promise（微任务）** 收结果，而 `VirtualScheduler` 由**同步** `runNext()` 驱动 ——
同步循环只要还有定时器就**永远不给微任务机会**，worker 的回包（宏任务）也排不上。

**已在 `Match.js` 里从设计上排除**：调度器是虚拟时间时**直接拒绝池**（`!this.sched.virtual` 才接受）。
虚拟时间下调用方（测试/工具）本来就想要主线程满载，池在那里毫无收益、只有卡死风险。
这样也保证**所有既有测试与 golden 永远只走那一条内联路径**。

并补了一条回归测试钉住它。

## 四、试跑的**核心结论**：2 核机器上，池是净亏损

在**真实服务器**（2 vCPU，同时有 43 真人在线）上，同一棵隔离代码树、同一 60/180 秒窗口、同一 seed：

| 配置 | 主线程 CPU / 回合 | 相对 |
|---|---|---|
| **无池**（今天线上） | **3905 ms** / 3920 ms（两次复测） | 基准 |
| `SP_SIM_WORKERS=1` | **4845 ms** / 4895 ms（两次复测） | **+24%** |

**两轮复测高度一致**（±1%），所以这不是噪声。

### 为什么加了 worker 反而更慢？

**因为盒子只有 2 个核，而线上已有 2 个 node 进程 + nginx 在跑 43 个真人。**
worker 线程确实用上了第二核（实测 worker 线程峰值 **165% 单核**、有 5/199 个采样窗口主线程与 worker **同时** >20%），
但：

1. **第二核本来就不空闲**——它被另一个槽的 node 进程占着；
2. 池引入额外开销：把 spec 序列化、跨线程传、结果传回、promise 调度；
3. bot 排练是**脉冲式**的（只在休整期末尾），worker 大部分时间在等，而它占用的调度槽位/内存仍在。

**也就是说**：方案本身在"多核且主线程饱和"的机器上是对的（本机 20 核实测主线程阻塞 **−38%**），
但**这台 2 核小机器不满足前提**。

### 顺带优化掉的一处浪费

试跑还暴露：池路径原本**同时构建 `battles`（完整 Battle 对象，用不上）和 `specs`**，
每个候选还要**快照棋盘两次**。已重构成**二选一**（有池只建 specs，否则只建 battles）。
这一改动把差距从 **+49% 收窄到 +24%**（1050 ms → 800 ms 的额外开销），但**仍不足以翻盘**。

## 七、这次试跑的三点教训

1. **真实事件循环与虚拟时间会走到不同的分支** —— TDZ 崩溃只在真实调度下出现，所有测试都测不到。
2. **"能并行"不等于"更快"** —— 只有在**有闲置核**时才成立；2 核机器上第二核已有主，offload 只是搬来搬去还多了传输成本。
3. **测量必须控制变量** —— 一开始我用真实时限跑，两边完成的回合数不同（1 vs 2），数字毫无意义；
   改成"每回合主线程 CPU"并两次复测才得到可信结论。
