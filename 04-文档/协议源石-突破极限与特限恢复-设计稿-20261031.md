# 协议源石 ·【突破极限】【特限恢复】· 设计稿（实现口径）

> 日期：2026-10-31。业主原话见 §1。范围：两张**普通**协议源石卡（无 `requiresBond`），都只对**抽到卡的玩家自己**生效：
> 【突破极限】3 阶（棱彩）：盟约叠层上限 9999；【特限恢复】2 阶（gold）：拥有者的干员使用 **3 级模组**数据，
> 且**特限模组（ISW / SO / RA）的专属效果**在卫戍协议里生效。

## 0. 已确认事实（业主 2026-10-31 答复）

- 两张都是**普通协议源石**（不限盟约），只对拥有者生效；阶位：突破极限 3 阶、特限恢复 2 阶。
- 【突破极限】9999 上限覆盖：备战期加层、战斗内加层、回合结算、客户端显示（**全部**）。
- 【特限恢复】的 3 级模组：**所有形态**都用 3 级（普通形态现在没有模组，也要给）；「有模组的」= 该干员有模组数据。
- 特限模组：**打开专属效果**（「在集成战略中…」「在生息演算中…」的专属天赋 / 特性在卫戍协议里也生效）。

## 1. 业主原文

> 增加协议源石“突破极限”3阶叠层上限增加至9999；
> “特限恢复”2阶，特限模组可以生效，所有干员解锁3级模组（有模组的）。

## 2. 卡面参数

```js
// hex_break_limit（3 阶 / prismatic / 普通卡）
effect: { bondCap: { cap: 9999 } }

// hex_mode_modules（2 阶 / gold / 普通卡）
effect: { modeModules: { level: 3, types: ['ISW', 'SO', 'RA'] } }
```

## 3. 【突破极限】实现口径（只对拥有者）

- 新增每玩家上限：`bondLayerCapOf(ps)`（server/match/hextech.js）= 默认 `BOND_LAYER_CAP`（999），拥有带
  `params.bondCap.cap` 的卡时取 `max(默认, cap)`。
- `shared/constants.js` 的 `layerGainRoom(before, n, cap = BOND_LAYER_CAP)` 增加可选 `cap` 参数（默认行为不变）。
- 备战：`server/match/player/economy.js addLayers` / 预览、`server/match/bondsMeta.js`（预览）、
  `server/match/match/settle.js`（战斗内加层结算）、`server/match/fields.js`（客户端结果校验）、
  `server/match/invariants.js`（校验）都改用**该玩家**的 cap。
- 战斗：`PlayerBattleInput` 增加 `bondLayerCap`（match 侧写入）；`server/sim/battle/economy.js addLayers`
  用 `battle` 的 cap（缺省 `BOND_LAYER_CAP`）；客户端 `public/js/battle/runner.js` 与 `public/js/ui/watchBonds.js`
  用 battle spec / state 里的 cap（缺省 `BOND_LAYER_CAP`）。
- 9999 上限下「每 25 层发锤子」等里程碑会多很多次 —— 属于卡的效果，不额外限制。

## 4. 【特限恢复】实现口径（只对拥有者）

### 4.1 3 级模组数据（新生成文件 `data/moduleLevels.json`）

- `tools/build-data.mjs` 额外产出一份 `moduleLevels`：对每个有 ADVANCED 模组的干员，把模组 **equipLevel 3** 的阶段
  （`battleEquip[id].phases` 里 `equipLevel === 3`）按现有 `splitModuleParts / moduleAttr / traitRecord /
  moduleTalentChanges` 的同一套逻辑算出记录：
  `{ uniEquipId, name, typeName, typeIcon, icon, level: 3, attr, traitOverride, talentChanges }`，
  按 `uniEquipId` 建 map。**只新增文件，不动其它 data**（`node tools/build-data.mjs --out <tmp>` 已验证当前 data 可逐字节重建）。
- 该文件不计入现有 6 MB 总大小守卫（或把守卫抬到 8 MB，二选一，实现时记录理由）。

### 4.2 组合（拥有者的干员用 3 级模组）

- `server/data.js` 加载 `data/moduleLevels.json`；`server/sim/simdata.js` 暴露 `moduleLevel3(id)`。
- 组合入口：`shared/loadoutRecord.js` 增加 `withModuleLevel3(rec, moduleId, level3Map)`：
  用 3 级记录替换 `rec.module` 的 attr / traitOverride / talentChanges（`stats = statsBase + attr`、
  `trait = traitOverride || traitBase`、`talents = composeTalents(talentsBase, talentChanges)`），
  `module.level = 3`；**普通形态**（`module.active === false`）用该干员的默认模组 id 也套 3 级数据。
- 战斗侧：`server/match/match/combat.js` 组 `PlayerBattleInput` 时，若玩家拥有本卡，给每个 unit 的 loadout 打
  `moduleLevel: 3`（或直接在 `getChess` 组合时传）；`server/sim/simdata.js getChess(id, loadout)` 按它套 3 级数据。
- 备战预览：`server/match/player/prep.js unitStats`（或对应组合处）同样套 3 级数据，保证预览与战斗一致。
- 客户端：备战/详情面板读服务端给的 stats；若详情面板自己组合记录，按同一 helper 处理（实现时确认）。

### 4.3 特限模组专属效果（战斗脚本）

- 新模块 `server/sim/content/hexcards/stone_mode_modules.js`（`installModeModules(hooks)`），
  `BATTLE_SPEC_KEYS` / `HEX_SCRIPT_KEYS` 接 `hex_mode_modules → 'modeModules'`。
- 生效条件：拥有该卡 + 该干员**当前装备的模组** typeName 以 `ISW-` / `SO-` / `RA-` 开头（`u.def.module.type`）。

## 7. 落地补充（2026-10-31 实现时定下的口径）

### 7.1 【突破极限】叠层上限（队友 E）

- `shared/constants.js layerGainRoom(before, n, cap = BOND_LAYER_CAP)`：第三参数是每玩家上限，0/负/非有限 = 无上限（与
  `BOND_LAYER_CAP = 0` 的既有约定一致）。
- `server/match/hextech.js bondLayerCapOf(ps)`：默认 999；认 `data.hexId` 或 `key` 命中的 `hex_break_limit`，
  取 `max(999, params.bondCap.cap)`（只抬高、不压低）。
- 备战：`player/economy.js` 的 `addLayers` / `layerGainOf`（预览）/ `setLayers`、`bondsMeta.bondsWithGains`、
  `player/round.js bondsView`、`match/settle.js`（战斗内加层结算）、`fields.js`（客户端结果上界）、`invariants.js`。
- 战斗：`player/round.js battleInput()` 写 `bondLayerCap`（普通 / 首领 / 联防 / 预览共用这一处）→
  `sim/battle/economy.js _layerCapOf`（per-player input → battle 级 → 999）。
- 客户端：`public/js/battle/runner.js` 按 spec 的 `bondLayerCap` 截断并在 `state().bondCaps` 暴露；
  `public/js/ui/watchBonds.js` 的 strip / popup / 详情 chip 按 owner 的 cap 显示（`screens/game.js` 转发 5 行）。

### 7.2 【特限恢复】3 级模组（队友 F）

- `tools/build-data.mjs` 额外产出 `data/moduleLevels.json`：176 个 ADVANCED 模组在 **equipLevel 3** 的
  `{ uniEquipId, name, typeName, typeIcon, icon, level: 3, attr, traitOverride, talentChanges }`（按 uniEquipId 建 map）。
  只新增文件、其它 data 逐字节不变（`--out` 重建已验证）；数据总大小守卫 6 MB → 8 MB（本文件 199 KB）。
- `server/data.js`：`rawModuleLevels()` / `getModuleLevel3(id)`（缺文件返回冻结的 `{}`）。
- `server/sim/simdata.js`：`DataSource.rawModuleLevels()/moduleLevel3()`；`getChess` / `getDiy` 支持
  `loadout.moduleLevel === 3`（普通形态用 `rec.module.id` 的默认模组也套），缓存 key 加 `|l3`；`normalizeChess` 补
  `module`（`u.def.module` 从此存在，§4.3 的模块靠它判类型）。
- `shared/loadoutRecord.js withModuleLevel3(rec, moduleLevels, moduleId?)`：stats / trait / talents / module 换成 3 级，
  `modules` 列表同条目也换（否则范围判定读 1 级 talentChanges）；不改原对象。
- 接线：`player/round.js battleInput` 在拥有 `hex_mode_modules` 时给己方 chess / 自选单位 `moduleLevel: 3`；
  `sim/battle/players.js` 把 `inp.moduleLevel` 进 loadout；`sim/content/index.js inputLoadout()` 带上；
  `sim/spec.js sanitizeUnitLoadout` 只保留 3 并删掉补位 / 召唤物。
- 预览 = 实战：`match/intents.js _unitStatsOf` 的 `g.unitStats` 走同一份 battleInput，测试逐字段比对。

### 7.3 【特限恢复】特限模组效果（队友 G / H）

- `server/sim/content/hexcards/stone_mode_modules_isw.js`（ISW：空弦 / 水月 / 灵知 / 夕 / 归溟幽灵鲨 / 安洁莉娜 /
  迷迭香 / 琳琅诗怀雅）与 `stone_mode_modules_ra.js`（RA：百炼嘉维尔 / 异客 / 佩佩）；同一张卡、同一个 spec key
  `modeModules`，两个 installer 都装。
- 判定：拥有者自己的干员 + 当前装备模组类型前缀（`u.def.module ?? u.def.raw.module`，type 以 `ISW-` / `RA-` 开头、
  `active === true`）。逐条 [ASSUMED] 见两个模块头注释（含：琳琅诗怀雅只落地再部署半边；佩佩无「资源」⇒ 恒定再部署 -50%；
  异客环境伤害按 `dmg.tags` 含 `'terrain'` 判；归溟幽灵鲨替身按同 Unit `form='doll'` + 同玩家 token）。

### 7.4 已知限制（本次不做，记录在案）

- 客户端**详情面板**（`public/js/ui/gameLogic/loadout.js chessLoadout`）仍按 1 级模组显示属性：战斗与 `g.unitStats`
  预览已经是 3 级；要显示 3 级需客户端加载 `moduleLevels` 并组合（跨 public/js 多文件，后续再做）。
- 补位干员（standIn）不套 3 级：它打的是 data/backups.json 里另一名干员的身体与模组。
- 自选编队（diy）当前是空操作：backups 的模组 id 不在 `moduleLevels` 里（tier-6 形态本来就是 equipLevel 3 的 attr）。
- 召唤物的模组变体仍是 1 级那份（3 级只改干员 def）。
- `data/chess.json` 里带 ISW/RA 模组的只有 12 条记录（11 名干员）；SO- 模组在棋子数据里不存在，故 SO 半边无对象。
