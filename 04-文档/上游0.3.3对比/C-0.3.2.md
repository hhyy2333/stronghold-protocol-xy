## §0 一句话

**值得动，但只能「摘件」，不能「整合」。**
0.3.2 的三件大货里，**只有一件该马上做**（§37.30 的穿透顺序，公式级修复）；

心虚设计师朝向）——**每条 S 级、golden 动 0–4 个场景**，是这节里性价比最高的部分。

## §2 三个「深水区」

### 2.1 (a) 「官方分阶段结算顺序」到底改了什么？我方差在哪？搬不搬？

**上游改了什么（一句话）**：把「一次伤害 = 几个大函数顺序执行」改成「一次伤害 = 一条**有名字的阶段链**，
每个阶段都能被内容以对象请求介入」，并把**伤判效果从"一个聚合判定"拆成"逐 buff 按优先级 → 获取顺序排队"**。
代码落在 `上游:server/sim/attack/{calculation,hit,effects,health,element,transfer,heal,helpers,legacy}.js`（共 978 行）
+ `上游:server/sim/attack.js`（87 行，5 个公开算子）。旧管线 `server/sim/damage.js` 被**删除**
（"第二个内核不再留作独立 oracle"，§37.32 合并修正条）。

**我方差在哪（逐条，带行号）**：

### 2.2 (b) `data/versions/*` 多版本并存怎么做的？对我方有用还是纯负担？

**机制（四层）**：

| 层 | 做法 | 证据 |
|---|---|---|
| 1. 身份 | `shared/versions.js` 纯函数：`DEFAULT_VERSION = 'act2autochess'` + 冻结的 `VERSIONS` 表（4 条，默认排第一）+ 助手 `versionById / versionSlug / versionOfData`。id = 官方 activity id，子版本加 `@V1_1`；路径用 slug（`act1autochess-v1_1`） | §37.22.1 |
| 2. 数据切片 | 非默认版在 `config.json` **最后一个键**写 `config.version = { id, family, rules }`；默认版**没有这个键** —— 所以默认版 `data/*.json` 与旧版**逐键相同**（我实测上游默认版 `data/config.json` 的 23 个键与我方完全一致，无 `version`）。每版 16 文件（15 个生成 + `tuning.json` 字节拷贝），四版合计 48 文件 ≈ 15.0 MB（zip 约 1.3 MB） | §37.22.1、§37.22.3；`上游:data/versions/act1autochess-v1_1/config.json` → `{"id":"act1autochess@V1_1","family":"covenant","rules":{"deployOrder":"rowBottomUp","soloTimed":true,"benchEquip":false,"bossMirrorShare":false}}` |
| 3. `config.version.rules` 是什么 | **历史核心规则开关**：`deployOrder:'rowBottomUp'`（自下而上部署）、`soloTimed`（solo 300 s / 机变 150 s）、`benchEquip:false`（无备选区装备）、`benchFullSwap:false`（备选满不可换，0.3.3 已删）、`bossMirrorShare:false`（不共享首领池）。引擎/对局读它；默认版走代码默认值 | §37.22.7；`上游:docs/SIM.md:1134`、`上游:docs/design/engine.md:20`、`上游:server/match/match/prep.js:57` |
| 4. 谁选 | 服务端只"开放 + 定默认"（`SP_VERSIONS` / `SP_VERSION_DEFAULT` / 构造参数 `versions:{enabled,default,maxHosts}`）；**玩家浏览器偏好**决定大厅版本；**房间只有一个版本**，房主提议 + 在座真人一致投票（60 s 过期）；一版一子进程 match host；静态服务只服务已开放目录，其余 404 | §37.23.1–§37.23.4 |

**两个隐藏成本**（不是"多三个目录"那么轻）：
- **按 charId / effectId 寻址**：第一期复用默认版的 id 却指不同东西（**50/100 个商店 chessId 指另一个干员**，
  `chess_char_1_02_a` 是讯使不是角峰；72 个 item id 带另一个效果）。于是整套手写行为要从"按 id"改成"按它是什么"，
  且只在带 `config.version` 的数据上生效（插件内容集 / 默认数据保持旧行为）—— §37.22.4。
- **19 个第一期干员要单独写 kit**（`ver-<codename>.js`、`VERSION_KIT_FILES`），因为它们的 chessId 在默认版属于别人。

**对我方的判断：纯负担，不搬。** 三条理由都能落到我方文件：
1. **我方是"单季 + 自有内容"结构**：`app/data/config.json` 只有一套 `season/seasonName`（无 `version`），
   自有内容（协议源石 / 盟约专属 / 债务 / 灵魂炸弹 / 黑蛇 / 潘多拉 / 百变）**同时长在数据与代码两侧**
   （`data/{bands,effects,hextech,items,bosses,enemies}.json` + `server/sim/content/**`），且数据由
   `tools/build-data.mjs` 生成（自有内容也在生成器里，实测 35 处命中）。做多版本 = 每版再叠一遍自有内容，
   **三份额外 15 MB 目录 + 三份叠加逻辑**，而玩家能看到的增量只有一个"选老版本"的按钮。
2. **`config.version` 是"要么全有要么全无"的开关**：它一出现，寻址方式、规则开关、素材并集、
   golden 语料（每版 220 / 218 / 269 场景）、match host、静态服务、投票、统计、设置迁移 —— **整条链一起变**。
   我方自有 kit 全部按默认 id 寻址，落地即全部要复查。
3. **反面例外（唯一有用的一点）**：若只想要「第一期」的**内容**（老干员 / 老敌人 / 老盟约）而不要"玩家可选版本"，
   那是另一件事 —— 把老版本的 `chess/bonds/items/effects` **并入我方单套数据**（改 build-data 的合并逻辑），
   不引入 `config.version`。成本 ≈ 一个构建脚本 + 数据体积，**远低于** M0+M1+M2。
   上游 §37.22.3 的表正好是"每版该有哪些表"的清单（chess 200/240/266、bonds 18/23、items 89/115…），可直接用。

### 2.3 (c) `MOD_API_VERSION` 抬了几次？我方现在是多少？

**先纠一个说法**：**`MOD_API_VERSION` 从头到尾是 1，一次都没抬**（0.3.0 → 0.3.3）。
抬的是另一个常量 `PLUGIN_API`（插件/脚本层 API 面），它抬了**两次**：

| 次 | 版本节 | 从 → 到 | 证据 |
|---|---|---|---|
| 1 | `0.19.1-0.3.1` | `{current:1,min:1}` → `{current:2,min:1}`（旧包仍按 `min` 装得上） | `上游:CHANGELOG.md:176-177` |
| 2 | `0.20.0-0.3.2` | `{current:2,min:1}` → **`{current:3,min:2}`**（CHANGELOG 口径） | `上游:CHANGELOG.md:50-52` |
| 实测 | 代码 0.21.0 | 只有 `{current:3,min:1}` —— **`min` 仍是 1** | `上游:shared/constants.js:89` |

> **三处口径互不相同**：CHANGELOG 说 `min:2`，代码是 `min:1`，`上游:docs/PLUGINS.md:138` / `:910` 还写着
> `{ current: 1, min: 1 }`。以代码为准则 **current 3 / min 1**，这条记入待复核。

**为什么抬到 3**（不是推送帧形状变了 —— 那是 `PROTOCOL_VERSION`，一直 2）：因为 §37.32 把结算拆成阶段后，
**插件钩子的语义变了**：
- `kit.onHitBy` / `onHitOn` 明确是"**计算前**"，DEF/RES/屏障/闪避都还没动；`流失` 与元素仪填充**永远不到 `hit`**；
- `kit.onDamagedOn` 变成"HP 步之后"：全吸收报 0、闪避**不报**、特殊生命值报的是**计算伤害**；
- `kit.byEnemyAttack`（= tier1 `byEnemyDamage`）**不再排除 `counter`/`reflect` 标签**（官方反击按来源/类型/路径过滤），
  写反击的 kit 必须自己防重入。

证据：`上游:docs/PLUGINS.md:1943-1953`、§37.32「Merge and review fixes」末条、
`上游:test/plugins/sdk-hooks-settlement.test.js`。
也就是说 **api 3 = "在分阶段结算下重新定语义的 kit 契约"**，它不是独立功能，而是 #15 的下游。
**工坊包不受影响**：包比的是 `MOD_API_VERSION`（仍 1）。

**我方现在**：
- `app/shared/constants.js:84` `PLUGIN_API = { current: 1, min: 1 }`；`:30` `MOD_API_VERSION = 1`；
  `:16` `PROTOCOL_VERSION = 2`；`:34` `APP_VERSION '0.19.36'`；`:46` `UPSTREAM_VERSION '0.3.0'`。
- 校验点 `app/shared/plugins/manifest.js:622`：`m.api` 必须落在 `[min, current]`，**今天是 `[1,1]`**。
  后果：**任何声明 `api: 2` / `api: 3` 的插件在我方判 `PLUGIN_INCOMPATIBLE`**。
- 还有一处要同改：`app/shared/plugins/surface.js:125-126` 把 `PLUGIN_API.min/current` 作为**冻结表面**登记（stable），
  `docs/PLUGIN-API.md:486-487` 也钉着；只改常量不改表面表，测试会红。

**判断：不搬（单独抬 current = 假兼容）。** 我方没有 #15 的分阶段结算，抬到 3 只是放行一批**语义对不上**的插件，
比拒绝更坏。真要做，顺序只能是「先有 api 2 的表面增量 → 再搬 #15 → 再抬 3」，即 #37 完全依附 #15。
便宜的那件事是把 `min` 的语义想清楚；在生态只有自家插件 + 工坊包的前提下，**保持 `{1,1}` 是当前最诚实的状态**。
