# 服务器怎么办 · 2026-10-13 晚实测

> 承接「部署与多核试跑记录」。多核池在这台 2 核机器上是净亏损，所以问题变成：**那到底该怎么办？**
> 以下全部基于刚测出来的数据，不是推测。

---

## 一、现状：**这台机器现在就在极限上**

46 真人在线时逐线程实测（60 秒，120 个采样）：

```
MAIN JS 线程（占单核）: p50 = 6.0%   p90 = 95.6%   p99 = 99.8%   max = 99.8%
余量 p99: 0.2%        超过 80% 的采样: 17 / 120      超过 60%: 19 / 120
```

**主线程已经没有余量了。** 而平均 CPU 只有 10–14% —— 说明瓶颈是**脉冲式尖峰**：
`m.public` 每 100ms 广播 + bot 排练在休整期集中到期，把单核瞬间打满。

**CPU 去向（21 个房间的实测）**：

| 房间类型 | 房间数 | 平均 CPU |
|---|---|---|
| **带 bot** | 7 | **1.33% 单核/房间** |
| 纯真人 | 14 | **0.07% 单核/房间** |

**带 bot 的房间贵 19 倍。** 全站 43 真人 + 16 bot。

## 二、三个可立即执行的措施（按性价比）

### 措施 1 ⭐ 清理槽 B 的 9 个僵尸存档（**免费，立刻回收 227 MB**）

实测发现：**旧槽 B 还在跑，占着 227 MB 内存**，上面挂着 9 个「独立模拟」存档（每个 1 个真人、已挂 **83–188 分钟**）。

**关键判断：这些存档已经完全无法恢复。**

- 槽 B 的 `sockets: 0` —— 9 个会话**全部已断开**
- nginx upstream 指向**槽 A**（:3000），玩家重连会被送到槽 A
- 而会话/房间是**进程内 Map**，槽 A 根本不认识槽 B 的 token（实测：槽 A 64 sessions、槽 B 9 sessions，互不相通）

**也就是说**：那 9 个人**现在重连也回不到存档了**，槽 B 只是一个占 227 MB 的空壳。

```bash
sudo systemctl stop stronghold-b     # 回收 227 MB，零玩家影响
```

> 保留它的唯一理由：万一要 `--rollback` 回旧 build。但新 build 已稳定运行 1 小时、零异常，
> 且**包还在**（`/home/admin/sp-deploy-new.tar.gz`），随时能重新解包。**建议停掉。**

### 措施 2 ⭐⭐ 给 `botRehearsal` 加运维开关（**省 23% 的 bot CPU，不占第二核**）——**已实现**

**原状**：`botRehearsal` **硬编码为 3**（`Match.js:214`），不在 `LOBBY_OPTION_KEYS`、无 `SP_*`、`lobby.js` 不传
—— **运维完全动不了**。

**实测收益**（本机，1 真人 + 3 bot）：

```
botRehearsal=3（默认）: 8062 ms CPU/局
botRehearsal=1        : 6957 ms  (−14%)
botRehearsal=0（纯启发式）: 6207 ms  (−23%)
```

**代价**：bot 少试几个摆阵方案，变笨一点（**人类玩家完全不受影响**——这是 AI 队友的决策质量）。

**已实现**（照 `SP_MAX_*` 的既有做法）：

```bash
SP_BOT_REHEARSAL=0     # AI 只用启发式摆阵（最省）
SP_BOT_REHEARSAL=1     # 只试 1 个方案
SP_BOT_SLICE_MS=4      # 更细：每次调度回调只排练 4ms（默认 8）
```

- **不设 = 行为与今天逐字节相同**（`Match` 仍用默认 3，实测确认）
- 显式 `startServer()` 选项仍然优先
- 输入串（`abc`）保留默认，不会把值变成 `NaN`
- `SP_BOT_REHEARSAL=99` 会被夹到模块上限 8
- **端到端验证**：`SP_BOT_REHEARSAL=0` 与 `=1` 都真实传到了运行中的 `Match.botRehearsal`

**这正是「多核」想解决的问题，但它用「少干活」而不是「换颗核」，而且立刻见效。**

### 措施 3 ⭐⭐⭐ 建议玩家少用 AI 队友（**最大的杠杆，零成本**）

**bot 贵真人 19–23 倍**。线上 43 真人却配了 **16 个 bot**。

如果把这 16 个 bot 换成真人（或让空位就空着），**CPU 会大幅下降**，因为：
- 真人的战斗在**他自己的浏览器**里跑
- bot 的战斗 + 排练在**服务器**上跑，还要占一个主线程切片

具体做法（任选）：
- 房间满员再开始（不加 bot）
- 或者：**把 bot 当"临时补位"，人来了就踢掉 bot**（现在需要房主手动踢）

## 三、不建议现在做的事

| 做法 | 为什么不建议 |
|---|---|
| **开 `SP_SIM_WORKERS`** | 实测 2 核上主线程 CPU **+24%**（复测 ±1%）。第二核已被另一个槽和 nginx 分享，offload 只是搬来搬去还多了传输成本 |
| **加内存** | 内存**不是**瓶颈（RSS 255 MB / 1613 MB，可用 743 MB）。瓶颈是单核主线程 |
| **升级到更多核** | **只有 3 核以上才有意义**（本机 20 核实测主线程阻塞 −38%）。2 核 → 4 核会让 worker 池真正可用 |
| **多进程分片** | 需要外置会话/房间状态或粘性路由，是大工程；先做完措施 1–3 再说 |

## 五、执行建议（今天就能做）

```bash
# 1) 回收 227 MB（零风险：那 9 个存档已经无法恢复）
sudo systemctl stop stronghold-b

# 2) 观察一天，确认新槽稳定（无需回滚）
sudo journalctl -u stronghold-a -n 100 --no-pager
```

**措施 2（`SP_BOT_REHEARSAL`）已经写好并验证**，只等一次部署就能用。建议：

```bash
# 部署新版本后，在 stronghold-a.service 里加一行，然后重载：
#   Environment=SP_BOT_REHEARSAL=1
sudo systemctl edit stronghold-a       # 添加 Environment=SP_BOT_REHEARSAL=1
sudo systemctl restart stronghold-a
```

> 注意：重启会**结束当前所有对局**（房间存内存里）。所以这一步应该**在没人玩的时候做**，
> 或者走蓝绿发布（`sp-release.sh`）而不是 restart——蓝绿是零停机的。

**建议顺序**：先做措施 1（今天、零风险）→ 观察 → 下次发布时带上措施 2 → 视情况调 `SP_BOT_REHEARSAL`。

## 六、一句话回答

> **主线程已经 99.8% 满载，但平均 CPU 只有 10–14% —— 瓶颈是 bot 带来的脉冲尖峰，不是核数不够。**
>
> 所以「怎么办」的答案是**少让服务器干 bot 的活**，而不是「换更多核」：
> ① **停掉那个占 227 MB、存档已无法恢复的旧槽**（免费，今天就能做）；
> ② **`SP_BOT_REHEARSAL` 开关**（已实现、已端到端验证；省 23% 的 bot CPU、不占第二核）；
> ③ **让玩家少用 AI 队友**（bot 贵真人 19–23 倍，这是最大杠杆）。
>
> **多核池要等机器 ≥ 3–4 核才有意义**，现在开反而慢 24%（实测复现 ±1%）。
