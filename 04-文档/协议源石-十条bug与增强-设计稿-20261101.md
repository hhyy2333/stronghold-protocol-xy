## 1. 首领【伤心的大锁】开局秒人 / 「无视不屈」

**报障**：「大锁开局秒人且无视不屈效果伤害有问题」。

**根因**：伤害路径本来就是标准的（`hurt()` → `dealDamage` → `applyHpLoss` → `fatal` → `kill` → `death`），不屈实测
三种伤害（普攻 / 溅射 / 流失）都能触发。真正的问题是**受击反击的计数口径**：`kitDoll` 的 `taken` 把**任何** `damaged`
实例都算一次（包括生命流失、反伤、`noSp` 的持续伤害），而 PRTS 原文是「每受到 **20 次可触发受击回复的伤害**后」——
引擎自己的判据就是 `damage.js applyHpLoss` 里那行 `!dmg.noSp && dmg.type !== 'element'`。盟约盘面上反伤 / 流失 /
DoT 很多，20 次一秒就攒满 ⇒ 开场即全场 800 法术溅射。

**「无视不屈」**：不复现。不屈只保**地面**干员（`bonds/addon/battle.js`，官方口径 + 业主 2026-10-13 的修正），同一次
溅射里高台干员本来就不会被拉回 —— 盘面以高台为主时看起来就像「不屈被无视」。另有 `battle.redeploy` 在休息格被占时
静默失败的边角（不屈掷中了也拉不回来）。

**改动**：`server/sim/content/bosses.js` 的 `taken` 只统计「可触发受击回复」的伤害（跳过 `isHpLoss` / `isRetaliation` /
`dmg.noSp`）。**开局不该发生的事都正常**（终结 icd 480、屏障 icd 60 第 0 秒不升屏障、第 0 秒无 lpLoss），已写成用例。

**业主追加拍板（2026-11-01）：溅射加最小间隔 4 秒**（`aoetrigger.min_interval`，缺省取大锁自己的攻击间隔 4 s；0 = 关闸
回到官方口径）。这是**有意偏离官方**：本模式 8–12 人全在打一个静止、全场射程的领袖，20 次受击 1–3 秒就攒满，官方口径下
全场溅射变成每 1–2 秒一发。实现要点：攒满 20 次后 `P.charged = true`（**计数不清零**），闸内每一发真实受击重新判一次
「距上次溅射 ≥ 4 s」，到点立刻打出；蓄力预警（第 10/30/50… 次）节奏不变。实测同一盘面：溅射时刻从 `[1.03, 3.03,
6.03]` 变成 `[4.03, 8.03, 12.03]`（间隔严格 ≥ 4 s），首个阵亡从 4.27 s 推到 8.03 s；`aoetrigger.min_interval: 6` 时
间隔变 6 s，证明数值确实从数据读。

**[ASSUMED]**：第一发也受闸约束（从上场时刻起算）—— 否则开场那一发仍会立刻落地，「开局不秒人」就不成立。

## 2. 【困毙之雪】：每 5 秒 +1 层霜寒 / 六人口 15 秒真伤

- **A（新增效果，口径：完全无条件）**：「所有【谢拉格】干员每 5 秒获得 1 层霜寒」从 <在场3名> 分支提升为**基础效果** ——
  不要求在场人数、也不要求「场上没有敌人被冻结」（`idleFrostUnconditional: true`；缺省按 true）。3 名档的其它效果
  （攻击施寒 / 解冻回层 / 冰封阻挡真伤）仍要 N ≥ 3 —— 因为 A 之后 1–2 人也能进冰封，冰封阻挡真伤补了显式闸。
- **B（bug）**：<在场6名> 的「全员冰封 → 15 秒真伤」原来只在 0.25 秒轮询里**采样**「全员冰封」，而每名干员的冰封各自
  只有 5 秒，重叠窗口完全可能短于 0.25 秒 ⇒ **整段被跳过**（玩家看到的几秒真伤其实是 3 名档的「冰封阻挡真伤」）。
  改成**事件驱动触发**（进入冰封那一刻判定）+ **绝对截止时刻**（`until = time + 15`）+ `battle.after` 兜底收尾，
  窗口期间不重启不叠加，来源每拍现取（触发者阵亡不哑）。

**[ASSUMED]**：① 霜寒与「3 名档解锁」解耦：1–2 名也能叠、也能进冰封；② 15 秒与「全员冰封」状态解耦（冰封 5 秒结束后
真伤照打）；③ 窗口不延长、不刷新。

## 3. 【炎百兽】：炎佑回血 / 防御力法抗继承

- **A（bug）**：生命共享只有掉血方向，没有 `heal` 钩子 ⇒ 干员被治疗时炎佑不回血。现在**双向**：干员被治疗（含 5 名档
  每秒回血）时炎佑按同数值回血。实现要点：镜像必须用**自我回复**形式（`battle.heal(other, other, …)`），因为引擎有一条
  「友方召唤物（`kind !== 'op'`）收不到别人的治疗」的规则 —— 那条规则就是设计稿里说的【禁疗】；`regen: true` 表示「同一个
  血池里的血量移动」而不是一次新的治疗能力（不再乘一遍 `healingDealtMul`、不受禁疗影响）；超量治疗不凭空造血；标记防递归。
  比例读卡面 `shareHealPct`（缺省 100）。
- **B（业主拍板：100% 继承）**：炎佑的防御力与法术抗性**等于**对应干员的 def / res（100%，**替换**模板值 200 / 0；
  不是「模板 + 干员」，也不是 80%）。比例读卡面 `inheritDefPct` / `inheritResPct`（缺省 100；0 = 关掉）。实现落点
  `server/sim/content/tokens.js` 的 `spawnYanyou`（加可选 `def` / `res`，不传则逐字节等同从前）。

**[ASSUMED]**：继承的是**召唤那一刻**的 def / res；干员之后的变化不回溯。

## 4. 【突破极限】：联防也能叠层

**口径（业主）**：只有**拥有这张卡**的玩家在联防里也能叠层，没拿的人照旧。

**实现**：联防 spec 保持整场 `layerGainsEnabled: false`（老 spec 逐字节不变），另加**每玩家**
`flags.layerGainsByPlayer`（只点名拥有者，判据是卡面 `bondCap.uniteLayers === true`）。唯一读法
`Battle.layerGainsOn(playerId)`：表里点名的听表，否则听整场 flag。消费方 5 处：sim `addLayers`、
`support.gainLayers`（特质主路径）、`settle.js`（非拥有者战报里的层数丢弃，仍走 `layerGainRoom` + `bondLayerCapOf`）、
`fields.js`（客户端战报校验按玩家判）、`runner.js`（盟约条显示按玩家判）。联防 relay 两阶段的层数会合并（原来
`combineUniteResults` 只并 coins/killed/damage/unitStats，会把层数丢掉）。**一个拥有者都没有时不写这个键** —— 测试用同
seed 两局（有卡 / 无卡）证明 flags 去掉新键后 `JSON.stringify` 逐字符相同。

**[ASSUMED]**：老 ref（无 `uniteLayers` 字段）按「拥有这张卡」开启；relay 两阶段层数相加（阶段 2 的输入层数是备战态，
相加是唯一不丢层的读法）。

## 5. 赤刃明霄陈 S3 剑气 vs 木桩：伤害奇高、能打死？

**根因**：剑气 tick 的转向循环里逐次 `w.hit.clear()` —— 被墙角 / 边界卡住时一帧连转 4 次、位置不动，命中表**每帧被
清空**，同一目标**每 tick 命中一次（30 次/秒）**，每次「目标当前生命 6%」（PRTS `hp_ratio` 0.06）= 木桩 20 亿血时
1.2 亿/次。量化：修复前死角里 30 次/秒、6 秒 128.9 亿；修复后 1 次、1.2 亿。

**「能打死」不复现**：木桩的 `fatal` 锁血没有被绕过 —— 3 倍血池、同 tick 连打 30 发致死、逐 tick 致死 ×30，全部停在
1 血且活着（每发 `fatal` 的 `prevented` 独立）；而且每发是 6% **当前**生命、自愈 100%/s，数学上也到不了 0。能复现的
观感是「每次 6% 的掉血闪烁」和死角里血量卡在 ~52%。

**改动**：转向循环不再清空命中表；改成「转了向 **且** 这一帧确实在走 **且** 方向与当前直行不同」才清空（PRTS
「转向后忘记打过的敌人」保留）。**百分比伤害不封顶**（6% 是 PRTS 的数据，1.2 亿只是木桩血量的读数）。

## 6. 【特限恢复】：有特限模组的干员 −2

卡面 `onPrice.specialLimitDiscount { delta: -2, min: 1, types: ['ISW','SO','RA'] }`；「有特限模组」= 该干员的模组记录里
存在 ISW / SO / RA 类型（读已有的 `gd.chess().modules[].typeName`，不新造数据源）。生效点 `economy.js priceOf`（商店显示 /
购买扣款 / 测试场选人同一处），`price = max(min, price + delta)`，只对干员；复制第二份 ref 不会叠成 −4。

## 7. 协议源石发的钱不计入 n19 的 30 块上限

`addFunds` 加 reason 前缀约定：`reason` 以 `hex` 开头（`'hex'` / `'hex_debt'` / `'hex:…'`）⇒ 全额豁免且**不占额度**。
不是新通道：`applySpec` 的每一笔钱本来就写 `'hex'`（战备津贴 / 源石红利 / 装备转化 / 售出返还 / 精英馈赠 / 商店契约 /
远见透支…），债务写 `'hex_debt'`。结算到下回合的钱（战损回收 / 过路费 / 破财消灾）由 `ctx.addPendingFunds` 记
`ps.pendingHexFunds`，回合开始那笔 `income` 按它豁免；走**悬赏通道**的过路费与骑士金神金币（`addCoins(…, { hex: true })`
→ `coinsHex`）也在 `settle.js` 记进 `pendingHexFunds`。回合收入 / 卖出 / 真悬赏照旧受限（**只**豁免协议源石来源）。

## 8. 【战争机器】被复制后队友拿不到第二次 +5

**根因**：`applyHex()` 对 `effect.team` 卡逐目标发（本人 + 所有存活队友），但【复制】的 `drainPendingHexCopies()` 只对复制者
一个人跑 `onHexPick` + `onPick.lp`。**改动**：新增 `applyCopiedHex()`，口径与 `applyHex` 逐字对齐（每个存活队友各跑自己的
`onHexPick` / `onPick.lp` / `m.dispatch`，复制者不重复，死队友不发，`applyHexExtras` 仍只对复制者一次）；复制与策略
「管理员」两条复制路共用它。

## 9. 【绿洲】层数里程碑拖到下回合 / 复制重复发

**根因**：① `runOnPick` 是死代码 —— rung 挂在 `effect.onLayers`，而 `onHexPick` 派发的是 `effect.onPick`，所以「拿到卡时
该盟约已 ≥60 层」要等下一次加层（往往就是下一回合）；② 计数器按 ref 命名空间化 ⇒ 复制第二份 ref 会发两只【缇缇】。
**改动**：获得时用当前层数**回放**这张卡自己的 `onLayers`（`replayLayerGift`，复用模拟器 handler），并让一张卡的所有 ref
共用计数器（`data.sharedCounters`）。战斗内加层 / 回合结算加层本来就当场发。

## 10. 【量产线】：获得时立即给 1 名当前等级阶干员

卡面加 `effect.onPick.chess = { tier: 'level', count: 1 }`（与每回合那条同一个 tier 口径，复用已有的 onPick.chess 通道）。
