# 多人容量移植评估（三者对照）

> 评估对象：两份第三方参考件 vs 本仓现状
> - **F-引擎** = `Stronghold-Protocol-Forge-0.15.0-0.2.4-win-x64`（Forge 分支，自研 0.15.0 + 上游 0.2.4）
> - **P-20人** = `参考对象\Windows.20.v0.2.4-20p.5fix`（LongQianChen `feat/IncreasePlayerCapacity`，上游 0.2.4）
> - **本仓** = `Stronghold-Protocol-repo`（业主 0.3.0 分支，git HEAD `2931f347`，工作树有未提交改动）
>
> 本文**只做评估与方案，不含任何代码改动**。所有行号均已核对到具体位置。

## 0. 结论

1. **两份参考件解决的不是同一个问题，不能二选一。**
   - **F-引擎**回答的是「**怎么让默认行为一行不变**」——它的 `MAX_SEATS` 仍然是 4，容量靠 `SP_MAX_SEATS` 环境变量打开，并且用「条件字段 + 门控」保证 ≤4 座逐字节等价。**这是工程范本。**
   - **P-20人**回答的是「**8/20 人时玩法规则该长什么样**」——固定卡池分组、机变按组并行、联防轮数、领袖血量基准、座位顺序分组。**这是玩法蓝本。**
   - **本仓**目前两样都没有：`MAX_SEATS` 是硬编码常量，且玩法层完全没有多人假设的处理。

2. **本仓的移植成本比 F-引擎低，原因是一个结构性差异**：F-引擎要动 `shared/wireSchema.js`（二进制线格式的行号注册表），本仓是 **JSON 全帧协议**（全仓 `wireSchema` / `viewsDelta` **0 命中**）。新增一个可选字段在本仓是**天然向后兼容**的，在 F-引擎需要同步注册表。

3. **建议路线：抄 F-引擎的架构 + 抄 P-20人的规则表，但本仓有自己的第三条路。**
   本仓的既有约定是「**字段永远存在**」而非「条件字段」（`room.state.visibility` 的注释明写：*always present (never omitted) so the room screen reads one field and the client can never mistake "absent" for a third state*）。因此本仓更适合 **`capacity` 字段恒存在**（4 座时值为 4），而不是 F-引擎的「≠4 才带」。代价是 `room.state` 帧变化，收益是与本仓风格一致、客户端只需一条读法。**见 §4.2 的取舍。**

4. **玩法层（卡池/联防/血量）不能只改常量。** 本仓的 `coopPoolMultiplier = 2` 是**全队共享、与人数无关**的（`gamedata.js:316` 注释原话："shared by the whole co-op team, independent of team size"）——20 人共用一个 2 倍池必然稀缺。这正是 P-20人 引入固定分组、F-引擎引入独立牌库的原因。**不改玩法层而只开座位，会得到一个能进 20 人但玩不了 20 人的房间。**

5. **三个必须先裁决的硬点**（详见 §5、§6）：
   - **A**｜`aliveFull: 4` 把领袖血池夹在 4 人份（`gamedata.js:79`）——20 人房的血条会是 4 人的，必须改。
   - **B**｜`hiddenCore.multi = 1200`（`build-data.mjs:3851`）是隐秘核心激活门槛——扩容后会被轻易突破。
   - **C**｜`RESULT_LIMITS.players = 4`（`shared/protocol.js:34`）是**协议级**上限，20 人的对局结果帧会被它拒绝。

## 4. 该抄谁、抄哪段

### 4.1 直接可抄（纯函数，零依赖）

**`shared/playerCapacity.js`（P-20人，46 行）** —— 这是整个移植里**唯一可以近乎逐字复制**的文件。它是纯 ESM、无 Node API、无状态，服务端与浏览器共用：

```js
export const MIN_COOP_DRAFT_CARDS = MAX_DRAFT_CARDS;
export const GROUPED_POOL_MIN_PLAYERS = 6;
export const MAX_UNITE_ROUNDS = 5;
export const MAX_UNITE_HELPERS = MAX_UNITE_ROUNDS * 2;

const POOL_GROUP_LAYOUTS = {
  6: [3, 3], 7: [4, 3], 8: [4, 4], 9: [4, 5], 10: [4, 3, 3],
  11: [4, 4, 3], 12: [4, 4, 4], 13: [5, 4, 4], 14: [4, 4, 3, 3],
  15: [4, 4, 4, 3], 16: [4, 4, 4, 4], 17: [5, 4, 4, 4],
  18: [4, 4, 4, 3, 3], 19: [4, 4, 4, 4, 3], 20: [4, 4, 4, 4, 4],
};
export function poolGroupSizes(players) { /* 1–5 单池；≥6 查表 */ }
export const poolCopyScale = (groupSize) => Math.max(1, groupSize / BASE_SEATS);
export const uniteRoundLimit = (n) => Math.max(1, Math.min(MAX_UNITE_ROUNDS, n));
export const coopHiddenLayerThreshold = (baseline, players) =>
  Math.ceil(baseline * Math.max(1, players / BASE_SEATS));
```

**注意**：本仓的 `MAX_DRAFT_CARDS` / `BASE_SEATS` 名字与 P-20人 不同，落地时需对齐；`BASE_SEATS` 本仓没有，要新增。

**`shared/constants.js` 的纯函数（F-引擎）** —— `maxSeatsFrom(env)` / `clampSeats(want, max)` 同样是纯函数，可直接抄。**关键纪律**：`shared/` 被浏览器加载且在 `jsconfig.json` 的 typecheck 范围内，**绝不能碰 `process`**——F-引擎的写法是把 `env` 当参数传进来，调用方（`server/lobby.js`、`shared/protocol.js`）各自传 `process.env`。本仓已有同构先例：`server/http/config.js:197 parseCount`。

### 4.2 帧字段：本仓该走第三条路

F-引擎用条件字段换取「4 座帧逐字节不变」。**本仓不必照抄**，因为：

- 本仓是 **JSON 全帧**（`wireSchema` 0 命中），多一个键的成本远低于二进制线格式；
- 本仓既有约定是**字段恒存在**——`room.state.visibility` 的注释（`server/lobby.js:297-299`）明写：*ALWAYS present (never omitted) so the room screen reads one field and the client can never mistake "absent" for a third state*；
- 条件字段会让客户端出现「有/无」两条读法，与本仓风格相悖。

**建议**：`room.state` 恒带 `capacity`（4 座时为 4）。代价是 `test/lobby.test.js` 一类断言要同步；收益是客户端一条读法。**若业主更看重「零测试改动」，则改抄 F-引擎的条件字段。**

### 4.3 玩法层：先 P 后 F

| 层 | 抄谁 | 理由 |
|---|---|---|
| 卡池分组 | **P** —— `createPoolGroups` 按座位顺序切 3/4/5 人组 | 规则明确、已实测、不需要改客户端帧形状 |
| 机变 | **P** —— 每组独立六张 | 但本仓机变帧形状需评估（P 的方案加了 `draftId`/`groupId`） |
| 联防 | **P** —— 轮数 = 固定组数 | **不要**抄 F 的 `unite100.mjs`（535 行、每队一战场、改帧形状、B 项被单列一期） |
| 领袖血量 | **P** 的规则 + **F** 的修法 | P：`bloodPoint × 开战存活人数`；F 的修法是 `max(aliveFull, seatCap)` 而非改数据 |
| 独立牌库 | **暂不抄** | F 自己标注为「设计级 A」，且有**未结的平衡账**（`hiddenCore.multi = 1200` 被轻易突破，作者实测 32 座 `layerSum = 10073` ⇒ 每局都进隐秘核心） |

## 8. 建议不做的事

1. **不要把 `MAX_SEATS` 直接改成 20。** 这是 P-20人 的做法，代价是「4 座房也走新代码路径」，无法用「默认不变」证明没坏。F-引擎的 `SP_MAX_SEATS` 是更好的形状。
2. **不要抄 F-引擎的 `unite100.mjs`。** 535 行、改联防帧形状、作者自己把 B 项（机变按小队）单列一期未做。P-20人 的「轮数 = 固定组数」简单得多。
3. **不要抄 F-引擎的独立牌库（设计级 A）。** 它有**未结的平衡账**：`hiddenCore.multi = 1200` 在独立池下被轻易突破（作者实测 32 座 `layerSum = 10073`），意味着**每局都会进隐秘核心**。这是玩法平衡改动，不是可移植的自包含项。
4. **不要在本机声称任何测试通过。** 见 §7.1 的测量纪律。
