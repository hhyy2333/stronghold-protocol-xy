## 根因一：浮游（drone）记账模型重构 —— 14 处

**这是唯一的大根因**，对应 CHANGELOG 的 PR #535 / #536 / #537。

### 0.2.5 改了什么

`server/sim/ai.js:327-346`，官方把浮游伤害**拆成两次独立结算**：

| | 金额 | `isAttack` | tags |
|---|---|---|---|
| **本体一击**（旧版只有这一次） | `atk × scale × mulT`（**不含**浮游倍率） | `true` | `prof.tags` |
| **浮游附加**（0.2.5 新增） | `atk × scale × mulT × funnelMul` | `false` | `[...tags, 'addition', 'funnel']` |

旧版是**一次结算**，浮游倍率折进 `mulT`，且 `isAttack = true`。

代码原文：
```js
const attachedFunnel = !!prof.funnelMul && prof.funnelBodyHits !== 0;
if (!attachedFunnel) mulT *= funnelMul;          // 旧路径：倍率进本体
...
if (attachedFunnel && info.index === 0) {        // 本体一击（倍率=1）
  for (let h = 0; h < bodyHits && target.alive; h++)
    dealtMain += b.dealDamage(u, target, { amount: atk * scale * mulT, isAttack: true, ... });
}
for (let h = 0; h < hits && target.alive; h++) { // 浮游附加（乘 funnelMul）
  const d = { amount: atk * scale * mulT * (attachedFunnel ? funnelMul : 1),
    isAttack: !attachedFunnel, tags: attachedFunnel ? [...tags, 'addition', 'funnel'] : tags, ... };
  dealtMain += b.dealDamage(u, target, d);
}
```

### 为什么测试会红

绝大多数测试用 **`.dmg.isAttack`** 过滤"这一次攻击"，于是**只拿到本体一击**（倍率 1.0），而期望值填的是**浮游倍率**（如 `0.2`）。

**铁证**：`op_gdglow` 的失败值是 `206.04 vs 41.208` —— **正好 5 倍**。测试期望 `ramp = 0.2`（tier5 的 `init_atk_scale`），实得是 1.0 倍的本体。

## 根因二：受击格取整 `roundHalfEven` —— 影响 #12 / #13（已并入上表）

CHANGELOG #520 / PR #520，官方把 `Math.round` 换成**四舍六入五成双**：

```js
// server/sim/targeting.js
- const r = Math.round(u.y), c = Math.round(u.x);
+ const r = roundHalfEven(u.y), c = roundHalfEven(u.x);
```

`server/sim/{targeting,body}.js` 共 **8 处**改为 `roundHalfEven`。
**后果**：站在边界（坐标 x.5）的敌人，归属格子会变 → 范围判定结果变 → 「在范围内/不在范围内」的断言翻转。

## ⚠️ 补记 2：`test/i18n.test.js` 红 —— 18 处中文没进 i18n 管道（已修）

同一批排查里撞出来的。`test/i18n.test.js` 有一条硬规则：**`public/js`、`shared`、`server`（`server/sim` 的
字面量除外）里不许有"没包过的中文字面量"**（官方面向玩家的文案必须走 `t()`，msgid 进 `public/i18n/en.json`）。
`public/admin/` 里那份面板**故意在管道之外**（它自带 `STRINGS` 表，见 `public/admin/admin.js` 顶部说明），
所以它不受这条规则管——但**服务端/共享层的诊断文案**受管。

红的 18 处（都在 2026-10-13 那批新功能里，与性能面板无关）：

| 文件 | 行 | 内容 |
|---|---|---|
| `shared/updateNotes.js` | 187–198（12 条） | `notesErrorText()` 的中英对照错误理由 |
| `server/admin.js` | 653/654/670/671 | 公告接口未启用的中英对照 message |
| `server/match/match/platform.js` | 113 | `` `bad 自选 pick ${id}` `` |
| `shared/dataPacks.js` | 56 | `…the 内容 mod registry…` |

**改法：改成 ASCII 英文诊断**，而不是硬塞进 i18n 包。理由：

1. 这些是**运维/开发诊断**，不是面向玩家的文案——面板自己会用本语言的外框包住它
   （`保存失败：{why}` / `Save failed: {why}`），底层技术细节用英文是这个代码库既有的惯例
   （同文件里 `loadout locked for this match`、`loadout swap is a prep action` 本来就是英文）。
2. 进 i18n 包意味着 4 个语言包（en / ja / ko / zh-TW）都要补齐这 18 条译文，收益是一个运维细节的多语言化，
   代价是 72 条翻译与 4 个包的同步风险——**不划算**。
3. **玩家能看到的更新公告正文不受影响**：那是**数据**（`{ version, date, headline, sections }`，
   每条文本带 `zh`/`en`/`ja`/`ko`），不是字面量，照旧完全多语言。

> 注意 `notesErrorText()` 的既有约束不能破：`test/update-notes-server.test.js:121` 要求每个错误码返回**非空**
> 文本，`:340` 要求 `BAD_DATE` 的文案**包含 `YYYY-MM-DD`**。改完后 78 项 i18n / 公告 / 数据包测试通过。

## 观察（已定位并修好）：一次浮点 1-ulp 闪烁 —— **是我自己新写的测试**

`test/match` 一批文件连跑时，**有一次**出现：

```
actual: 0.6, expected: 0.6000000000000001   (operator: strictEqual)
```

**已定位**：不是模拟层，也不是插桩，而是**我这次新增的 `test/match/perf.test.js`** 里
「总览合计 = 各房间之和」那条断言。两边各自四舍五入到两位小数，两次舍入的**和**不保证与**和的舍入**在最后
一个 ulp 上相等（`0.57` vs `0.5700000000000001`）。

**修法**：把断言改成「按**发布精度**相等」——`Math.abs(second.totalMs - total) < 0.01`，
并在注释里写明为什么不能用 `===`。改完连跑 **6 次全绿**。

> 顺带说明：这条也解释了之前那 5 次「全绿」的复现困难——它只在**两个房间的耗时恰好落在舍入边界**时触发，
> 概率低但真实存在。**与 0.2.5 合并无关，与性能插桩本身也无关**（插桩只读时钟，不做算术）。
