## 二、真家伙（能不能落地复用）

包的**核心结论**是：传输层压缩 `perMessageDeflate` 是 `WebSocketServer` 的**启动选项**，工坊包碰不到。这个结论**完全正确**，我也实测复现了它的边界（见下）。

但结论的**另一半**是本仓库的真机会：

```
server/http/websocket.js:41
  const wss = new WebSocketServer({ noServer: true, maxPayload: WS_MAX_PAYLOAD, perMessageDeflate: false, clientTracking: false });
                                                                                            ^^^^^^^^^^^^^^^^^^^^^ 关着的
```

**工作区里没有任何一处实现了传输层压缩**，我全盘扫过：

| 位置 | `perMessageDeflate` |
|---|---|
| `Stronghold-Protocol-repo\server\http\websocket.js:41` | `false`（开发版 0.3.0） |
| `参考对象\Stronghold-Protocol-v0.2.5\...\server\http\websocket.js:40` | `false` |
| `参考对象\Stronghold-Protocol-Forge-...\app\server\http\websocket.js:58` | `false` |

**一个都没开。** 连 Forge 都没有。这就是能直接薅的地方。

### 为什么这笔特别划算

卫戍协议的 `m.public` 是**每 100 ms 广播一次的全量公开状态**（`server/match/match/common.js:22` `PUBLIC_THROTTLE: 100`），而且**前后帧高度相似**——同一批玩家、同样的 bond 结构、只变几个数字。这正是 permessage-deflate 上下文保持的完美猎物。

## 三、实测硬数字（真机、真 socket、逐字节回读校验）

环境：`node v24.19.0` / `ws 8.22.0` / Windows。脚本在 `_verify\`。

### 1. 主对照：真实 `m.public` 帧（4 人席，2340 B/帧）

| 档位 | 实收/帧 | 每连接带宽（100 ms 一帧） | 压缩倍数 | 握手协商串 |
|---|---|---|---|---|
| **off（仓库现状）** | 2344.0 B | **22.89 KB/s** | 1.00x | `(无 Sec-WebSocket-Extensions)` |
| **on（`{threshold:64}`）** | 35.9 B | **0.35 KB/s** | **65.24x** | `permessage-deflate` |
| on + `serverNoContextTakeover` | 319.0 B | 3.12 KB/s | 7.34x | `permessage-deflate; server_no_context_takeover` |

**每连接省 98.5% 带宽。** 一个人省 22.5 KB/s，100 人省 2.2 MB/s，2000 并发（`net.js` 的 `maxConnections`）省 ≈ 45 MB/s。

### 2. 变化内容下的上下文保持（300 帧，平均 2357 B/帧）

| 档位 | 实收/帧 | 倍数 |
|---|---|---|
| 上下文保持 ON（默认，不声明） | 92.4 B | **25.50x** |
| 上下文保持 OFF（safe 档） | 343.0 B | 6.87x |
| 关闭压缩 | 2361.0 B | — |

**关掉上下文保持 = 只剩 1/4 收益**，与参考包 `ws-compression.json:38` 说的"少拿约 3/4"**吻合**。

### 3. ⚠️ 纠正：参考包对 `threshold` 的说法**只对了一半**

参考包说（`ws-compression.json:24-25`）：

> ws 把 threshold 当硬开关：低于它的帧以 rsv1=0 发出，即完全不压。旧值 512 配上帧瘦身后让 61% 的热帧静默失去压缩。

**实测 + 源码级验证：这条只在「上下文保持被关掉」时才成立。**

决定性源码在 `node_modules/ws/lib/sender.js:371-384`：

```js
if (this._firstFragment) {
  this._firstFragment = false;
  if (rsv1 && perMessageDeflate &&
      perMessageDeflate.params[perMessageDeflate._isServer
        ? 'server_no_context_takeover'      // ← 仅当这一侧关掉了上下文保持
        : 'client_no_context_takeover']) {
    rsv1 = byteLength >= perMessageDeflate._threshold;   // ← 才拿 threshold 当开关
  }
  this._compress = rsv1;
}
```

实测（高熵载荷，实收≈原样即"没压"）：

| 帧大小 | 保持 ON（默认） | 保持 ON th=1024 | 保持 OFF th=64 | 保持 OFF th=1024 |
|---|---|---|---|---|
| 100 B | 压 | **压** | 不压 | 不压 |
| 200 B | 压 | **压** | 压 | 不压 |
| 600 B | 压 | **压** | 压 | 不压 |
| 2000 B | 压 | 压 | 压 | 压 |

**保持 ON 时，`threshold` 设 64 还是 1024 完全没区别，所有帧都压。** 所以：

- 参考包说"旧值 512 让 61% 热帧失去压缩"——**成立的前提是那一侧上下文保持是关的**。
- 默认档（不声明任何选项 → 上下文保持开）下，`threshold` 是**惰性参数**，写成 64 只是"防一手 + 表意"，不是收益来源。

**真收益来自上下文保持，不是来自阈值。** 这一点照抄会误判，必须点出来。

### 4. 实测复现参考包「显式声明会拒客户端」的警告 —— 属实

| 服务器设置 | 客户端 offer | 结果 |
|---|---|---|
| 不声明（交给协商） | Chrome 风格 | `permessage-deflate` ✅ |
| 显式 `serverNoContextTakeover: false` | 要求 `server_no_context_takeover` | **HTTP 400，连不上** ❌ |

与参考包 `ws-compression.json:16` 的说法**逐字吻合**：ws 把"不可接受的协商"变成 HTTP 400，是**连不上**不是降级。所以 **绝对不要显式写 `serverNoContextTakeover: false` / `serverMaxWindowBits`**。

## 四、落地补丁（可直接上，实测全绿）

### 唯一必改点：`server/http/websocket.js:41`

```diff
-  const wss = new WebSocketServer({ noServer: true, maxPayload: WS_MAX_PAYLOAD, perMessageDeflate: false, clientTracking: false });
+  // permessage-deflate（RFC 7692）：m.public / m.private 是每 100 ms 一次的高相似度 JSON，实测 25–65x。
+  // 故意【不声明】serverNoContextTakeover / serverMaxWindowBits —— 声明等于"要求"，
+  // ws 会把不可接受的协商变成 HTTP 400（实测：客户端要求 server_no_context_takeover 而服务器显式 false
+  // → 握手直接 400，是连不上而不是降级）。不声明 = 交给协商，谁都不会被拒。
+  const wss = new WebSocketServer({
+    noServer: true,
+    maxPayload: WS_MAX_PAYLOAD,
+    perMessageDeflate: { threshold: 64 },
+    clientTracking: false,
+  });
```

顺带改文件头第 5 行的注释（现在写的是 `no per-message deflate`，改完就不对了）。
